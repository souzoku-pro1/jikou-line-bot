# UX-PENDING-1 画面設計（対応待ち運用を「通知タップ → 1 画面 → 返信」に一本化）

票: UX-PENDING-1。ブランチ feature/ux-pending-1（origin/main `ce92973` から）。本書は **実装前の設計** です。大野が読んで確認するための文書なので、画面ごとに「何が見えて・何を押すと・何が起きるか」を書きます。確認後に実装します。

## 0. 結論（1 枚で）

- 業務 LINE の【対応待ち】通知に **その件を開く URL** と **「対応終了」にする URL** を入れます。タップ → （ログインしていなければログイン）→ その件に着地します。URL に氏名・LINE の ID・本文は入りません。
- 「対応待ち」と「承認キュー（未送信）」を **1 つの画面** にまとめます。各件に **[返信する] [対応終了] [不要]** の 3 つだけ。
- 返信画面は **[送信] ボタンに文字を出し**、「確認していません」のチェックをやめ、**送信時にサーバーが自動で確認** します。問題があれば送らずに理由を表示します。
- 上部メニューに「対応待ち」を足します（承認の隣）。古い /app/pending はそこへ飛びます。
- 署名付きリンクでできるのは **「開く」と「対応終了にする」だけ** です。リンクから顧客へ送信されることはありません。

## 1. 全体の流れ

```
 相談者の LINE 受信 → bot が自動返信できない
        ↓
 業務 LINE に【対応待ち】通知（本文なし・URL 2 本）
        ↓ タップ
 [A] 返信画面 /app/reply/No.   ←── ログインが要れば先に /app/login、終わったら自動でここへ
        ↓ [送信]
 サーバーが自動確認 → 問題なし: LINE で送信・対応待ちは自動で閉じる
                    → 問題あり: 送らずに理由を表示

 （別の方法＝LINE アプリ等で返信してしまったとき）
 通知の 2 本目の URL → [C] 確認画面 1 枚 → [対応終了にする] → 閉じる（送信なし）

 （一覧から探したいとき）
 メニュー「対応待ち」→ [B] 対応待ち画面 /app/inbox → 各件の 3 ボタン
```

## 2. 画面 B: 対応待ち（統合一覧）  `/app/inbox`

**見出し**: 「対応待ち」。説明文は 1 行だけ:「bot が自動返信できなかった相談と、未送信の返信下書きの一覧です。」

**並び**: 古い順（上が一番待たせている件）。既定は **未処理だけ**。画面下に「閉じた件も表示する」のリンク（直近 50 件・参照のみ）。

**各件のカード（上から）**

1. 相談者名（承認キューにある名前。無ければ「（お名前未登録）」）と受付時刻（「今日 16:58」の形式）
2. 状態の札（最大 3 つ・色付き）: 「bot 停止中（対応中）」「承認待ちの下書きあり」「初回 1 通（J-0）送信済み」など。理由は人の言葉にします（例: 「承認降格（下書きあり）」→「bot が判断できず下書きだけ作成」）。
3. お客様からのメッセージ（承認キューの本文。対応待ちだけで承認キューが無い件は「LINE アプリで受信をご確認ください」）
4. **ボタン 3 つ（横並び・指で押しやすい高さ）**

| ボタン | 押すと | 記録 |
|---|---|---|
| **返信する** | 画面 A（返信画面）へ移動 | なし（移動だけ） |
| **対応終了** | 「別の方法で返信済み」として閉じる。bot を再開する（対応中を解除） | 対応待ち: 状態 `closed_external`・履歴に「人・画面から」。承認キューだけの件: 閉じた記録表に 1 行 |
| **不要** | 返信不要として閉じる（bot の再開はしない） | 対応待ち: 状態 `not_needed`（現行どおり）。承認キューだけの件: 閉じた記録表に 1 行 |

- **対応終了** と **不要** は押した直後に閉じ、画面上部に「対応終了にしました（No.123）」と 1 行出ます。取り消しは「閉じた件も表示する」から **[未処理に戻す]**（これも記録に残す・物理削除なし＝RV-08）。
- 承認キューが無い対応待ち（LINE 側で bot が無言にしただけの件）は **返信する** ボタンの代わりに「LINE アプリで返信 → 対応終了を押してください」と出します（返信画面は承認キュー No. が無いと宛先を解決できないため・現行と同じ制約）。
- **V2 以前の承認キュー項目**（対応待ちの表が無く、kintone の承認キューに「送信済み=no」で残っている件）も同じカードで出し、同じ 3 ボタンで閉じられます。閉じた記録は Railway の DB（新しい表 `approval_close`）に残し、kintone は書き換えません（kintone 書込は承認がないため・必要なら別票）。

**空のとき**: 「対応待ちはありません」だけ。

**fix2 BU-09（走査の続き）**: 承認キューの未送信は 1 回に 500 件まで走査します（閉じ済み・対応待ちが参照する No. を除いた未処理が 50 件に達するまで）。
500 件で上限に達したときは「承認キューの未送信を 1〜500 件目まで走査しました（この範囲の未処理 0 件）。続きがあります。」と **[続きを読み込む（次の 500 件）]** が出ます
（未処理 0 件の「対応待ちはありません」とは区別）。除外する No. が 100 件以下なら kintone の問い合わせ条件で除外し、1 回で到達します。

**fix2 BU-08（解除の要確認）**: 「対応終了」を押したとき、その相談者の **会話と対応中の世代を特定できなかった件**（承認キューだけの件で LINE userId を引けない・会話の記録が無い）は、
bot の対応中を **自動では解除しません**。一覧の上部に「解除の要確認」として出し、現在の状態（bot 停止中（対応中）／対応中ではない／会話の記録なし／相談者を特定できない）を表示します。
大野が **[対応中を解除する]** を押したときだけ、その時点の世代を取得して解除します（解除に失敗したときは、取得した世代を先に記録してあるので、回収ジョブはその世代にだけ再試行します）。

**旧 URL**: `/app/pending` は `/app/inbox` へ転送（303）。旧画面のボタン（不要にする・対応終了（bot 再開））は新画面に統合します。

## 3. 画面 A: 返信画面  `/app/reply/{承認キュー No.}`（変更点だけ）

現行の構成（相談者名・お客様のメッセージ・直近のやり取り・返信文の欄）は変えません。変えるのは 4 点です。

1. **[送信] ボタン**: 文字を「送信」にし、**紺地に白文字・太字・幅いっぱい** にします（他のボタンは白地のまま）。ボタンの文字色と背景色を CSS で明示し、`<meta name="color-scheme" content="light">` を全画面に足します。
   - ラベル欠落の原因について: HTML 上はラベル「LINE で送信する」が出力されています（コードで確認）。したがって欠落は **端末側の描画** で起きています。現行 CSS はボタンの **背景色（白）だけ指定して文字色を指定しておらず**、ダークモード／ブラウザの強制ダーク表示では文字色が背景と同化し得ます。iPhone の Safari では「確認していません」のチェックが未チェックのまま [送信] を押すと **何も起きない**（iOS は必須チェックの警告を出さない）ため、「文字がない・効かないボタン」に見えた可能性もあります。対策は上の明示色＋チェック廃止で両方をつぶします。**大野へ確認**: 端末（iPhone/Android）・開いたアプリ（Safari/Chrome/LINE 内ブラウザ）・ダークモードの有無を 1 行で教えてください（実装後の実機確認にも使います）。
2. **「全体停止・停止リスト・人対応中の状態は確認していません」のチェックを廃止**。代わりに [送信] を押したとき **サーバーが自動で確認** します（§5）。
3. 画面の上部に **いまの状態** を札で表示します: 「全体停止中（bot）」「停止リスト登録あり」「人対応中」「対応中（bot 停止）」。送る前に目で分かるように。
4. **「この返信を手本として保存する」は残します**（既定 ON のまま）。
5. 上の戻りリンクを「対応待ちへ戻る」にします（承認・送信確認待ちへのリンクも残す）。

送信後の表示（「送信しました」「同じ相談者の対応待ち 1 件を閉じました」など）は現行どおり。

## 4. 画面 C: 対応終了の確認画面  `/app/go/close/{署名付き符号}`

通知の 2 本目の URL から来る画面。**1 枚だけ**、文章は 3 行。

```
対応終了にしますか？
（この相談者に、LINE アプリなど別の方法で返信済みのときに押してください。bot を再開します。顧客への送信はしません）
相談者: ○○ 様　受付: 今日 16:58
[ 対応終了にする ]   [ やめる（対応待ちへ） ]
```

- [対応終了にする] は POST。処理後は「対応終了にしました」と出て、対応待ち画面へ戻ります。
- **同じ URL をもう一度開いても二重に処理しません**（既に閉じていれば「この件は 17:05 に対応終了になっています」と出すだけ＝冪等）。
- 符号が改ざんされている・期限切れ: 「リンクが無効です（期限切れか、改ざんの疑い）。対応待ち一覧から開いてください」＋一覧へのリンク。詳細理由は出しません。

## 5. 送信時のサーバー側自動確認（返信画面の [送信]）

いままで大野がチェック 1 つで「承知のうえ送る」としていた 3 条件を、サーバーが実際に読みに行きます（bot の送信前チェックと同じ関数 `send_policy.conditions()` を使います）。判定表は既存の許可表「大野の明示送信」列（`send_ledger.decide_send(actor=human)`）をそのまま使い、**チェック無し（explicit_confirm=False）で実値を入れる** だけです。

| 条件 | 読む場所 | 結果 | 送る？ | 画面の文言 |
|---|---|---|---|---|
| 全体停止 | env AUTOREPLY_PAUSED | 停止中 | **送る**（人の返信は bot のブレーキの対象外・札で表示） | — |
| 停止リスト（App 39） | kintone | 登録あり | **送らない** | 「この相談者は自動返信停止リストに登録されています。送信していません。送る場合は停止リストから外してください」 |
| 停止リスト | kintone | 照会できない | **送らない** | 「停止リストを確認できなかったため送信していません。しばらくして再試行してください」 |
| 人対応中（App 21 response_mode） | kintone | 人対応 | **送る**（大野本人の返信なので当然） | — |
| 人対応中 | kintone | 照会できない | **送らない** | 「相談者の対応モードを確認できなかったため送信していません。しばらくして再試行してください」 |
| 対応中（bot 停止） | 台帳 | 対応中 | **送る**（現行どおり・送信で対応中＝人に更新） | — |

- 「送らない」のときは **LINE へは何も送らず**、本文は欄に残したまま理由を表示します（やり直しは同じ画面で可）。
- **裁定をお願いしたい点**: 「照会できない」を送らない側に倒すのは fail-closed の規律に合わせた案です。急ぎのときは LINE アプリから直接返信できます。「照会できないときも送る（札で警告だけ）」にする場合はその旨をください。

## 6. 通知文（業務 LINE）

### 6-1. 【対応待ち】通知（`send_policy.notice_text`・承認台帳の対象外）

```
【対応待ち】自動返信できない問い合わせがあります。
承認キュー No.123・カテゴリ: その他判断系
返信する: https://<公開ドメイン>/app/go/r/<符号>

```

- 承認キューが無い件は 1 本目の代わりに「一覧で確認: https://<公開ドメイン>/app/inbox」（返信画面を開けないため）。
- 氏名・本文・LINE の ID は従来どおり入れません。符号にも入れません（§7）。
- 公開ドメインは Railway が注入する `RAILWAY_PUBLIC_DOMAIN` だけを使います（診断リンクと同じ・未設定なら URL 行を出さず従来文面）。

### 6-2. 経過通知（1 日 2 回・承認台帳の定型 `ops_age_notice_v1`）

件数だけの通知なので「該当件」はありません。末尾の「/app/pending からご確認ください。」を **完全な URL** にします。この文は承認済み定型なので **新しい版 `ops_age_notice_v2` として大野の承認が必要** です（本文は票の成果物で提示・承認までは v1 のまま送る）。

```
【対応待ち・未返信】
未返信の対応待ち {{open}} 件（{{threshold}} 分超 {{over}} 件・最長 {{oldest}} 分経過）・再処理待ち {{queued}} 件
https://<公開ドメイン>/app/inbox からご確認ください。
```

- 差し込みは数値 5 つ＋URL 1 つ（URL は固定の基底＋固定の path だけ・件ごとの値は入らない）。

## 7. 署名付きリンクの仕組み（技術メモ・大野は読み飛ばし可）

- 符号の形: `<種別>.<pending_id>.<有効期限 unix 秒>.<HMAC-SHA256 先頭 32 桁>`。鍵は既存の `WEBAPP_SESSION_SECRET`（画面のセッションと同じ鍵・`webapp_auth._sign` を再利用）。
- 種別: `r`（返信画面を開く）／`c`（対応終了の確認画面を開く）。`c` の符号で `r` の操作はできない（種別が署名に入る）。
- 期限: **72 時間**（通知から 3 日。切れたら一覧から開く）。
- 識別は `pending_id`（DB の **連番・署名付き**）。氏名・LINE の ID・本文・会話参照は入れない。
  - **fix1 BU-06（Codex R-UX1・裁定）**: 連番の露出は許容する。理由: HMAC 署名で改ざん・推測した番号の利用はできない／通知の閲覧者は
    大野のみ／漏れる情報は件数の目安程度。初版の「不透明」の記述はこの裁定で訂正（コード変更なし）。
- 検証: 形式 → 署名（compare_digest）→ 期限 → 件の存在、の順。どれかに落ちたら固定文言（§4）。ログは「リンク無効（固定語彙）」だけ。
- **ログイン後の着地**: `/app/go/...` は認証関所（`_gate`）の内側。未ログインなら `/app/login?next=<path>` へ。`next` は **`/app/go/` と `/app/inbox` と `/app/reply/` で始まる相対 path だけ** 受け付け（それ以外は従来どおり `/app` へ）、ログイン成功後にそこへ 303。外部 URL・`//`・改行は拒否。
- リンクからできる操作は「開く」と「対応終了（確認画面つき）」だけ。**顧客への送信は返信画面の [送信] のみ**（承認なし送信経路ゼロは不変）。

## 10. 試験用 LINE アカウント（要件 6・提案のみ・実施は大野の承認後）

状況: 大野の試験アカウントは App 21 に 8 月からのヒアリング中レコードがあるため、受信は常に **ヒアリング経路** に入り、分類（triage）・許可表（V2）・apply_v2 を通りません（11/3 16:58 の 2 通で確認済み）。

| 案 | やること | 本番データ | 評価 |
|---|---|---|---|
| **C（推奨）env の allowlist** | `JIKOU_TEST_USER_HASHES` に試験アカウントの **ハッシュ**（`sha256("jikou:" + userId)`・大野が手元で計算・値はチャットに出さない）を置く。受信時にハッシュが一致したら、App 21 の status に関わらず **顧客対応経路（分類→guard→許可表→apply_v2）** に入れる（メモリ上の扱いだけ。App 21 は読むだけ・書かない） | 触らない（App 28 のログと App 29 の下書きは通常どおり作られる＝試験の痕跡は残る） | 実機で本番と同じ経路を通せる。切替は env だけ・空なら無効 |
| B 新しい試験アカウント | 別 LINE アカウントを友だち追加し、App 21 に status 受任前のレコードを **大野が手で** 作る | レコード 1 件追加 | 仕組みの変更なし。ただし App 21 に手入力が要る |
| A 既存レコードの status 変更 | 試験アカウントの App 21 status をヒアリング外に変える | **本番レコードを変更** | 不採用（ヒアリング記録を壊す） |

- C の注意: allowlist は **経路の選択だけ** に効かせ、許可表・停止リスト・台帳・承認は本物のまま通します（試験でも承認なし送信経路は作らない）。ログには `[ROUTING] test allowlist → customer` の固定語彙だけ。
- C は本票では **設計と env 名の予約まで**。実装は大野の承認後（同じブランチに 1 commit 追加か、別票）。
