# 時効診断フォームの二重送信抑止（FORM-DUP-1）— 設計の要点と既知の制約

対象: `shindan_form.py`（HP の時効診断フォーム `/shindan`・App 21 への保存）。票 FORM-DUP-1 と fix1〜fix8（Codex R-FD1 BF-01〜BF-14）。テスト: `test_form_dup_1.py`・`test_form_dup_1_fix2〜fix8.py`。

## 1. 仕組み（1 枚で）

- フォーム表示（GET）のたびに **送信操作 ID（nonce）** を発行し hidden 項目 `n` で運ぶ。`<exp>.<乱数>.<HMAC-SHA256>`・署名鍵はプロセス起動時の乱数（env なし）・有効 **24 時間**（`NONCE_TTL_SEC`）。
- POST は「検証 → nonce の状態 → **原子的予約**（asyncio.Lock）→ token 照合 → 作成 → 結果保存」の順。同じ nonce は必ず 1 本だけが作成し、他は予約者の完了を待って同じ完了画面を返す（待ちきれなければ受付中ページ・作成 0）。
- nonce の状態は 2 つ＋なし: **有効**（署名正・24 時間以内）／**24 時間超**（署名正 → 固定ページ 410「入力から時間が経ったため…」・作成 0）／**なし・署名不正**（従来どおり新規）。
- 結果は in-memory の有界表 `_nonce_results`（上限 5000）に nonce をキーで 24 時間保持（値は record_id・受付番号・診断パターン・照合欄の SHA-256 のみ）。
- 書込結果の区別（fix7 BF-11）: **確定失敗**（書込前の失敗・kintone の明示的拒否）だけ予約を解放して取り直しを許す。**結果不明**（外部書込を開始した後の通信例外・5xx・キャンセル）は予約を解放せず「不明」として 24 時間保持し、初回も同じ nonce の再 POST も固定ページ（409「送信結果を確認できませんでした…再送信はせず、LINE の無料相談から」・作成 0）。
- **不変条件（fix8 BF-12〜14・Fable 裁定）**: 「外部書込（kintone の create/update）を開始した後は、成功の記録か unknown の保持のどちらかで必ず終わる。予約の解放は、書込を開始していないことが確実な場合に限る。」予約オブジェクト（`_NonceEntry`）の `write_started` を外部書込の呼出直前（同期）に立て、成功は書込が返った直後（通知・mark_used・写真トークン等の他の await より前）に同期で記録し、後始末は `_submit_with_nonce` の finally の `_nonce_settle` **1 か所**だけ（結果記録済み → そのまま／`write_started` かつ結果なし → unknown 保持／`write_started` でない → 解放。例外の種類・キャンセル・未分類例外を問わない）。確定失敗として解放してよいのは **kintone が明示的に拒否し書込が行われていないことが応答から確実な場合だけ**（`_definite_reject`: 4xx かつ本文が kintone のエラー JSON として解析できて code を持つ）。5xx・通信例外・timeout・応答解析失敗（JSON 不正・id 欠落）・code の無い 4xx・キャンセルはすべて unknown。plain（k なし）・linked（本人専用リンク）の両経路で同じ。nonce なしの送信も表に載せない局所の予約で同じ規則（不明ページ・WARNING）。
- linked 経路の不明（fix8 BF-14）: 作成成功後の `mark_used` 失敗でも結果は記録済みなので同じ nonce の再送は同じ完了画面（再作成なし）。unknown では plain と同じ不明ページ（従来の判定結果画面は返さない）・token 予約（SLL-02 の claim）も解放しない（`CLAIM_TTL_SEC`=120 秒で失効し、その後の再送は LINEユーザーID 検索で冪等）。
- 容量退避（fix7 BF-10）: 表が上限に達したら **結果確定済み**のエントリだけを最古から退避する（処理中・不明は退避しない。全部が処理中・不明なら新規予約を拒否し「ただいま混み合っています」ページ・作成 0）。退避した確定済みには **作成済みの印**（nonce の SHA-256 と期限のみ）を別集合 `_nonce_marks` に 24 時間残し、印のある nonce の再 POST は作成せず固定の「送信済みです」ページ（fix1 BF-03 と同じ）。

## 2. 固定ページ（相談者向け・入力値の反射なし）

| 場面 | HTTP | 見出し・本文 |
|---|---|---|
| 同じ nonce の再 POST（結果あり） | 200 | 1 回目と同じ完了画面（同じ受付番号／同じレコード） |
| 1 回目が処理中で待ちきれない | 200 | 送信を受け付けています… |
| 表が処理中・不明で満杯 | 200 | ただいま混み合っています… |
| 使用済み token で nonce 不一致／作成済みの印のみ | 200 | 送信済みです… |
| 24 時間超の nonce | 410 | 入力から時間が経ったため、送信できませんでした。…もう一度フォームを開いて入力してください。 |
| 書込結果が不明（初回・再 POST とも・plain／linked） | 409 | 送信結果を確認できませんでした。二重のお申込みを避けるため、再送信はせず、LINE の無料相談からご連絡ください。 |
| 確定失敗（k なし）・再採番上限・token 照合の取得不能 | 500 | エラーが発生しました… |
| 確定失敗（本人専用リンク）・token 予約中（busy）・mark_used 失敗 | 200 | 判定結果のみ（固定文言あり・受付番号・写真導線なし・従来どおり） |

## 3. 既知の制約（裁定済み・FORM-DUP-1-fix7 で明記・本票では直さない）

1. **プロセス再起動で鍵と記憶が消える。** 旧 nonce は署名不正＝「なし」＝新規扱い（再起動直後の再送は k なし経路なら新規作成・使用済み token なら送信済みページ）。
2. **単一 worker・メモリ内保持が前提。** `_nonce_results`・`_nonce_marks` はプロセス内の有界表（`_attempts`・`_upload_tokens` と同じ既知の制約）。複数 worker・複数インスタンスでは worker をまたぐ同一送信を判定できない。
3. **nonce を実際に入手した第三者は、有効期間中その送信の完了画面（受付番号・写真導線）を取得できる。** nonce は本人のブラウザの hidden 項目にしか無く、URL・cookie・ログには出さない。
4. **作成済みの印の集合が上限 200,000 件を超えた場合は最古から捨てる。** 捨てられた印の nonce で再 POST されると新規作成になり得る（確定済み 5000 件の退避後、さらに 200,000 件の退避が 24 時間以内に起きた場合のみ）。

## 4. 運用

- env・migration なし。merge＝デプロイで即時有効。
- ログは固定語彙＋件数・record_id のみ（nonce 値・回答本文は出さない）。業務 LINE 通知は既存の「要確認」1 箇所のみ（k なし経路の結果不明・確定失敗・再採番上限）。linked 経路の結果不明は ERROR 1 行 `shindan_link_write_unknown head=…`（通知なし）。
- 結果不明の保持は WARNING 1 行 `write result unknown (held, no retry) count=N`（`_nonce_settle`・保持中の不明件数のみ）。
- 結果不明（409）が出たら、通知の受付番号で App 21 を突合し、重複があれば kintone 画面で削除する（相談者には再送信を促さない）。
