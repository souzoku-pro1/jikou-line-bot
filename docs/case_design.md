# CASE 設計書 — 時効援用の解決事例を半自動で作る（コード変更なし・実装前の設計）

票: CASE-DESIGN-1。ブランチ docs/case-design-1（origin/main `8cf7be0` から・文書のみ）。
目的: 完了した時効援用案件から、jikou-law.jp に載せる **解決事例の記事** を半自動で作る。流れは
「完了を検知 → 事実を抽出（PII なし）→ Fable が大野の文体で下書き → 大野が承認 → WordPress に **下書き** 投稿 → 大野が公開」。
本書は大野が読んで確認するための文書です。UX-PENDING-1／K の設計と同じ粒度で、「どこで・何が起きて・大野には何が見えるか」を書きます。
裁定点 5 つは **2026-11-09 に大野が確定**（§7-3・裁定済み）。各節の両案併記は経緯として残し、採用した案を各節の冒頭に明記した。§10 の確認 4 点は回答待ちのまま（CASE-1 の設計には影響しない）。

## 0. 結論（1 枚で）

- **承認なしに公開されることはありません。** 仕組みの側で二重に止めます: (1) WordPress へは `status=draft`（下書き）でしか書けない（公開の API 権限を持たせない・コード上も `publish` を送る経路を持たない）(2) 下書き投稿そのものも大野の承認（§4）を通った記事だけ。公開ボタンを押すのは WordPress 管理画面で大野だけです。
- **個人情報は最初から読みません。** 抽出は「読んでよい列」の閉集合だけを kintone／DB から取り、氏名・住所・生年月日・契約番号・LINE userId・正確な金額と日付は列として選びません（§2）。記事に載るのは債権者の社名・債権の種類・請求額の帯・最終返済からの年数・届いた書類の種類・時効の成否・所要日数・相談者の属性（「40 代・会社員・関東」程度）までです。**不成立事例は載せません**（裁定 ③）。社名は事実のみを載せ、k-匿名を満たさない事例では伏せ、公開前の文言承認は大野が必ず行います（裁定 ⑤）。
- **下書きは K と同じ下書き専用モデルの経路**（env `JIKOU_DRAFT_MODEL`・既定 claude-fable-5-1・fail-closed）で作ります。文体は大野の既存の事例記事を手本にし、見出し構成は「相談のきっかけ・状況・対応・結果・弁護士のひとこと」で固定します（§3）。
- **完了の検知** は **App 21 の `status`=完了 を暫定の起点** にして先に動かし、**12 月に案件管理 S（JIKOU-STAGE-APP-1）が完成したら S の「完了」に切り替えます**（裁定 ①）。切替は「列の対応表 1 枚」の差し替えだけで済む構造にします（§1-2）。事例に要る不足列は App 21 には足さず S 側に持たせ、S が間に合わない間は専用の小表（閉集合の列のみ）に置きます（裁定 ②）。
- 費用は **1 件あたり約 35 円（Fable 5.1・下書き 1 回）**、月 10〜20 件で **約 350〜700 円**、再生成 1 回ずつを見込んでも約 1,400 円までです（§8）。
- 承認の場所は **統合一覧＋承認画面（案 (a)）** に確定（裁定 ④）。実装は 3 票に分けます: **CASE-1** 検知・抽出・下書き生成・承認画面、**CASE-2** WordPress 下書き投稿、**CASE-3** SEO 連携（親子記事への内部リンク）。裁定点は 5 つ（§7-3）。

### 1-2. 設計（裁定 ①: **B（App 21）暫定で開始 → 12 月の S 完成後に A へ切替**）

```
S: 案件の最後の債権者が 報告済／報告済(不成立) → bot が「完了にする」→ R-2（相談者への報告）を送る
   → 同じ処理の末尾で「事例候補」を 1 行作る（新表 case_article・state=detected・案件 ID と S のレコード ID だけ）
   → 以後は §2〜§4 の後追い処理（相談者への送信とは無関係・失敗しても S の処理に影響しない）
暫定（S 未配備のとき）: App 21 の status が 完了 になった webhook／日次の照合（既存の kintone 読取・1 日 1 回）で同じ 1 行を作る
```

- 検知は **1 案件 1 行**（PK＝案件 ID）。再配送・再実行で二重に作らない（INSERT … ON CONFLICT DO NOTHING・送信台帳と同じ流儀）。
- 「不受任」「決済完了」は起点にしない。「完了」以外から事例は作らない。
- 大野が手で起点を押す口も用意する（統合一覧の「事例にする」ボタン・§4-1）。S の完了を待たずに事例化したい案件や、S 以前に終わった案件はこれで拾う。
- **切替の構造（裁定 ①）**: 起点と抽出元の「どのアプリ・どの列・どの値が『完了』か」を **列の対応表 1 枚**（`hub/case_source_map.py` の定数 1 つ・暫定＝App 21 用と S 用の 2 枚を同じ形で持ち、env `CASE_SOURCE` の閉集合 {app21, stage} で選ぶ）に閉じ込める。検知・抽出・k-匿名・下書き・承認のコードは対応表の名前だけを見て、アプリ ID・列名・値を直接書かない。12 月の切替は `CASE_SOURCE=stage` と S の対応表の確認だけで、コードの他の箇所は変えない（受入条件に「対応表以外に列名が現れない」静的検査を入れる）。

## 2. 抽出する事実と匿名化

### 2-1. 原則: 「読んでよい列」の閉集合だけを選ぶ

抽出は kintone の `fields=` と DB の SELECT の列を **閉集合** で固定します（テストで pin）。氏名・住所・生年月日・電話・メール・契約番号・LINE userId・ハッシュ・正確な金額・正確な日付・自由記述（相談文・回答要旨・メモ）は **列として選びません**。「読んでから消す」ではなく「読まない」です（RV-10 と同じ考え方）。

| 読む列（閉集合） | 記事に渡す形 |
|---|---|
| 債権者名（S） | 社名そのまま（法人名は公開情報。表記ゆれは正規化表で統一） |
| 債権の種類（S・新列） | 閉集合の語（カード／消費者金融／銀行カードローン／携帯・通信／奨学金／家賃・その他） |
| 請求額の概数（S・新列・万円） | **帯**: 〜10 万／10〜30 万／30〜50 万／50〜100 万／100 万〜 |
| 最終返済日の **年**（App 21 `最終返済日_テキスト` から年 4 桁だけを正規表現で） | **帯**: 5 年以上／10 年以上／不明（5 年未満は事例にしない） |
| 届いた書類（S・新列・複数） | 閉集合の語（督促状／催告書／債権譲渡通知／支払督促／訴状／なし） |
| 時効の成否（S の状態） | 成立／不成立／一部成立（複数債権者）／回答なしのまま完了 |
| 受任日時・完了日時（App 21・S） | **帯**: 2 週間以内／1 か月以内／1〜2 か月／2 か月超（日付そのものは渡さない） |
| 年代・職業・地域（新列・閉集合） | そのまま（「40 代・会社員・関東」） |
| 債権者の数（S のレコード数） | 1 社／2 社／3 社以上 |

### 2-2. k-匿名の規則（案）

- **同一債権者で同月 1 件なら月をぼかす**: 記事には「2026 年 11 月」のような月は書かず、「2026 年秋」「最近の事例」とする。公開日と完了月が近いと特定につながるため、**公開は完了から 1 か月以上あける**（CASE-2 の投稿時に完了日時＋30 日より前なら下書きのまま保留＝大野に理由を表示）。
- **属性の組み合わせで 1 人に絞れないか**: 同じ債権者×同じ年代×同じ地域の事例が直近 6 か月に **2 件未満** なら、属性のうち地域を落とす（「40 代・会社員」）。それでも 1 件なら年代も落とす。判定は DB の `case_article` の既存行だけで行う（外部に問い合わせない）。
- **数字は帯だけ**: 金額・年数・日数は帯。債権者が 1 社で金額帯が端（〜10 万／100 万〜）のときは隣の帯と合わせて「数十万円」のように広げる。
- **自由記述は渡さない**: 相談文・大野の返信・回答要旨・メモは下書きの入力に入れない（文体の手本は §3 の既存記事から）。
- **社名（裁定 ⑤）**: 社名は事実（公的に確認できる商号）のみを載せる。上の k-匿名の規則で属性を落としても 1 件に絞れる場合＝k-匿名を満たさない事例は **社名を伏せる**（「大手カード会社」「貸金業者」の閉集合の語に置き換える）。社名を含む本文の公開前の文言承認は大野が必ず行う（§4-1 の承認画面＝承認なしに下書き投稿も公開もない）。
- **固有名詞の残留検査**: 下書きができたら `hub/pii_scan.residue_hits`（Q3a-fix1 の context_name を含む）に通し、1 件でも掛かれば承認画面に出さず「要修正」で止める（保存はするが承認ボタンを出さない）。

## 3. 下書き生成

### 3-1. 経路（K と同じ・env 共有）

```
case_article: state=detected
  → 抽出（§2）→ facts（閉集合の値だけの dict・PII なし）を同じ行に保存（state=extracted）
  → 下書き専用モデル（env JIKOU_DRAFT_MODEL・K §1-3 と同じ閉集合・既定 claude-fable-5-1・thinking 無効・FALLBACK なし・1 回・timeout 90 秒）
       system: 事例記事の規則ブロック（§3-2・sha pin）＋ 手本記事 2〜3 本（§3-3・匿名化済み・sha pin）
       user:   facts を箇条書きにしたもの（それ以外の文脈は渡さない）
       出力:   見出し 5 つの本文（Markdown・1,200〜1,800 字）＋ タイトル案 3 つ＋ FAQ 2 問（記事内の事実だけから）
  → 残留検査（§2-2）→ state=drafted（または needs_fix）→ 業務 LINE へ「事例の下書きができました（案件 No.・成否・件数のみ）」
```

- **送信関数を持たない**: 本モジュールは LINE へ送る関数・WordPress の publish を呼ぶ関数を一切持ちません（通知は既存の `send_business_notice` の固定文言＝承認台帳の対象外の運用通知）。
- モデル未設定（`JIKOU_DRAFT_MODEL` が off／未設定／閉集合外）なら **何も作らず detected のまま**（fail-closed・ログは固定理由）。K を有効化したときに自動で動き始めます。
- 再生成は承認画面の [もう一度作る]（1 件あたり 3 回まで・回数は行に記録）。

### 3-2. 見出し構成と文体規則（固定・sha pin）

| 見出し | 書くこと | 書かないこと |
|---|---|---|
| 相談のきっかけ | 届いた書類の種類・相談者の属性・債権者（社名）・債権の種類 | 日付・金額の正確な値・相談文の引用 |
| 状況 | 最終返済からの年数（帯）・請求額（帯）・時効が成立しうる根拠（5 年／10 年の説明は定型） | 契約番号・支店・担当者名 |
| 対応 | 時効援用通知の送付（内容証明）・信用情報の確認・相談者へ伝えた注意点（「支払わない・連絡しない」等の定型） | 通知文面の引用 |
| 結果 | 成否（成立／不成立）・債権者の反応の種類（回答なし／請求停止の連絡／争い）・所要（帯）・費用（事務所の公表料金の範囲で） | 回答文書の引用 |
| 弁護士のひとこと | 同じ状況の人への 1 つの助言（規則 v1.5 の「逃げない・言い切る・次の 1 問」を記事向けに） | 結果の保証・「必ず」「100%」 |

文体規則（大野の既存記事から抽出して確定・K §2 の v1.5 と同じ形で 8 項以内）: ですます調・一文 60 字以内・専門語には 1 行の言い換え・数字は帯・断定 NG 表現（K §2-2 を流用）・弁護士業務広告規程に触れる語（「必ず」「絶対」「日本一」「No.1」「成功率」）は禁止語として機械検査。

### 3-3. 手本

- 大野が書いた既存の事例記事を手本にします。**URL（または WordPress の記事 ID）を大野に 2〜3 本教えてもらう**（§10-①）。手本は本文を取り込み、pii_scan を通し、`docs/case_examples/`（匿名化済み・sha pin）に置く＝K-2 と同じ手順。
- 手本が無い場合は、§3-2 の構成だけで 1 本試作し、大野の赤入れを 1 往復してから手本にする。

### 3-4. 不成立事例の扱い（裁定 ③: **載せない**・両案は経緯として残す）

| 案 | 内容 | 利点 | 難点 |
|---|---|---|---|
| (ア) 不成立も記事にする | 「時効が成立しなかった事例」として、成立しなかった理由の種類（時効の中断・債務承認・年数不足）と、その後の対応（分割交渉・債務整理への切替）を書く | 誤導しない（成功例だけ並べない）・検索意図「時効 失敗」に答える | 相談者の不利益が読み取れる形になり得る → 属性を落とし、債権者名も伏せる（「大手カード会社」）条件つき |
| (イ) 不成立は記事にしない | 成立事例だけ。不成立は FAQ（「成立しないのはどんなとき」）に一般論として集約 | 特定リスクが低い・運用が単純 | 成功例のみの印象（広告規程の「誤導」に配慮して「成立しない場合もある」の注記を全記事に入れる） |

→ **裁定 ③（確定・2026-11-09・大野決定）**: **(イ) 載せない**。CASE-1 の検知は成立（時効確認済）の案件だけを事例候補にし、不成立・一部成立・回答なしは `case_article` を作らない（手動ボタンでも不成立は選べない）。全記事に「成立しない場合もある」の注記を入れる。**将来載せる場合は別裁定**（本書の (ア) は参考として残す）。PC-A の当初推奨（(ア) 条件つき）は採られなかった。

## 4. 承認（裁定 ④: **案 (a) 統合一覧＋承認画面を採用**・(b) は採らない）

### 4-1. 案 (a): 業務 LINE 通知 ＋ 統合一覧（/app/inbox）に「事例」札 ＋ 承認画面

```
drafted → 業務 LINE「【事例の下書き】案件 No.X（成立・カード 1 社）」＋ 署名付きリンク（既存 pending_link と同型・72h）
       → /app/inbox に「事例」札のカード（相談者名は出さない＝記事は匿名が前提。案件 No.・成否・債権者名・作成日時だけ）
       → /app/case/{id}: 左に facts（閉集合の値）・右に下書き（タイトル案 3・本文・FAQ）。本文は編集欄。
            ボタン: [この内容で承認する]（→ approved・履歴）／[もう一度作る]／[事例にしない]（→ rejected・理由は閉集合）
            承認時にもう一度 残留検査＋禁止語検査 → 掛かれば承認しない（固定文言・Q3a-fix2 BQ-06 と同じ流儀）
       → approved は CASE-2 の投稿ジョブが拾う（§5）
```

- 既存の画面部品（`_gate`・PRG 303・署名付きリンク・固定文言）をそのまま使う。送信関数なし。
- 利点: 承認の場所が 1 つ（返信・解除・事例が同じ一覧）。承認の履歴が DB に残る（RV-08）。残留検査を承認の直前にもう一度かけられる。
- 難点: 画面を 1 つ作る（CASE-1 の工数の 4 割）。

### 4-2. 案 (b): WordPress の下書きに直接入れ、管理画面で大野が確認して公開

```
drafted → すぐ WordPress に status=draft で投稿（§5）→ 業務 LINE「下書きを入れました（記事 ID）」
       → 大野が WordPress 管理画面で直して公開
```

- 利点: 画面を作らない（工数小）。大野は使い慣れた WordPress で編集できる。
- 難点: **承認前の文が WordPress に置かれる**（下書きでも、管理画面の権限を持つ人は読める・サイトの別の管理者がいれば見える）。残留検査に掛かった下書きも人の目に触れる前に止める場所が無い。承認の記録が WordPress 側だけになる。

### 4-3. 両案に共通の保証

- WordPress の資格情報は **下書き作成だけができる** アプリケーションパスワード（投稿者（Author）権限のユーザーに発行）。公開（`status=publish`）は権限上もできない。
- コードは `status` に `"draft"` 以外の値を持たない（定数・テストで pin）。
- 残留検査・禁止語検査に掛かった本文は、(a) では承認ボタンが出ない、(b) では投稿しない（needs_fix で止まり業務 LINE に固定文言）。

→ **裁定 ④（確定・2026-11-09・大野決定）**: **(a)**。承認前の文を外（WordPress）に置かない・履歴が残る・既存部品で作れる。**(b) WordPress 下書き直行は採らない**（§4-2 は経緯として残す・CASE-2 でも「承認済みだけを下書き投稿」であり、承認前の本文が WordPress に入る経路は作らない）。

## 5. 投稿（CASE-2・WordPress REST API）

### 5-1. 現状

- この repo に WordPress へ投稿するコードは **ありません**。docs/current-state-report.md（2026-07-03）に、jikou-law.jp の運用は別系統（`wp-auto-poster/`・`swell_converter.py`・`post_from_html.py`・`insert_common_faq.py` 等・リポジトリ外）とあり、**一部に資格情報の平文埋め込みがある** と注意書きがあります。PC-A の探索ではこれらのファイルの所在は見つかりませんでした（§10-②）。
- dispatch-bot の設計（docs/dispatch-bot/05・06）では「解決事例作成は第 3 弾・WordPress への公開は常に人」「外部送信の禁止リストに WordPress 公開」と定めてあります。本設計はこれと矛盾しません（下書きまで）。

### 5-2. 設計

```
approved → 投稿ジョブ（回収ジョブに相乗り・5 分ごと・1 件ずつ）
  → POST /wp-json/wp/v2/posts { title, content(ブロック HTML), status: "draft", categories: [事例], tags: [債権者名・債権の種類] }
  → 返ってきた記事 ID・編集 URL を case_article に保存（state=posted_draft）→ 業務 LINE「下書きを入れました（記事 ID）」
  → 公開は大野が WordPress で（公開日時の記録は CASE-3 で Search Console 連携と一緒に）
```

- 認証: WordPress の **アプリケーションパスワード**（大野が発行・ユーザーは投稿者権限）。env `CASE_WP_BASE_URL`・`CASE_WP_USER`・`CASE_WP_APP_PASSWORD` の 3 つ（値はチャット・文書・ログに出さない。`hub/redact` の対象に追加）。未設定なら投稿ジョブは何もしない（fail-closed）。
- 既存部品の流用: `swell_converter.py` 等が見つかれば、ブロック変換の関数だけを repo に移して（資格情報は持ち込まない）使う。見つからなければ本 repo に小さな変換器を書く（§5-3）。
- 失敗（HTTP エラー・timeout）は attempts+1 で pending のまま、次の周で再試行（3 回で止めて業務 LINE に固定文言）。二重投稿は「案件 ID → 記事 ID」の対応で防ぐ（投稿前に行をロック・送信台帳の流儀）。
