# 06. 復唱確認と安全装置

## 1. 原則（確定判断2の再掲・本書の前提）

- LINE上のOKは「**解釈確認＋起票承認**」のみ。対外効果を伴う処理の承認とは
  絶対にみなさない。対外実行は必ずkintone上の別途承認
- OKなしで起票しない。pending_command_id なしで実行しない

## 2. 復唱テンプレート（リスク比例・確定判断6）

全タスク一律のフル復唱は**流し読みを誘発するため禁止**。リスク区分（§4）で densité を変える。

### 2.1 低リスク用（簡潔版・2行程度）

```
鈴木一郎さん（No.45・受任）に送付案内を起票します。
OK / キャンセル（30分有効）
```

### 2.2 中・高リスク用（フルテンプレ）

```
【確認】以下で起票します
案件: No.45 鈴木一郎（時効援用・受任）
タスク: 職務上請求（App 30 起票）
宛先: 川口市（→川口市役所 市民課）
請求: 戸籍謄本2通・戸籍の附票1通（小為替は起票後に自動計算）
対象者: 鈴木花子（昭和25年3月15日生）
対外送信: なし（発送は kintone 承認後・投函は人）
リスク区分: 中
有効期限: 30分（このOKは起票の承認です。発送の承認は従来どおりkintoneで行います）
OK / キャンセル
```

- フルテンプレの必須項目: 案件・顧客名・ユニット・タスク・起票先・実行範囲・
  対外送信の有無・リスク区分・確認期限・**「OKは対外承認ではない」の注記**
- 完了・不受任案件への起票は先頭に「⚠ status=完了 の案件です」を付す（03 §4.3）

## 3. pending_command_id（確定判断7・8）

### 3.1 仕様

| 項目 | 仕様 |
|---|---|
| 発行 | 復唱送信時に一意ID（UUID）を発行し、解釈結果JSON・対象案件・起票先とともに保持 |
| 期限 | **30分**。期限後のOKは「期限切れです。もう一度指示してください」と返し**何もしない** |
| 単回実行 | OK受領で消込（起票成功・失敗を問わず無効化）。2回目のOKは「実行済みです」+ 起票済みレコードのリンク再掲 |
| 割込み無効化 | pending有効中に**別の指示・解釈の変わる発言**が来たら旧pendingを即無効化し、新しい解析を開始（「先ほどの確認は取り消しました」を付す）。「OK」「キャンセル」「番号選択」「聞き返しへの回答」だけは現pendingへの応答として扱う |
| 保持数 | ユーザーごとに**常に最大1件**（ホワイトリストは少人数のためグローバルでも実質1〜2件） |

### 3.2 第1弾の保持方式（インメモリ・明示仕様）

- 第1弾はプロセス内メモリ（dict）で保持する。これに伴い:
  **Railway再起動（デプロイ・env変更・クラッシュ）で pending は消える。
  再起動後にオーナーがOKを送っても期限切れ扱いとなり、再復唱（指示のやり直し）に
  なる。** つまり障害時は「勝手に実行される」方向ではなく
  「もう一度確認される」方向に倒れる（**安全側**）。これは許容仕様であり不具合ではない
- 既存前例: 顧客Botの conversation_histories も in-memory（README 既知の不具合 #4）。
  指示Botの pending は上記のとおり安全側に倒れるため、第1弾では許容する
- **永続化は第2弾（実行キュー導入）の課題として記録**: 確認待ちレコード方式
  （04 §3）への切り替えを D6 で判断する

### 3.3 二重実行防止（多層）

1. pending の単回消込（同一OKの2連打・LINE Webhookの再送に対応）
2. 起票処理自体の冪等化: pending_command_id を起票レコードに記録し、
   起票直前に「同じ pending_command_id のレコードが既に存在しないか」を検索
   （プロセス並行・再送の最終防衛線）
3. App 30 起票後の実行系は既存の claim パターン（実行済み no→yes）が守る

### 3.4 修正フロー（確定判断8）

- 第1弾の復唱への応答は **OK／キャンセルの二択**。キャンセル→「取り消しました。
  言い直してください」（言い直しは新規解析）
- 「宛先だけ蕨市に変えて」のような**部分修正の対話設計は第2弾以降の課題として記録**
  （解釈差分の適用・再復唱の設計が必要。第1弾では複雑化を避ける）

## 4. リスク区分の定義

| 区分 | 定義 | 復唱 | 例 |
|---|---|---|---|
| 低 | 内部完結の生成・起票のみ。誤っても kintone 上で削除すれば済み、対外・金銭影響なし | 簡潔版 | 送付案内起票・OCR投入・owner-manual更新候補 |
| 中 | 金銭計算・必須項目が多い・誤ると人の手戻りが大きい（ただし対外効果はまだない） | フル | 職務上請求（小為替）・Drive整理（移動実行）・財産目録 |
| 高 | 法的効果・対外発信・課金に**接続する**タスク（実行自体は下準備まで） | フル | 契約書生成・登記取得準備・協議書作成 |

- 区分はタスクレジストリの属性（05）。即答型はリスク区分の外（復唱なし）

## 5. 対外送信禁止リスト（横断ガード・正本）

指示Bot・実行キューのいかなる経路からも**直接実行しない**操作:

1. CloudSign 送信（契約書の先方送付）
2. FAX 送信
3. e内容証明の差出し
4. 登記取得の課金操作（登記情報提供サービス等）
5. 外部メール送信
6. **顧客LINEへの送信**（顧客Botの送信経路を指示Botから呼ばない）
7. Stripe の請求・決済リンク送付
8. WordPress 等への公開（解決事例の投稿）

- これらは必ず kintone 上の承認（App 30 承認待ち→承認済／App 29／将来の
  実行キュー承認欄）を経て、**既存の承認後経路**または**人の手**で実行する
- 実装上はタスクレジストリと独立した禁止関数リスト（アダプタ実行前の
  アサーション）として二重に守る（05 §4）

## 6. 高リスクタスクの実行範囲限定

- 高リスクタスクの自動実行は「**下準備・成果物生成・承認キュー起票まで**」。
  例: contract_draft は docx 生成・キュー添付で停止（05 §3.3・台帳2-5参照）、
  touki_prep は対象一覧化まで（課金取得は人）
- 範囲の定義はレジストリの `auto_scope` / `approval_scope` に置き、
  コード内に散在させない

## 7. 「今日の要対応一覧」（即答型・daily_digest）

### 7.1 集計対象（kintone上で照会可能なデータに限定）

| 項目 | ソース | 判定 |
|---|---|---|
| 顧客対応の承認待ち | App 29 `ステータス2=承認待ち` | 件数＋顧客名 |
| 発送の承認待ち | App 30 `発送ステータス=承認待ち` | 件数＋件名 |
| 返送期限超過 | App 30 `返送待ち` かつ 返送期限<今日（return_deadline_check と同判定・期限当日は含めない） | 件名＋超過日数＋追跡番号 |
| 発送エラー | App 30 `発送ステータス in (エラー, 要確認)` | 件名＋エラー詳細冒頭 |
| 未対応の問い合わせ | App 21 `status=問い合わせ/受付`（滞留） | 件数＋顧客名 |
| 実行キューのエラー・承認要 | EXEC_QUEUE `実行ステータス=エラー`・`完了かつ承認要否=要`【第2弾】 | 件数＋タスク名 |

- **CloudSign・Stripe の状態は kintone 上の status フィールド経由に限定**し、
  **外部API直叩きはしない**（照会の副作用ゼロ原則・応答速度・障害面の限定）
- **データソースが存在しない項目は集計対象に入れない**（例:「今日の入金予定」は
  kintone に予定データがないため出さない。無いものを推測で埋めない）

### 7.2 表示設計（スマホで読みやすく）

```
【要対応 7/4(土)】
🔴 返送期限超過 1件
・No.9 職務上請求（川口市・戸籍）超過3日 追跡1234-…
   https://<sub>.cybozu.com/k/30/show#record=9
🟡 発送の承認待ち 2件
・No.12 送付案内（鈴木一郎）…
🟡 顧客対応の承認待ち 1件
⚪ 未対応の問い合わせ 2件
（エラーなし）
```

- 表示順＝緊急度順に固定: ①返送期限超過・エラー（🔴）→②承認待ち2種（🟡）→
  ③滞留（⚪）。0件のセクションは「（〜なし）」の1行に畳む
- 各行に **kintoneレコードリンク**（`https://<KINTONE_SUBDOMAIN>.cybozu.com/k/<app>/show#record=<id>`）。
  スマホのkintoneアプリ/ブラウザで直接開ける
- 全体で4900字上限（notify系の既存上限と同じ）。超過時は各セクション先頭5件＋「他N件」

### 7.3 将来拡張: 毎朝自動配信

- hub/scheduler に `DAILY_DIGEST` ジョブ（例: 毎朝8:30 JST・既存2ジョブと同流儀）を
  登録し、同じ集計関数の出力を指示Botのpushでオーナーへ配信する
- 照会関数を「LINE応答」と「ジョブ配信」で共用できるよう、集計と送信を分離して
  実装する（第2弾 D8 の完了条件に含める。ジョブ有効化は env で切替）

## 8. テスト観点

- 復唱: リスク別テンプレ出し分け・注記文言の固定・完了案件警告
- pending: 期限切れOK→無視＋案内／二重OK→実行済み案内／割込み→旧pending無効化／
  番号選択・聞き返し回答は割込みにならない
- 二重起票防止: 同一 pending_command_id での2回目起票が検索ガードで止まる
- 禁止リスト: 全レジストリエントリとの突合・アダプタ前アサーションの発火
- digest: 各ソースのモックで表示順・畳み・リンク・上限切り詰め・外部API不使用
