# 05. タスクレジストリ：種別追加が「登録のみ」で済む構造

## 1. 設計思想

- チャネルアダプタ（channels/CHANNEL_REGISTRY）と同思想:
  **タスク種別の追加＝レジストリへの1エントリ登録＋実行アダプタ1クラス**で完結し、
  解析器・復唱・起票・キュー処理のコードには手を入れない
- 実装イメージ（`dispatch_bot/registry.py`）:

```python
@dataclass
class TaskSpec:
    task_type: str            # 一意キー（英小文字スネーク）
    display_name: str         # 表示名（復唱・キューのDROP_DOWN値）
    answer_only: bool         # True=即答型（復唱不要・副作用ゼロ）／False=起票型
    destination: str          # 起票先: "app30" | "exec_queue" | なし（即答型）
    run_at: str               # 実行場所: "railway" | "office_pc" | "human"
    risk: str                 # リスク区分: 低 | 中 | 高（06 §4）
    auto_scope: str           # 自動実行可能範囲（下記各表）
    approval_scope: str       # 人の承認が要る範囲（下記各表）
    required_fields: list[str]    # 必須入力項目（不足→聞き返し。03 §7）
    search_apps: list[str]        # 案件検索対象アプリ（env名。例 ["KINTONE_APP_ID"]）
    artifacts: str            # 成果物種類・保存先
    adapter: str              # 実行アダプタ（クラス名。即答型は回答関数名）
    on_failure: str           # 失敗時の扱い
```

- 解析プロンプトの「タスク種別一覧」はレジストリから自動生成（03 §5）。
  復唱テンプレのリスク区分・注記も同様にレジストリ駆動（06 §2）
- **対外送信禁止リスト（06 §5）はレジストリより優先される横断ガード**。
  レジストリの誤登録があっても禁止リスト該当操作は実行されない（二重防御）

## 2. 即答型タスク（照会のみ・副作用ゼロ・復唱不要。確定判断5）

| task_type | 表示名 | 参照先 | 自動でやること | 人の承認 |
|---|---|---|---|---|
| `daily_digest` | 今日の要対応一覧 | 06 §6 の集計対象（kintone照会のみ） | 集計・整形・返信 | 不要（照会のみ） |
| `approval_list` | 承認待ち一覧 | App 29 ステータス2=承認待ち／App 30 発送ステータス=承認待ち | 同上 | 不要 |
| `overdue_list` | 返送期限超過一覧 | App 30 返送待ち＋返送期限超過（return_deadline_check と同判定） | 同上 | 不要 |
| `error_list` | エラー一覧 | App 30 発送ステータス=エラー（第2弾〜: 実行キュー エラーも） | 同上 | 不要 |
| `case_status` | 案件ステータス照会 | 案件検索（03 §4）→ status・直近の発送管理レコード | 同上 | 不要 |

- 即答型は kintone の**読み取りのみ**（更新API・外部API・LINE以外への出力を持たない）。
  この不変条件をテストで固定する（更新系モックが呼ばれないこと）

## 3. 起票型タスク（確認必須）

### 3.1 発送・受領系 → App 30（二台帳制・第1弾/第1.5弾）

### 3.3 contract_draft と台帳2-5の接続点（確定判断12）

- 将来構想「委任契約書自動生成＋CloudSign送信の一気通貫」
  （automation-task-ledger.md §2-5。**本設計時点でリポジトリ未収載のため、
  指示文で提示された構想要旨を典拠として記載**）との衝突予防:
  - **第1弾（本設計）の実行範囲は `auto_scope=generate_draft_only`**。
    生成した契約書docxは実行キューの成果物に添付して止まり、
    CloudSign送信のコードパスを**持たない**
  - 台帳2-5を実装する際は、**本レジストリの contract_draft エントリの
    `approval_scope` を拡張**（「kintone承認後にCloudSign送信アダプタを実行」）する
    ことで吸収する。**新たな契約書生成タスクを別途設計しない**（二重設計の禁止）
  - その際も CloudSign 送信の承認は kintone 上（確定判断2）。LINE OK では送信されない
  - 関連: H8（CloudSign/Stripeのユニット一般化）が documentID の横断検索・
    締結フックの callback 化を先に整えるため、2-5実装は H8 の後が望ましい

## 4. レジストリのテスト観点

- 全エントリの属性完備（required_fields非空〔起票型〕・destination妥当・risk∈{低,中,高}）
- 即答型に destination が無いこと／起票型に必ず復唱が挟まること（結線テスト）
- 対外送信禁止リストとの突合: どのエントリの adapter も禁止操作を含まない
  （禁止リストはアダプタ実行前の横断ガードとしても実装。06 §5）
- 新タスク追加のリハーサル: ダミーエントリ追加だけで解析プロンプト一覧・
  復唱・起票が動くこと（「登録のみで済む」の受け入れ検査）
