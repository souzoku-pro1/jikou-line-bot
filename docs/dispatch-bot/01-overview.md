# 01. 全体像：LINE指示Bot（dispatch入口）＋実行キュー

- 作成日: 2026-07-04（設計のみ・実装はD系列タスクで行う）
- 目的: オーナー（弁護士）がスマホのLINEから自然言語で業務指示を出せる入口を作る
  - 例:「鈴木さんに送付案内を作って」「佐藤さんの職務上請求を川口市宛で」
    「田中さんの委任契約書を作っておいて」「今日の要対応一覧を出して」
- 名称について: 本設計の「指示Bot（dispatch-bot）」は **既存の `hub/dispatch.py`
  （App 30 のチャネルディスパッチャ）とは別物**。コード・設計書とも混同しないよう、
  実装モジュールは `dispatch_bot/` パッケージとし、hub/ 配下には置かない

## 1. 全体フロー

```
[オーナーのスマホ]
   専用LINE公式アカウント（指示Bot）に自然言語で入力
       ↓
[Railway] POST /webhook/dispatch-bot
   1. LINE署名検証（チャネル別secret）→ 即200 + BackgroundTasks（既存流儀）
   2. ホワイトリスト判定（userId）
      NG → 応答を返さず沈黙 + 管理者LINEに警報（02 §4）
   3. Claude解析（claude_gateway経由・tool useで構造化JSON。03）
       ├─ 即答型（照会のみ・副作用ゼロ）→ その場で回答して終了【復唱なし】
       ├─ OK/キャンセル → pending_command_id の消込（06）
       └─ 起票型 → 4へ
   4. kintone横断の案件検索（同姓同名・複数候補は選択肢提示。03 §4）
   5. 復唱確認（リスク比例の2種テンプレ + pending_command_id 発行。06）
       ↓ オーナーが「OK」
   6. 起票（二台帳制。§3）
       ├─ 発送・受領に関わるもの → App 30 発送管理 に「下書き」で起票
       │    → 以降は既存の状態機械（prepare→承認待ち→弁護士承認→…）に合流
       └─ それ以外の内部タスク → 実行キュー（EXEC_QUEUE・第2弾）に起票
       ↓
   7. 起票結果をLINEで返信（kintoneレコードリンク付き）
```

**LINEの「OK」は「解釈確認＋起票承認」のみ**（§4）。対外効果を伴う実行の承認は
すべて従来どおり kintone 上で行う。既存の承認原則（承認待ち→承認済への
サーバー遷移コードを書かない・SERVER_TRANSITIONS）は一切変更しない。

## 3. 二台帳制（確定判断3）

| 台帳 | 載るもの | 状態機械 |
|---|---|---|
| **App 30 発送管理**（既存・稼働中） | 発送・受領に関わるもの: 送付案内・宛名ラベル・職務上請求・e内容証明・FAX・返送待ち・スキャン受領消込。将来: メール・SMSチャネル | 既存の 下書き→承認待ち→承認済→発送処理中→…（architecture/01 §4。**変更しない**） |
| **実行キュー（EXEC_QUEUE）**（第2弾で新設） | 発送/受領に限らない内部タスク: 契約書生成・要対応一覧（履歴）・OCR投入・Drive整理・登記取得準備・財産目録作成・協議書作成・解決事例作成・Search Console分析・owner-manual更新候補 | 受付→確認待ち→実行待ち→処理中→完了／エラー（04 §2。App 30の思想を踏襲・発送固有フィールドは持たない） |

指示がどちらの台帳に載るかはタスクレジストリ（05）の `起票先` 属性で決まる。
振り分けロジックをコードに散らさない（チャネルアダプタと同思想）。

## 4. 「LINE OK」と「kintone承認」の意味の違い（確定判断2・最重要）

| | LINE上のOK | kintone上の承認 |
|---|---|---|
| 意味 | 「私の指示をそう解釈して**起票してよい**」 | 「この内容で**対外に出してよい**」 |
| 対象 | 解釈確認＋起票承認のみ | 対外効果を伴う実行（発送・送信・課金） |
| 実行者 | オーナー（スマホ・ホワイトリスト内userId） | 弁護士（kintone画面・従来どおり） |
| 実装 | pending_command_id の消込（06 §3） | App 30 承認待ち→承認済（人の操作のみ。SERVER_TRANSITIONS対象外）／実行キューの承認要否欄（04） |

**LINE上のOKを対外実行の承認とみなすことは絶対にない。** 以下は必ずkintone上の
別途承認を経る: CloudSign送信・FAX送信・内容証明差出・登記取得の課金操作・
外部メール送信・顧客LINE送信（対外送信禁止リストの正本は 06 §5）。

同様に区別すべき2つの「待ち」:

| 状態 | 意味 | 待っている人・場所 |
|---|---|---|
| **確認待ち** | LINE解釈確認待ち（復唱に対するOK待ち） | オーナー・LINE上（pending_command_id） |
| **承認待ち** | 弁護士承認待ち（対外実行の承認） | 弁護士・kintone上（App 30 / 実行キュー） |

## 5. 3つのLINEチャネルの分離（確定判断1）

| チャネル | 用途 | 方向 |
|---|---|---|
| 顧客Bot（時効援用公式アカウント・既存） | 顧客との対話（ヒアリング・トリアージ） | 双方向（顧客） |
| 弁護士向け通知（既存・push専用） | 【承認依頼】【返送期限超過】等の警報push（LINE_USER_ID / ATTORNEY_LINE_USER_ID 宛） | 片方向（システム→人） |
| **指示Bot（新設・専用公式アカウント）** | オーナーの業務指示・照会 | 双方向（オーナー） |

**通知チャネルに指示Botを同居させない理由（確定判断1の明記）**:
既存の通知チャネルには【承認依頼】等のpushが流れている。そこにOK応答文化を
持ち込むと、同じ「OK」という返信が「直前のpushへの応諾」なのか「指示の復唱への
承認」なのか**文脈で意味が変わるUI**になり、誤承認（読み違いによる意図しない起票）の
温床になる。指示Botを専用アカウントに分離することで、「このアカウントでのOKは
常に復唱への応答」という単一の意味に固定する。顧客Botとの分離は言うまでもなく
必須（顧客向けガード・FAQの混入防止。確定判断9）。

## 6. 既存資産の共用範囲（確定判断9）

| 資産 | 扱い | 理由 |
|---|---|---|
| `claude_gateway.py` | **共用する** | モデルフォールバック・クレジット残高警報を継承するため（全Claude呼び出しはここを経由する既存規約） |
| `chat_responder.py` | **一切共用しない** | 顧客向けガード（forbidden words・料金定型文）・FAQ・トリアージは指示Botに不要かつ混入は事故源 |
| `hub/notify.py` | 共用する（管理者警報・throttle） | 警報の一本化規約（architecture/03 §8） |
| `hub/kintone.py` | 共用する（案件検索・起票） | kintone I/O の一本化規約（T0-1） |
| `hub/webhook_auth.py` | 参考（署名検証はLINE方式のため独自。extract系は不使用） | LINEはHMAC-SHA256署名でトークンクエリ方式ではない |
| プロンプト・ガード・ログ・送信先 | **顧客Botと混ぜない**（指示Bot専用に新設） | 確定判断9 |

## 9. 絶対制約（本設計全体に適用）

- 顧客Botと指示Botを混ぜない。既存の顧客対応挙動を変えない
- LINE上のOKを対外実行承認とみなさない。OKなしで起票しない
- pending_command_id なしで実行しない。期限切れ・二重実行を許さない
- 実行キューから対外送信・課金操作・法的効果を発生させる操作を直接実行しない
- App 30 状態機械・承認原則（承認済への自動遷移コードを書かない）を壊さない
- App番号を新規に固定割当しない（実行キューは env `APP_EXEC_QUEUE` 参照）
- APIトークン・秘密情報をコードに直書きしない（すべて環境変数）
