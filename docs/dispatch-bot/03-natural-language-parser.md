# 03. 自然言語解析：意図分類・案件検索・構造化JSON

## 1. 方式（確定判断9）

- すべてのClaude呼び出しは **`claude_gateway.create_message_with_fallback` 経由**
  （モデルフォールバック・クレジット残高警報・両断時 ClaudeUnavailableError を継承）。
  `context="指示Bot解析"` を必ず渡す（フォールバック警報で呼び出し元が判別できるように）
- **chat_responder のプロンプト・ガード・カテゴリ判定は一切使わない**
- 出力は **tool use による構造化JSON**（§3のスキーマ）。テキスト応答からの
  JSON切り出し（コードフェンス除去等）はしない — スキーマ検証をAPI層に寄せる
- モデルは config.PRIMARY_MODEL（既存規約どおり config で一元管理・直書きしない）

## 2. 解析の入口分岐（確定判断5）

解析の第一段は「この入力は何か」の意図分類:

| intent | 例 | 後続 |
|---|---|---|
| `query`（即答型） | 「今日の要対応一覧」「鈴木さんの案件どうなってる」「承認待ち何件？」 | **復唱なしで即答**（照会のみ・副作用ゼロ。06 §6） |
| `task`（起票型） | 「鈴木さんに送付案内を作って」「佐藤さんの職務上請求を川口市宛で」 | 案件検索→復唱→pending発行（06） |
| `confirm` | 「OK」「はい」「お願いします」 | pending_command_id の消込・起票実行（06 §3） |
| `cancel` | 「キャンセル」「やめて」「違う」 | pendingを無効化し「取り消しました。言い直してください」 |
| `unknown` | 解釈不能・雑談 | 聞き返し（§7）。**推測で起票しない** |

- 即答型か起票型かの区分は**タスクレジストリ（05）の属性が正**。解析器は
  task_type を判定するだけで、区分の知識をプロンプトに重複記述しない
  （レジストリから動的に「即答型タスク一覧/起票型タスク一覧」を生成してプロンプトに埋め込む）

## 3. 構造化JSONスキーマ（tool use）

```json
{
  "name": "parse_instruction",
  "description": "オーナーの業務指示を構造化する。判断できない項目は null にし、勝手に補完しない",
  "input_schema": {
    "type": "object",
    "properties": {
      "intent": {"enum": ["query", "task", "confirm", "cancel", "unknown"]},
      "task_type": {"type": ["string", "null"],
                    "description": "タスクレジストリのtask_type。該当なしはnull"},
      "customer_name": {"type": ["string", "null"],
                        "description": "指示中の顧客名（敬称除去。例:「鈴木さん」→「鈴木」）"},
      "task_params": {"type": "object",
                      "description": "タスク種別ごとの追加項目（例: 職務上請求のmunicipality/request_items、照会の対象期間）"},
      "confidence": {"enum": ["high", "medium", "low"],
                     "description": "解釈全体の確信度"},
      "missing_fields": {"type": "array", "items": {"type": "string"},
                         "description": "起票に必須だが指示から読み取れなかった項目名"},
      "clarification": {"type": ["string", "null"],
                        "description": "confidenceがlow/unknown時にオーナーへ返す聞き返し文"}
    },
    "required": ["intent", "confidence"]
  }
}
```

- `task_params` の必須項目はタスクレジストリの `必須入力項目`（05）で定義し、
  不足分は `missing_fields` に列挙 → 聞き返し（§7）
- 例:「佐藤さんの職務上請求を川口市宛で」→
  `{"intent":"task","task_type":"shokumu_seikyu","customer_name":"佐藤",
    "task_params":{"municipality":"川口市"},"confidence":"medium",
    "missing_fields":["request_items（請求種別と通数）","target（対象者・本籍・生年月日）"]}`

## 4. 案件検索（kintone横断）

### 4.1 検索対象と順序

- 検索対象アプリはタスクレジストリの `案件検索対象アプリ` 属性で決まる
  （第1弾はすべて **App 21 案件（時効援用）**。相続放棄ユニット実装後は App 33 が加わる）
- クエリ: `顧客名 like "<customer_name>"`（既存 hub/kintone.search_records 使用）。
  ヒット0件なら空白除去・姓のみでの再検索を1回だけ行う

### 4.2 同姓同名・複数候補の扱い

- **1件ヒット**: その案件で復唱へ（復唱に顧客名・レコードNo・statusを含めるので、
  取り違えはOK前に人の目で気づける）
- **複数ヒット**: 自動選択しない。番号付き選択肢をLINEで提示:

```
「鈴木」の案件が3件あります。番号で選んでください:
1. 鈴木一郎（No.45・受任・時効援用）
2. 鈴木花子（No.52・手続き中・時効援用）
3. 鈴木一郎（No.12・完了・時効援用）
```

  - 返信「1」等を選択として受理（pendingに候補リストを保持。06 §3）。
    同姓同名（1と3）は status・レコードNoで区別する
- **0件ヒット**: 「該当する案件が見つかりません。氏名の表記を変えて言い直すか、
  kintoneのレコード番号（例: No.45）で指示してください」。レコードNo直指定
  （「No.45に送付案内」）も解析対象にする（task_paramsに record_id）
- **確信度**: 検索前の customer_name 抽出が low のときは検索せず聞き返し
  （誤検索→誤復唱の連鎖を入口で止める）

### 4.3 statusによる警告

- 完了・不受任の案件への起票指示は禁止しないが、復唱に
  「⚠ この案件は status=完了 です」を必ず含める（誤指示の気づきを促す）

## 5. 解析プロンプトの骨子（指示Bot専用・顧客Botと共有しない）

```
あなたは法律事務所の業務指示を構造化するパーサーです。
入力者は事務所のオーナー弁護士本人です（顧客ではありません）。

# やること
- 指示を parse_instruction ツールで構造化する。それ以外の出力はしない
- 判断できない項目は null / missing_fields に入れる。推測で補完しない
- 「OK」「はい」等の短い肯定は intent=confirm、「キャンセル」「違う」は intent=cancel

# タスク種別（レジストリから自動生成して埋め込む）
<即答型> daily_digest: 今日の要対応一覧 / case_status: 案件ステータス照会 / ...
<起票型> soufu_annai: 送付案内の作成 / shokumu_seikyu: 職務上請求 / ...

# 制約
- 顧客への返信文を作らない（この会話に顧客はいない）
- 法的判断・文面の創作をしない（あなたの仕事は構造化のみ）
- 同名タスクがなければ task_type=null・intent=unknown とし clarification を書く
```

- プロンプト全文は実装タスク（D2）で確定。**顧客Botの SYSTEM_PROMPT・
  forbidden words ガードとは無関係に新設**する（確定判断9）

## 6. 起票データへの変換（起票型のみ）

- OK受領後、タスクレジストリの `起票先` に従って変換:
  - App 30 起票: 発送ステータス=下書き・チャネル=<レジストリ定義>・ユニット種別・
    件名（自動組み立て:「<タスク表示名>（<顧客名>）」）・顧客名表示用・
    案件アプリID/案件レコードID・チャネル固有データ（task_params から組み立て）
  - チャネル固有データに指示Bot由来メタを付加:
    `"dispatch_bot": {"指示原文": "...", "userId": "U...", "解釈日時": "...", "pending_command_id": "..."}`
    （恒久ログ・監査用。02 §6）
  - 起票後は**既存の /hub/dispatch Webhook が下書きを検知して prepare を実行**する
    （指示Botは prepare を直接呼ばない。状態機械への干渉ゼロ）
- 実行キュー起票（第2弾）: 04 §1 のフィールドへ同様に変換

## 7. 聞き返し設計

- 聞き返しは**1メッセージに1論点**（スマホで答えやすく）:
  - confidence=low / intent=unknown → clarification をそのまま返す
  - missing_fields あり → 不足項目を箇条書きで質問
    （例: 職務上請求「請求する書類の種別と通数を教えてください（例: 戸籍謄本2通と附票1通）」）
  - 複数候補 → §4.2 の番号選択
- 聞き返しへの返答は**元の指示と結合して再解析**する（pendingに解析途中状態を保持。
  結合上限: 直近の指示1件分のやりとりのみ。古い文脈は使わない）
- 聞き返しが2往復続いても確定しない場合は「kintoneから直接起票してください」と
  案内して打ち切る（無限対話の防止）

> **D4 での変更（2026-07-04・職務上請求の多段聞き返し対応）**: 「最大2往復で打ち切り」は
> 必須項目が多いタスク（職務上請求: 種別通数・自治体・対象者・生年月日）に合わないため、
> 次のとおり改訂する:
> **「1論点1往復×必要項目数まで許容。ただし同一論点の再質問は1回まで
> （質問＋再質問で埋まらない論点は打ち切り）、全体でタスクごとの上限
> （TaskSpec.max_clarify・既定2・職務上請求8）往復を超えたら打ち切り→
> kintone直接起票を案内」**。送付案内など項目の少ないタスクは従来の2往復上限のまま
> （max_clarify=2 が既定のため挙動不変）

## 8. テスト観点

- 解析: 代表指示→期待JSON のゴールデンテスト（送付案内・職務上請求・照会・OK・
  キャンセル・雑談。test_triage_classification の一致率方式を踏襲）
- 案件検索: 1件/複数/0件/レコードNo直指定/完了案件警告（FakeClient）
- 聞き返し: missing_fields→質問文生成・回答結合再解析・2往復打ち切り
- ClaudeUnavailableError → 定型返信・起票ゼロ
