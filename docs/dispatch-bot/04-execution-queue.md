# 04. 実行キュー（EXEC_QUEUE）設計 — 第2弾実装

## 0. App番号の扱い（確定判断4・変更禁止）

- 本設計書では**固定のApp番号を割り当てない**。仮称「**実行キュー（EXEC_QUEUE）**」とする
- 実機のアプリ番号は**作成時に確定**する（kintoneの採番は作成順。既存設計書の
  App 33〜44 はすべて未作成の予定番号であり、先に他アプリが作られれば番号はずれる）
- コードは環境変数で参照する（`APP_SHIPPING`=30 と同流儀）:
  - `APP_EXEC_QUEUE` … アプリID
  - `TOKEN_EXEC_QUEUE` … APIトークン（閲覧・追加・編集。トークン直書き禁止）
- 作成直後に `EXPECTED_KINTONE_SCHEMA` へ登録し日次死活監視の対象にする（既存規約）

## 1. フィールド設計

フィールドコードは**日本語**。「ステータス」は kintone 予約語のため使わず、
既存流儀（「ステータス2」「発送ステータス」）に従い「**実行ステータス**」とする（確定判断11）。

| フィールドコード | 型 | 用途 |
|---|---|---|
| `タスク種別` | DROP_DOWN | タスクレジストリの task_type（表示名で選択・05） |
| `リスク区分` | DROP_DOWN | 低／中／高（06 §4。レジストリから転記） |
| `対象案件アプリID` | SINGLE_LINE_TEXT | 例: "21"（App 21 案件）。案件非依存タスクは空 |
| `対象案件レコードID` | SINGLE_LINE_TEXT | 対象案件のレコード番号 |
| `顧客名表示用` | SINGLE_LINE_TEXT | 一覧視認用（App 30 と同名の流儀） |
| `ユニット種別` | DROP_DOWN | 時効援用／相続放棄／相続一般／補助金／事務所内部 |
| `指示原文` | MULTI_LINE_TEXT | オーナーのLINE入力そのまま（監査・学習用） |

| `成果物` | FILE | 生成したdocx/PDF等の添付 |

## 2. 実行ステータス（状態機械）

最小構成（第2弾で実装するのはこの6状態のみ）:

```
受付 ──→ 確認待ち ──→ 実行待ち ──→ 処理中 ──→ 完了
              │                        │
              └─（期限切れ/キャンセル）  └──→ エラー ──（人が修正→実行待ちに戻す）
```

| 状態 | 意味 | 書き手 |
|---|---|---|
| 受付 | LINE指示を受理・解析済み（復唱送信前の瞬間状態） | サーバー |
| **確認待ち** | **LINE解釈確認待ち**（復唱へのOK待ち・pending有効） | サーバー |
| 実行待ち | OK受領済み・実行アダプタの処理待ち | サーバー |
| 処理中 | 実行アダプタが実行中（claim済み） | サーバー |
| 完了 | 成果物添付・完了日時記録済み | サーバー |
| エラー | 実行失敗（エラー詳細＋LINE警報。レコードは残す） | サーバー |

- **「確認待ち」（LINE解釈確認待ち）と「承認待ち」（弁護士承認待ち）は別概念**（01 §4）。
  第2弾の最小構成に「承認待ち」は**含めない**（承認が必要なタスクの成果物は
  「完了（承認要否=要）」で止め、対外実行はkintone上の既存承認フロー
  〔App 30 / App 29〕へ接続する）
- **拡張候補（記録のみ・第2弾では実装しない）**: `成果物あり` `承認待ち` `承認済` `却下`
  `要確認`。台帳2-5（契約書生成→CloudSign送信の一気通貫）を実装する際、
  実行キュー内で承認まで完結させる必要が生じたら `承認待ち`→`承認済`を追加する。
  その場合も **`承認済` へのサーバー遷移コードは書かない**（App 30 と同じ承認原則を踏襲）

### 状態機械の実装規約（App 30 の思想の踏襲）

- サーバー遷移は遷移表（frozenset）で強制し、表にない遷移は警報＋拒否
  （hub/approval.transition と同型の `exec_queue_transition()` を新設。
  hub/approval は App 30 専用のまま触らない）
- 二重Webhook・二重実行は `実行済み` の claim パターン（revision楽観ロック）で防ぐ
- kintone Webhook（レコード編集時）→ `/webhook/dispatch-bot` とは**別の受け口**
  `POST /exec-queue/dispatch?token=<EXEC_QUEUE_WEBHOOK_TOKEN>` を新設
  （/hub/dispatch と同型: token不一致は404で存在しないフリ）

## 3. pending永続化との関係（確定判断7）

- 第1弾の pending はインメモリ（06 §3）。**Railway再起動でpendingは消え、
  その後のOKは期限切れ扱い→再復唱になる（安全側に倒れる）**
- 第2弾で実行キューが出来た後は、`確認待ち` レコード自体が pending の永続化になる:
  起票を「受付」時点で行い、OK受領で「実行待ち」へ遷移する方式に切り替え可能。
  ただし**キャンセル・期限切れレコードがキューに堆積する**ため、切り替えの採否は
  第2弾実装時に判断する（D6の設計判断ポイントとして 07 に記録）

## 4. 一覧（kintone側GUI設定・推奨）

- 「実行待ち・処理中」（進行監視）／「エラー」（要対応）／「完了（承認要否=要）」
  （弁護士確認用）／「全件・作成日時降順」（監査）

## 5. テスト観点

- 遷移表: 全状態×全状態の許可/拒否網羅（test_hub_approval と同型）
- claim: 二重Webhookで実行アダプタが1回だけ動く・revision競合でスキップ
- 発送接続: 実行キュー発のApp 30起票が既存状態機械で正常に流れる（結線テスト）
- スキーマ監視: EXPECTED_KINTONE_SCHEMA 登録・フィールド改名の検知
