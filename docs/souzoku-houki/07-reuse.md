# 07. 時効援用との共通化：流用と新規の切り分け

## 1. そのまま流用（コード変更なし）

| モジュール | 用途 | 備考 |
|---|---|---|
| `claude_gateway`（フォールバック + 警報） | 全 Claude 呼び出し | モデル管理・スロットルも共通 |
| `hub/notify` `hub/scheduler` `hub/kintone` `hub/webhook_auth` `hub/docx_builder` `hub/address_label` | 全処理 | ハブ P0/P1 の成果物 |
| `hub/approval` `hub/dispatch` + M1 / M4 / M5 チャネル | 職務上請求・裁判所発送・書類受領 | `ユニット種別=相続放棄` の選択肢追加とマスタ行・テンプレ配置のみ |
| App 29 承認キュー + `/webhook/kintone/approval` | LINE 返信の承認 | アプリ・フロー完全共用 |
| `daily_healthcheck` | スキーマ・モデル監視 | `EXPECTED_KINTONE_SCHEMA` に App 33/34 を追加するだけ |
| App 28 チャットログ | 会話履歴 | `line_user_id` で自然に分離 |

## 2. 一般化が必要（既存コードのユニット対応 — ハブ側タスク）

現行コードには「時効援用専用」の焼き込みが3箇所ある。相続放棄を乗せる前に
UNIT_CONFIG 駆動へ一般化する（**動作不変のリファクタ + エントリ追加**の2段で行う）。

| # | 対象 | 現状の焼き込み | 一般化の内容 |
|---|---|---|---|
| G1 | `chat_responder` | App 21 の env・status 分類・システムプロンプト（時効の用語規則）・AUTO_SEND_CATEGORIES | ユニットごとに (案件アプリ, status 分類, プロンプト, カテゴリ集合) を UNIT_CONFIG から解決。**トリアージの仕組み（tool use・二重チェック・承認キュー保存）は共通のまま** |
| G2 | `cloudsign_webhook` | `KINTONE_APP_ID`（App 21）固定で documentID 検索・status="受任" | UNIT_CONFIG の全案件アプリを順に documentID 検索（documentID は全ユニットで一意）。ヒットしたアプリの status を更新。締結時フック（M2/M3 起票・相続放棄の書類チェック初期化）はユニット別に登録できる callback 化 |
| G3 | `main.py /webhook/stripe` | `"app": 21` ハードコード・`"ステータス"` フィールド（既知の不具合 #3） | Stripe 決済リンク作成時に metadata へ (ユニット種別, 案件レコードID) を埋め、Webhook はそれを見て該当案件を更新（新規レコード作成をやめる）。不具合 #3 もここで解消 |
| G4 | `main.py /webhook`（LINE 受信） | 単一 LINE チャネル（署名検証・トークンがグローバル） | §3 のマルチチャネル化 |

- 時効援用のヒアリング（SYSTEM_PROMPT + マーカー方式）は**変更しない**。
  相続放棄のヒアリングは新規エンジン（§4）で作り、実績が出てから時効援用の移行を検討する
  （動いているものを動いたまま、の原則）

## 3. LINE チャネルの分離（設計判断）

**相続放棄専用の LINE 公式アカウントを新設**し、`POST /webhook/souzoku-houki` で受ける
（パス名は 10-unit-02 §10.1〔参考資料〕から移植採用。ユニットのディレクトリ名・env 接頭辞と
揃えて自己説明的にするため）。

| 比較 | 同一アカウントに相乗り | 専用アカウント（採用） |
|---|---|---|
| ユニット判定 | 最初のメッセージで用件を聞く分岐が必要。誤判定リスク | 友だち追加 = ユニット確定。判定不要 |
| 広告・導線 | LP/広告からの計測が混ざる | 相続放棄 LP → 専用アカウントで分離 |
| プロフィール・挨拶 | 「時効援用専門窓口」の看板と衝突 | 相続放棄の顔で運用 |
| 実装 | ルーティング層の追加 | Webhook 1本と env 2個の追加（G4） |

- G4 の実装: `/webhook`（既存・時効援用）はそのまま**変更しない**（LINE Developers 側の
  再設定リスク回避）、`/webhook/souzoku-houki` を追加。将来 `/webhook/jikou` へ既存パスを
  改名したい場合はエイリアス追加方式（同一ハンドラに束ねる）で行う〔出典: 10-unit-02 §10.1〕。
  署名検証・reply/push は hub 共通化した LINE クライアントに channel 資格情報を渡す形にする
- 管理者・弁護士への警報/承認通知は**既存アカウント（時効援用側）に一本化**する
  （弁護士が2つのトークルームを見る運用にしない。`notify_admin_line` は現行のまま）

## 4. 相続放棄固有の新規部分

| # | 新規モジュール | 参照設計 |
|---|---|---|
| N1 | ヒアリングエンジン（tool use 段階収集・逐次 upsert・再開） | 02 §1-2 |

| N6 | 申述書・照会書回答・上申書・伸長申立書・完了報告書の生成 | 06 |

  ハブ設計 03 §2 のディレクトリ構成に `units/` を追加する位置づけ）

  予約（N4）は最初からユニット非依存に書き、質問定義・営業ルールを config/データで持つ
