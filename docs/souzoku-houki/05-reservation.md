# 05. 予約システム設計：Bot 内での枠提示方式

> **正本参照（2026-07-03）**: 予約枠アプリ（App 34）は **v1 不採用**
> （[正本 §0.1・§3.4](../architecture/10-unit-02-souzoku-houki.md)。電話日程はLINE会話で調整）。
> 本ファイルは将来拡張（月間電話件数の目安超過時に再検討）の設計として存置。


来所面談（A）・電話/Zoom（B）の日程を LINE 会話の中で確定させる。
外部予約サービス連携と kintone 自前管理を比較し、**kintone 自前管理を推奨**する。

## 1. 比較

| 観点 | 外部予約サービス（TimeRex / Calendly / STORES 予約等） | kintone 自前管理（★App 34） |
|---|---|---|
| LINE 内完結の UX | △ 外部 URL へ遷移（LINE を離れる）。離脱ポイントが増える | ○ クイックリプライで会話内完結 |
| 案件データとの一元性 | △ 予約データが外部に分離。案件紐付けは Webhook 連携の作り込みが必要 | ○ 案件参照フィールドで App 33 と直結。承認・警報も既存基盤 |
| 障害点・死活監視 | ✗ 外部 SaaS が増える＝監視対象と障害モードが増える。API 仕様変更リスク | ○ 既存の kintone + Railway のみ。daily_healthcheck に載る |
| ダブルブッキング防止 | ○ サービス側で保証 | ○ revision 楽観ロックで実装（ハブ 03 §3 の既存機構） |
| Google カレンダー連携 | ○ 標準機能 | △ 将来拡張（§5）。v1 は kintone 一覧 + LINE 通知で代替 |
| コスト | 月額課金（連携可能プランは概ね有料） | 追加コストなし |
| 実装工数 | 連携 Webhook + アカウント運用 | 枠アプリ + Bot フロー（1〜2 タスク） |
| 3原則との整合 | △ 枠メンテ・アカウント管理という人の作業が増える | ○ 枠自動生成で平常時人間ゼロ |

**推奨: kintone 自前管理。** 決め手は①予約が案件（App 33）・警報・死活監視と同じ基盤に
乗ること、②LINE 会話から離脱させないこと、③週数件規模の枠管理に外部 SaaS は過剰で、
障害点と運用アカウントだけが増えること。
カレンダー同期が必須になった時点で §5 の拡張で対応する（その時も予約の真実は App 34 に置く）。

## 2. 枠の自動生成（平常時人間ゼロ）

- 週次ジョブ `reservation_slot_generate`（hub/scheduler・毎週月曜 6:00）:
  config の営業ルールから **2〜4 週間先の枠**を自動生成する

```python
RESERVATION_RULES = {
    "枠長_分": 60,
    "提供枠": [  # 曜日・時間帯・種別
        {"weekday": "火", "times": ["10:00", "14:00", "16:00"], "type": "共用"},
        {"weekday": "木", "times": ["10:00", "14:00", "16:00"], "type": "共用"},
        {"weekday": "土", "times": ["10:00", "11:00"], "type": "来所"},
    ],
    "生成先週数": 4, "祝日除外": True,
}
```

- 弁護士の操作は「塞ぎたい枠を kintone で `弁護士ブロック` にする」だけ
- 生成は冪等（同一日時の枠が既にあればスキップ）。祝日判定は内包カレンダー
  （祝日 CSV 同梱・年次更新は依存ライブラリでなくデータ更新）

## 3. Bot 予約フロー

```
チャネル A/B 確定（02 §4）
 → Railway: App 34 から 枠状態=空き かつ 種別が合致する直近枠を最大10件取得
 → LINE クイックリプライで提示（「7/8(火) 10:00」…「他の日程を見る」「後で決める」）
 → 依頼者が選択
 → claim: revision 指定で 空き→仮押さえ（競合したら「その枠は埋まりました」+ 再提示）
 → 仮押さえ成功: 案件参照を記入・仮押さえ期限=+24h
 → 契約手続き（CloudSign 締結）まで進んだら 仮押さえ→確定:
     ├─ B(Zoom/電話): 実施方法メモ に OFFICE_INFO.Zoom固定URL / 「こちらからお電話します」
     ├─ A(来所):      実施方法メモ に OFFICE_INFO.アクセス案内
     └─ 弁護士へ LINE「【予約確定】7/8 10:00 来所 山田太郎（案件No.12）」
 → 「後で決める」: status はそのまま、日次ジョブが 3 日後にリマインド
```

- **仮押さえの自動解放**: 日次ジョブが `仮押さえ期限` 超過の枠を `空き` に戻し、
  依頼者に「仮押さえが期限切れになりました。改めてご希望日をお選びください」を送信
- 受任判断待ち（複雑性フラグ有り）の案件は、面談実施が受任判断の前提になるため
  **契約前でも予約を確定**する（この場合の確定トリガーは弁護士の「受任判断待ち」承知）

## 4. リマインド・変更・キャンセル（すべて自動）

| 処理 | 実装 |
|---|---|
| 前日リマインド | 日次ジョブ: 翌日の `確定` 枠 → 依頼者と弁護士の双方に LINE |
| 変更 | Bot トリアージの「予約の変更・確認」カテゴリ（02 §5・自動送信可）。現予約を `取消` → 枠再提示フローを再実行 |
| キャンセル | 同上。案件 status は変えず、弁護士に通知のみ |
| 無断キャンセル（枠時刻超過・面談記録なし） | 日次ジョブが検知 → 弁護士に通知 + 依頼者に再調整の案内 |

## 5. 将来拡張（設計変更なしで足せるもの）

- **Google カレンダー同期**: `確定` / `取消` 遷移時に Calendar API へ push する
  ジョブを1本追加（App 34 が真実、カレンダーは投影）
- **Zoom ミーティング自動発行**: 固定 URL 運用から Zoom API（meeting create）へ差し替え。
  `実施方法メモ` の書き込み関数を置き換えるだけ
- **他ユニットの相乗り**: App 34 は案件参照3点方式なので、相続一般・補助金ユニットの
  面談予約もアプリ追加なしで使える
