# 09. 申述パッケージ（家裁提出書類一式）

相続放棄申述の家裁郵送提出を「1つの申述パッケージ」として定義し、
組み立て（生成・充足チェック）→ 承認 → 発送 → 返送消込までを
発送/受領ハブ（M4 送付案内 + App 30）の仕組みで実装する。

## 1. 提出書類一式（8点セット）の定義

| # | 書類 | 入手区分 | ソース / 生成方法 | 標準型 | 3ヶ月超過型 |
|---|---|---|---|---|---|
| ① | 相続放棄申述書 | **生成** | 06 §1（App 33 差込・前提条件ガードあり） | ○ | ○ |
| ② | 手続委任状 原本 | **受領済み** | 依頼者から郵送受領（M5・書類チェック `委任状=受領`） | ○ | ○ |
| ③ | 代理人目録 | **生成** | 06 §6（新設テンプレ）。弁護士・事務所情報を config（OFFICE_INFO・弁護士登録情報）から自動差込 | ○ | ○ |
| ④ | 収入印紙 800円 | **物品** | 申述人1人あたり800円。同封チェックリストに金額明示（§4） | ○ | ○ |
| ⑤ | 予納郵券 | **物品** | 金額・切手組み合わせは**家裁ごとに異なる** → 家裁マスタ（§2）から明細印字 | ○ | ○ |
| ⑥ | 戸籍謄本一式 + 被相続人の住民票除票（または戸籍の附票） | **受領済み** | M1 職務上請求 / 依頼者提出（書類チェックの戸籍系が全行 `受領`） | ○ | ○ |
| ⑦ | 事情説明書（上申書） | **生成** | 06 §3。**3ヶ月超過型のみ** | — | ○ |
| ⑧ | 疎明資料（債権者からの通知等） | **受領済み・選択** | M5 受領済み書類から**同封対象を選択**（§3.2） | 案件による | ○（起算点の裏付けとして原則同封） |

- 標準型 / 超過型の判定: App 33 `案件類型` フィールド（死亡日ベースの機械判定・02 §3a）。
  超過型は ⑦ が必須・⑧ が原則必須になる（チェックリスト生成が自動で分岐。
  生成書類側の類型分岐は 06 §7 の表と1対1対応）
- 同時申述（兄弟等・案件レコード別）は**パッケージも案件ごとに1つ**。
  印紙は各パッケージに800円ずつ（04 §1.5 の「1申述人=1案件」原則と整合）

## 2. ★App 35 家裁マスタ

App 31 市区町村マスタ（ハブ 02 §3）と同方式の参照マスタ。
1レコード = 1家裁（本庁・支部・出張所ごと）。

### 2.1 フィールド定義

| フィールドコード | 型 | 用途 |
|---|---|---|
| `家裁名称` | SINGLE_LINE_TEXT | 例: `さいたま家庭裁判所`（支部・出張所名まで含めた正式表記） |
| `郵便番号` / `郵送提出先住所` | SINGLE_LINE_TEXT | 宛名ラベル・送付書の宛先 |
| `電話番号` | SINGLE_LINE_TEXT | 照会用 |
| `管轄市区町村` | MULTI_LINE_TEXT | 管轄区域の市区町村名を改行区切りで列挙（§2.3 の管轄確定に使用） |
| `郵券合計額` | NUMBER | 円 |
| `郵券組み合わせ` | SUBTABLE | 列: `額面`(NUMBER) / `枚数`(NUMBER)。チェックリストに明細印字 |
| `郵券確認日` | DATE | 情報の鮮度（家裁の運用変更検知用。1年超過は承認画面に注意表示） |
| `備考` | MULTI_LINE_TEXT | 提出方法の家裁固有ルール等 |
| `有効` | RADIO_BUTTON | yes / no |

- 環境変数: `APP_COURT_MASTER` / `TOKEN_COURT_MASTER`。作成後 `EXPECTED_KINTONE_SCHEMA` 登録（既定規約）

### 2.2 「使ったところから埋める」運用と未登録時の挙動

- 初期データ: **管轄区域内の家裁（さいたま家裁 本庁・川越/熊谷/越谷支部 等）のみ**
  名称・住所を投入。郵券情報は初回利用時に電話確認して実測登録
- **未登録・郵券未登録の家裁宛に申述パッケージが起票された場合**:
  - `エラー` 遷移**にはしない**（案件の落ち度ではなく、初回利用の正常な状態のため）
  - 発送ステータスを `下書き` のまま維持し、弁護士 LINE に
    **【郵券情報の登録依頼】**「App 35『○○家裁』の郵券合計額・組み合わせを登録して
    ください（家裁に電話確認: TEL）。登録後は自動で処理が再開します」を通知
  - 日次ジョブ `shinjutsu_pending_check` が「郵券待ちで止まっている下書き」を毎朝再検査し、
    登録済みになっていれば **prepare を自動再実行**（登録後の人の操作は不要 = 平常時人間ゼロ）
  - 7日以上未登録のまま → 再警報（熟慮期間の残日数を併記して優先度を伝える）

### 2.3 管轄家裁の確定

```
被相続人の住民票除票（または戸籍の附票）を M5 受領
 → OCR 抽出の「最後の住所」の市区町村を正規化（M5 既存の正規化ヘルパ）
 → App 35 の 管轄市区町村 でマッチ → 家裁マスタレコードを特定
 → App 33 に記録: 管轄裁判所（名称）+ 家裁マスタレコードID
 → マッチしない/複数マッチ → 管轄裁判所 は config 初期値（さいたま家裁）を仮置きし、
   弁護士 LINE に確認依頼（誤った家裁への提出は却下・時間損失に直結するため人が確定）
```

- ヒアリング時点の `被相続人最後の住所`（申告値）でも仮判定して表示するが、
  **確定は除票受領後**（公的書類ベース）。申述書 `{{管轄裁判所}}` は確定値のみ使用

## 3. 申述パッケージの組み立てフロー

### 3.1 前提条件ゲート（7条件・全て満たすまで起票しない）

**申述書生成（06 §1）と同一のガード関数を使う**（units/houki に1箇所だけ実装。
条件の二重定義による不整合を作らない）。

| # | 条件 | 判定ソース |
|---|---|---|
| 1 | 受任判断 = 受任可 / status ≥ 受任 | App 33 |
| 2 | 起算点確定済 = yes | App 33（03 §2） |
| 3 | 委任状 = 受領（紙原本・01 [4a] の郵送往復完了） | 書類チェック SUBTABLE |
| 4 | 本人確認ステータス = 確認済（弁護士チェック） | App 33（01 [4a]） |
| 5 | 戸籍セット充足（戸籍系・除票の全行が 受領 or 不要、かつ `連続戸籍充足=yes`・10 §4） | 書類チェック SUBTABLE + App 33 |
| 6 | 管轄家裁の確定（§2.3。家裁マスタレコードID あり） | App 33 |
| 7 | 超過型のみ: 事情説明書の弁護士承認済み | 06 §3 の専用承認 |

- 条件充足の検査は日次ジョブ + 書類チェック更新時のフックで自動実行。
  **全条件が揃った時点で自動起票**（人がボタンを押す必要なし）

### 3.2 疎明資料の同封選択

- 書類チェック SUBTABLE に列 `同封対象`（チェック）を追加（04 §1.5 に反映）
- M5 が受領・分類した書類（債権者通知・督促状等）は書類チェックに行が増えていくので、
  弁護士が **同封したい行にチェックを入れるだけ**（超過型では受領時に
  doc_type=業者からの通知 の行へ自動でチェックを入れ、外すのは弁護士判断）

### 3.3 起票 → 発送 → 消込（M4 送付案内の仕組みをそのまま使用）

```
前提条件ゲート通過（自動検知）
 → App 30 に自動起票: チャネル=送付案内 / ユニット種別=相続放棄 /
   件名=「相続放棄申述パッケージ（山田太郎・さいたま家裁）」/
   宛先=家裁マスタの郵送提出先 / チャネル固有データ={"package":"shinjutsu", "type":"標準|超過", ...}
 → prepare が成果物を生成・添付:
   a. 家裁宛送付書 docx（送付案内テンプレの家裁宛版・書類目録=8点セットの該当分）
   b. 同封チェックリスト PDF: ①〜⑧ の充足状況、**収入印紙 800円**、
      **予納郵券の額面×枚数の明細と合計額**（App 35 から差込）、疎明資料の選択一覧
   c. 宛名ラベル（家裁宛 + 返送用事務所宛）
 → 承認待ち + 弁護士 LINE（✅ 承認 = 対外発信の承認。超過型は上申書承認済みが前提）
 → 承認済 → 発送処理中: 👤 事務員の作業は「印刷・印紙/郵券の同封・投函・追跡番号入力」のみ
 → 発送済 → 返送待ち（返送期限 = 家裁からの応答待ち。既定30日・config）
 → M5 受領で消込:
   ├─ 照会書 → App 33 status=照会書対応（H11/H14 のフローへ）※App 30 は返送待ちのまま
   └─ 受理通知 → App 30 完了 + App 33 status=受理 + 事件番号転記
 → 期限超過（30日応答なし）→ 弁護士警報（家裁へ電話確認を促す）
```

- M4 チャネル・App 30 状態機械・承認・冪等はハブ実装を**コード変更なしで流用**。
  相続放棄固有なのは「前提条件ゲート」「チェックリスト内容」「消込時の App 33 連動」のみ
  （units/houki 側に実装。ハブ拡張ポイントの検証項目）

## 4. 収入印紙・予納郵券の扱い（在庫管理はしない）

- **在庫管理システムは作らない**（過剰設計の回避）。システムの責務は
  「このパッケージに何がいくら必要か」をチェックリストに明示するところまで
- App 30 に `必要印紙額` / `必要郵券額`（NUMBER）を追加し、prepare が記入する
- **kintone 一覧「今週の申述予定」**（App 30・GUI 設定）:
  - 絞り込み: チャネル=送付案内 かつ チャネル固有データに依らず件名に「申述パッケージ」
    を含む かつ 発送ステータス in (下書き, 承認待ち, 承認済)
  - 表示列: 件名 / 発送ステータス / 必要印紙額 / 必要郵券額 / 返送期限
  - 合計: kintone の集計（グラフ）機能で 必要印紙額・必要郵券額 の合計を表示
  - 運用: 週次の郵便局購入前にこの一覧を見るだけ（通知ジョブは作らない。
    見る動機が「発送承認をした」という既存動線に含まれるため）

## 5. 異常系一覧

| 事象 | 検知 | 自動対応 | 警報 |
|---|---|---|---|
| 家裁の郵券情報未登録 | prepare | `下書き` 維持・登録後に自動再開（§2.2） | ○【郵券情報の登録依頼】 |
| 管轄マッチ不能・複数マッチ | 除票受領時 | config 初期値を仮置き | ○（弁護士が確定） |
| 前提条件が残日数14日（社内締切日基準）時点で未充足 | 日次ジョブ | なし | ○（03 §5 の伸長検討提案と統合） |
| 家裁30日応答なし | 日次ジョブ | 返送待ち維持 | ○（電話確認提案） |
| 郵券確認日が1年超 | 承認画面表示 | 承認時に注意書き | ×（承認者が判断） |

## 6. テスト観点（実装タスク完了条件用）

- **8点セットのチェックリスト生成**: 標準型（⑦⑧なし）/ 超過型（⑦必須・⑧自動チェック）の
  分岐、印紙800円×申述人、郵券明細（額面×枚数・合計）の差込
- 前提条件ゲート: 7条件の各欠落パターンで起票されないこと・全充足で自動起票・
  申述書生成（06 §1）と同一関数を共有していること
- 郵券未登録: 下書き維持 + 登録依頼警報 + 登録後の自動再開（日次ジョブ）
- 管轄確定: 除票住所→家裁マッチ・マッチ不能時の仮置きと警報
- 消込分岐: 照会書（返送待ち維持）と受理通知（完了 + 事件番号転記）の違い
