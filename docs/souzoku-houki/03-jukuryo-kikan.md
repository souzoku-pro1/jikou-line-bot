# 03. 熟慮期間管理

相続放棄ユニットの生命線。「自己のために相続の開始があったことを知った時から3ヶ月」
（民法915条1項）の期限を、申告値/確定値の分離・安全側計算・段階警報で管理する。

## 1. 設計原則

1. **申告値と確定値の分離** — Bot が聞いた日付は法的判断を経ていない。
   `_申告` フィールドと `_確定` フィールドを分け、確定は弁護士のみが行う
2. **確定前は安全側で計算** — 起算点候補のうち**最も早い日付**（通常は死亡日）で
   仮の満了日を計算して警報する。実際の起算点（知った日）が後なら余裕が増えるだけで、
   逆方向の事故（本当は期限が近いのに警報しない）が起きない
3. **満了日はシステムの「目安」であり法的確定ではない** — kintone・警報文言に
   「暫定」「弁護士確認前」を明示する

## 2. フィールド設計（App 33・04 参照）

| フィールド | 書き手 | 意味 |
|---|---|---|
| `死亡日_申告` / `死亡を知った日_申告` / `相続人と知った日_申告` | Bot（ヒアリング） | 依頼者の申告。曖昧なら「YYYY-MM頃」文字列も許容（テキスト併記欄あり） |
| `起算日_確定` | **弁護士のみ** | 弁護士が記録・面談で確定した起算日（DATE） |
| `起算点確定済` | 弁護士のみ | yes/no。yes になるまで安全側計算を続ける |
| `起算点メモ` | 弁護士 | 起算点判断の根拠（3ヶ月超過案件では上申書の素材になる・06 §3） |
| `熟慮期間満了日_暫定` | Railway（日次ジョブ） | §3 の計算結果。人は編集しない |
| `残日数` | Railway（日次ジョブ） | 満了日_暫定 − 今日。マイナス=超過 |
| `期間伸長申立` | 弁護士 | 不要 / 検討中 / 申立済 / 認容（伸長後期限は `伸長後満了日` に記録） |
| `通知済み閾値` | Railway | CHECK_BOX {30日前, 14日前, 7日前, 超過}。警報の冪等キー |

## 3. 満了日の計算ロジック（実装仕様）

```
起算点 = 起算点確定済 == yes ? 起算日_確定
        : min(死亡日_申告, 死亡を知った日_申告, 相続人と知った日_申告 のうち値があるもの)
        # 申告が「YYYY-MM頃」しかない場合はその月の1日として扱う（安全側=早い方）

満了日 = 起算点の翌日を起算日とし（初日不算入・民法140条）、
        3ヶ月後の起算日応当日の前日（暦計算・民法143条2項）
        応当日が存在しない場合（例: 11/30 起算 → 2月）はその月の末日
伸長後: 期間伸長申立=認容 なら 満了日 = 伸長後満了日 で上書き
```

- 境界のテストケースを実装タスクの完了条件に含める:
  月末起算・うるう年2月・応当日なし・「頃」入力の月初丸め
- **計算式は実装前に弁護士レビュー必須**（H5 タスクの完了条件。期間計算の解釈は
  最終的に弁護士が確認する — 法的判断のシステム焼き込みに当たるため）

## 4. 閾値別アラート（日次ジョブ `jukuryo_deadline_check`）

`hub/scheduler.register_daily`（毎日 7:30 JST・死活監視の直後）に登録。
対象: App 33 の status が {完了, 不受任, 辞任, 受理} **以外**の全レコード。

| 条件 | 警報（弁護士 LINE） | 併せて行う自動処理 |
|---|---|---|
| 残日数 ≤ 30 かつ 30日前未通知 | 【熟慮期間30日前】案件No・顧客名・満了日(暫定/確定の別)・現在status | `通知済み閾値` に 30日前 を追加 |
| 残日数 ≤ 14 かつ 14日前未通知 | 【熟慮期間14日前】+ 現在の書類チェックリスト残 | 同上 + 期間伸長要否検知（§5） |
| 残日数 ≤ 7 かつ 7日前未通知 | 【熟慮期間7日前・要対応】 | 同上。以後**毎日**通知（7日前チェックを外して再通知） |
| 残日数 < 0 かつ 超過未通知 | 【熟慮期間超過・上申書要】 | 複雑性フラグ「死亡3ヶ月超過」を立て、上申書下書き生成をキュー（06 §3） |
| 起算点確定済=no かつ 残日数 ≤ 30 | 【起算点未確定のまま残30日】 | 弁護士に確定作業を促す（毎回の閾値警報に付記） |

- 冪等性: `通知済み閾値` CHECK_BOX で同一閾値の再通知を防ぐ（日次ジョブが2回走っても安全）。
  ただし残7日以降は意図的に毎日通知する
- **即時警報（ジョブを待たない）**: Bot ヒアリング中に日付が upsert された時点で
  残日数を計算し、30日未満なら即時に弁護士警報（02 §4）。夜間の相談が翌朝の
  ジョブまで放置されるのを防ぐ

## 5. 期間伸長申立てが必要なケースの検知

家庭裁判所への熟慮期間伸長の申立て（民法915条1項ただし書）を「機械が提案し、
人が判断する」形にする。以下のいずれかで弁護士警報に**伸長検討の提案**を付記:

| 検知条件 | 根拠 |
|---|---|
| 残日数 ≤ 14 かつ 書類チェックリスト（04 §2）に未収集項目あり | 財産調査が満了日までに終わらない見込み |
| 残日数 ≤ 14 かつ status が 受任 より前 | 契約手続き中に期限が来る |
| 複雑性フラグ「先順位放棄が絡む」かつ 先順位の受理確認が未了 | 起算点・順位の確定に時間を要する |
| 財産概況/負債概況 に「不明」が残ったまま残日数 ≤ 30 | 調査に時間を要する |

- 伸長申立て自体も裁判所への対外提出であり、申立書は 06 の書類生成（テンプレート追加）
  → App 30 M4 承認発送に乗せる（**伸長申立の判断・申立書の内容は弁護士承認必須**）
- `期間伸長申立=認容` の登録後は `伸長後満了日` 基準で §4 の警報が再稼働する

## 6. 表示（kintone・運用）

- App 33 一覧「期限順」: 残日数昇順・status/確定チャネル/通知済み閾値を列表示
  （警報を受けた弁護士が最初に開く画面）
- 残日数・満了日はレコード保存時ではなく**日次ジョブが毎朝再計算**して書き込む
  （kintone の計算フィールドは「今日」を扱えないため Railway 側で計算する）
- 死活監視: `jukuryo_deadline_check` ジョブの実行記録（最終実行日）を検査し、
  24時間以上実行がなければ警報（**期限監視ジョブ自体の死活**が最重要監視対象）
