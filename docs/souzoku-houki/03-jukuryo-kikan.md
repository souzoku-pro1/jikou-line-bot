相続放棄ユニットの生命線。「自己のために相続の開始があったことを知った時から3ヶ月」
（民法915条1項）の期限を、**期日二本立て**（法定満了日／社内締切日）・申告値/確定値の分離・
段階警報で管理する。

## 1. 設計原則

1. **期日は二本立てで管理する**

   | 期日 | 計算方法 | 用途 |
   |---|---|---|
   | **法定満了日** | 民法どおり正確に計算: 初日不算入（140条）・暦計算（143条）・末日が土日祝/年末年始なら翌開庁日へ繰越（142条） | 裁判所への主張・上申書・期間伸長申立ての根拠となる**参考値**。対外文書はこちらを使う |
   | **社内締切日** | 安全側計算: **初日算入**（知った日当日を1日目とする）・**142条の繰越は適用しない** | **警報・進行管理の基準はすべてこちら**。一覧表示・残日数・閾値警報の基準 |

   さらに郵送提出バッファとして **提出目標日 = 社内締切日の7日前** を置き、
   警報体系は「提出目標日までに投函する」前提で組む
2. **申告値と確定値の分離** — Bot が聞いた日付は法的判断を経ていない。
   `_申告` フィールドと `_確定` フィールドを分け、確定は弁護士のみが行う
3. **確定前は安全側で計算** — 起算点候補のうち**最も早い日付**（通常は死亡日）で
   両期日を仮計算して警報する。実際の起算点が後なら余裕が増えるだけで、
   逆方向の事故（本当は期限が近いのに警報しない）が起きない
4. **両期日はシステムの「目安」であり法的確定ではない** — kintone・警報文言に
   「暫定」「弁護士確認前」を明示する。法定満了日を対外に用いるのは
   起算点確定済=yes かつ弁護士が承認した文書内に限る

## 2. フィールド設計（App 33・04 参照）

| フィールド | 書き手 | 意味 |
|---|---|---|
| `死亡日_申告` / `死亡を知った日_申告` / `相続人と知った日_申告` | Bot（ヒアリング） | 依頼者の申告。曖昧なら「YYYY-MM頃」も許容（`日付申告メモ` に原文保持） |
| `起算日_確定` | **弁護士のみ** | 弁護士が記録・面談で確定した起算日（DATE） |
| `起算点確定済` | 弁護士のみ | yes/no。yes になるまで安全側計算を続ける |
| `起算点メモ` | 弁護士 | 起算点判断の根拠（超過型では事情説明書の必須の根拠源・06 §3） |
| `法定満了日` | Railway（日次ジョブ） | §3.2。対外主張の参考値。人は編集しない |
| `社内締切日` | Railway（日次ジョブ） | §3.3。**警報・一覧・進行管理の基準** |
| `提出目標日` | Railway（日次ジョブ） | 社内締切日 − 7日（郵送提出バッファ） |
| `残日数` | Railway（日次ジョブ） | **社内締切日 − 今日**。マイナス=社内基準超過 |
| `期間伸長申立` | 弁護士 | 不要 / 検討中 / 申立済 / 認容 |
| `伸長後満了日` | 弁護士 | 認容された伸長後の期限（裁判所決定の日付） |
| `通知済み閾値` | Railway | CHECK_BOX {30日前, 14日前, 7日前, 超過}。警報の冪等キー |

## 3. 期日の計算ロジック（実装仕様）

### 3.1 起算点の選定（両期日共通）

```
起算点 = 起算点確定済 == yes ? 起算日_確定
        : min(死亡日_申告, 死亡を知った日_申告, 相続人と知った日_申告 のうち値があるもの)
        # 「YYYY-MM頃」しかない場合はその月の1日として扱う（安全側=早い方）
```

### 3.2 法定満了日（民法どおり・対外参考値）

```
1. 初日不算入（140条）: 起算点の翌日を起算日とする
2. 暦計算（143条2項）: 3ヶ月後の起算日応当日の前日に満了
   応当日が存在しない月（例: 11/30 起算日 → 2月）はその月の末日（143条2項ただし書）
3. 繰越（142条）: 満了日が土曜・日曜・祝日・年末年始（12/29〜1/3）に当たるときは
   翌開庁日に繰り越す（祝日データは予約枠ジョブと同じ同梱 CSV を共用・05 §2）
```

### 3.3 社内締切日（安全側・進行管理基準）

```
1. 初日算入: 起算点当日を1日目とする（= 起算点を起算日として 143条計算）
2. 暦計算: 3ヶ月後の起算日応当日の前日。応当日なしは月末
3. 142条の繰越は適用しない（土日祝に当たってもそのまま＝早い側に倒す）
提出目標日 = 社内締切日 − 7日
伸長認容後: 法定満了日 = 伸長後満了日 で上書きし、社内締切日 = 伸長後満了日 − 1日・
            提出目標日を再計算（伸長後も郵送バッファを維持）
```

- この定義により **社内締切日 ≦ 法定満了日 − 1日** が常に成立する
  （初日算入で1日早く、繰越なしでさらに早くなることはあっても遅くならない）。
  この性質は**性質テスト**として実装する（§7）
- **計算式は実装前に弁護士レビュー必須**（H5 タスクの完了条件。期間計算の解釈は
  最終的に弁護士が確認する — 法的判断のシステム焼き込みに当たるため）

## 4. 閾値別アラート（日次ジョブ `jukuryo_deadline_check`）

`hub/scheduler.register_daily`（毎日 7:30 JST・死活監視の直後）に登録。
対象: App 33 の status が {完了, 不受任, 辞任, 受理} **以外**の全レコード。
**残日数・閾値はすべて社内締切日基準**。警報文言には両期日を併記する
（例: `社内締切 8/9（法定満了 8/12・暫定）`）。

| 条件（社内締切日基準） | 警報（弁護士 LINE） | 併せて行う自動処理 |
|---|---|---|
| 残日数 ≤ 30 かつ 30日前未通知 | 【社内締切30日前】案件No・顧客名・両期日（暫定/確定の別）・現在status | `通知済み閾値` に 30日前 を追加 |
| 残日数 ≤ 14 かつ 14日前未通知 | 【社内締切14日前】+ 書類チェックリスト残 | 同上 + 期間伸長要否検知（§5） |
| **提出目標日到達**（残日数 ≤ 7）かつ 7日前未通知 | 【提出目標日・要対応】「本日以降の投函では社内基準の郵送バッファを割り込みます」 | 同上。以後**毎日**通知 |
| 残日数 < 0 かつ 超過未通知 | 【社内締切超過】※法定満了日が未到来なら「法定期限までは残 N 日。直ちに提出判断を」と併記 | 案件類型を 3ヶ月超過型 に更新（02 §3a）+ 事情説明書下書き生成をキュー（06 §3） |
| 起算点確定済=no かつ 残日数 ≤ 30 | 【起算点未確定のまま社内締切30日】 | 弁護士に確定作業を促す（毎回の閾値警報に付記） |

- 冪等性: `通知済み閾値` CHECK_BOX で同一閾値の再通知を防ぐ。提出目標日以降は意図的に毎日通知
- **即時警報（ジョブを待たない）**: Bot ヒアリング中に日付が upsert された時点で
  社内締切日基準の残日数を計算し、30日未満なら即時に弁護士警報（02 §4）

## 5. 期間伸長申立てが必要なケースの検知

家庭裁判所への熟慮期間伸長の申立て（民法915条1項ただし書）を「機械が提案し、
人が判断する」形にする。以下のいずれかで弁護士警報に**伸長検討の提案**を付記
（残日数は社内締切日基準）:

| 検知条件 | 根拠 |
|---|---|
| 残日数 ≤ 14 かつ 書類チェックリスト（04 §1.5）に未収集項目あり | 財産調査・戸籍収集が提出目標日までに終わらない見込み |
| 残日数 ≤ 14 かつ status が 受任 より前 | 契約手続き中に期限が来る |
| **受任時点の突合**: 続柄別の収集見込み日数（10 §4）+ 確定チャネル=C の郵送往復（既定7日・UNIT_CONFIG）を積んだ申述予定日が提出目標日を超える | 受任した瞬間に「間に合わないリスク」を早期警報（伸長判断の材料を最速で出す） |
| 複雑性フラグ「先順位放棄が絡む」かつ 先順位の受理確認が未了 | 起算点・順位の確定に時間を要する |
| 財産概況/負債概況 に「不明」が残ったまま残日数 ≤ 30 | 調査に時間を要する |

- 伸長申立書は 06 §4 のテンプレート → App 30 M4 承認発送に乗せる
  （**伸長申立の判断・申立書の内容は弁護士承認必須**。申立書に記載する期限は法定満了日）
- `期間伸長申立=認容` の登録後は §3.3 の伸長後計算で警報が再稼働する

## 6. 表示（kintone・運用）

- App 33 一覧「期限順」: **社内締切日の昇順**・残日数/status/確定チャネル/通知済み閾値を列表示
  （警報を受けた弁護士が最初に開く画面）。法定満了日はレコード詳細で確認
- 両期日・残日数はレコード保存時ではなく**日次ジョブが毎朝再計算**して書き込む
  （kintone の計算フィールドは「今日」を扱えないため Railway 側で計算する）
- 死活監視: `jukuryo_deadline_check` の最終実行日を検査し、24時間以上実行がなければ警報
  （**期限監視ジョブ自体の死活**が最重要監視対象）

## 7. テストケース（H5 の完了条件・08 参照）

| 区分 | ケース |
|---|---|
| 140条 初日不算入 | 法定満了日が起算点翌日起算になっていること（社内締切日との1日差検証を兼ねる） |
| 143条 暦計算 | 月の日数が異なる区間（1/31 起算等）・応当日なし（11/30 起算 → 2月末日）|
| 142条 繰越 | 末日が土曜・日曜・祝日・12/29〜1/3 → 翌開庁日。**社内締切日は繰り越さない**ことを同時検証 |
| 月末起算・うるう年 | 11/30・12/31 起算、うるう年2月をまたぐ区間 |
| 「頃」入力 | 月初丸め（安全側）になること |
| **性質テスト** | ランダム日付を含む全ケースで **社内締切日 ≦ 法定満了日 が常に成立**すること |
| 警報 | 閾値 30/14/7（提出目標日）/超過・毎日通知切替・起算点未確定警告・両期日併記の文言 |
