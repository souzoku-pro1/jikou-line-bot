# 10. 続柄別の必要戸籍マトリクス

> **正本参照（2026-07-03）**: 相続放棄ユニットの正本は
> [docs/architecture/10-unit-02-souzoku-houki.md](../architecture/10-unit-02-souzoku-houki.md)。
> 本ファイルと記述が衝突する場合は正本が優先する（受任フロー=B案ベース・裁量スキップ、
> 料金=88,000円+2人目以降33,000円、契約順序=決済→CloudSign、予約枠アプリ不採用 等の変更あり）。
> 本ファイルは詳細設計・履歴として存置。


申述人の続柄（相続順位）ごとに必要書類セットを定義し、
①ヒアリングからの自動導出 ②職務上請求（M1）の反復ループ ③熟慮期間との突合、
の3つの接続を設計する。書類チェック SUBTABLE（04 §1.5）の初期行生成の**具体仕様**。

## 1. 全類型共通・絶対必須（最優先取得）

| 書類 | 理由 | 取得タイミング |
|---|---|---|
| **被相続人の住民票除票（または戸籍の附票）** | **管轄家裁（最後の住所地）の確定に必要**（09 §2.3 の管轄マッチの入力）。続柄に関わらず必ず取得 | **受任確定と同時に M1 職務上請求を自動起票**（書類収集ループの最初の請求対象。管轄が確定しないと申述先が決まらないため最優先） |

- 除票は**保存期間の制約**（死亡による消除から一定期間で発行不能になり得る）があるため、
  取得遅延は警報対象: 起票から14日（config）で未受領 → 弁護士 LINE
  「除票の取得が遅延しています。附票への切替・電話確認を検討してください」
- 除票が取得不能だった場合は戸籍の附票に自動で切替提案（チェックリスト行の差し替えは弁護士）

## 2. 続柄別マトリクス

| 続柄（相続順位） | 必要書類セット（共通の除票/附票に**加えて**） | 概算通数の目安 |
|---|---|---|
| **子** | 被相続人の除籍謄本（死亡記載）／申述人の現在戸籍 | 2〜3通 |
| **親（直系尊属）** | 被相続人の**出生から死亡までの連続戸籍**／申述人の現在戸籍 | 4〜6通 |
| **兄弟姉妹** | 被相続人の**出生から死亡までの連続戸籍**（子の不存在確認のため）＋**被相続人の両親双方の死亡が確認できる戸籍**／申述人の現在戸籍 | 6〜10通 |
| **甥姪（代襲）** | 兄弟姉妹セットの全部＋**申述人の親（被相続人の兄弟姉妹）の死亡を証する戸籍** | 8〜12通 |

- **先順位者の放棄による順位繰上りの場合**（複雑性フラグ「先順位放棄」）は、
  マトリクスによる自動導出を行わず**弁護士が必要書類を個別確定**する
  （先順位者の放棄申述受理証明書の要否等、定型化できない判断を含むため）。
  チェックリストは共通の除票行のみ自動生成し、警報「必要書類の個別確定が必要です」を出す
- マトリクスは config のデータ（dict）として持ち、家裁の運用差・弁護士の方針変更は
  データ修正のみで反映（コード変更なし）

## 3. 接続①: ヒアリング→自動導出→見積時の案内

```
02 ヒアリング フェーズ3（相続順位・続柄）の回答
 → マトリクスから必要書類セットと概算通数を導出
 → 見積提示（01 [3]）に自動で組み込み:
   「お手続きには、被相続人の出生から死亡までの戸籍（4〜6通程度）などが必要です。
    取得は当事務所が代行します（実費別）」
 → 受任確定時（H9）: 書類チェック SUBTABLE の初期行をマトリクスから生成
   （04 §1.5 の初期行生成の具体仕様。マトリクスの正は本書 §2）
   行の内訳: 取得方法=職務上請求（戸籍系）/ 依頼者郵送（委任状・身分証）/ 事務所手配（印紙・郵券）
```

## 4. 接続②: 職務上請求（M1）の反復ループ

「出生から死亡までの連続戸籍」は、**取得した戸籍を読んで従前戸籍の本籍地が判明して
初めて次の請求先が決まる**。1回の請求では完結しないため、反復ループとして設計する:

```
[起票] 判明している本籍地（除票・依頼者申告）宛に M1 職務上請求を起票（H10）
 → 承認・発送・返送（ハブ M1 のフローどおり）
 → [受領] M5 が戸籍を受領・分類 → 案件紐付け → 書類チェック行を 受領 に
 → [読解] OCR 抽出で「従前戸籍（改製・転籍前）の本籍地・筆頭者」を検出
    ├─ 検出できた → 弁護士確認（「次は○○市の戸籍を請求します。よろしいですか」
    │   を承認キューに積む。**連鎖の各請求も職務上請求＝対外発信のため承認必須**）
    │   → 承認 → 次の M1 請求を自動起票（チェックリストに行を自動追加）
    ├─ 出生まで到達（連続が完成）→ ループ終了・チェックリストの連続戸籍行を 受領 に
    └─ 検出不能・判読不能 → 要確認（M5 の要確認キュー・弁護士が本籍地を手動入力）
```

- ループの完成判定（出生まで遡れたか）は OCR ベースの機械判定を**参考表示**にとどめ、
  **確定は弁護士**（チェックリスト行の 受領 化はシステム、連続完成の宣言は弁護士が
  `連続戸籍充足` フィールドを yes にする — 申述パッケージ前提条件ゲートの入力）
- 収集見込み日数（§5）はこのループ回数に依存する（1往復 ≒ 7〜10日 × 想定回数）

## 5. 接続③: 熟慮期間との突合（受任時の早期警報）

受任確定時に以下を計算し、**間に合わないリスクを受任した瞬間に警報**する（03 §5）:

```
申述予定日（見込み） = 今日
  + 続柄別の収集見込み日数（config: 子=14日 / 親=28日 / 兄弟姉妹=42日 / 甥姪=56日 を初期値とし実測で更新）
  + 確定チャネル=C の場合: 委任状の郵送往復日数（既定7日・UNIT_CONFIG）
申述予定日 > 提出目標日（03 §2）
  → 弁護士警報【収集が間に合わないリスク】+ 期間伸長申立ての検討提案
```

- この申述予定日は 02 §3a の類型判定（標準型/3ヶ月超過型）の入力にも使う

## 6. テスト観点（H9 / H10 の完了条件・08 参照）

- **続柄4類型（子/親/兄弟姉妹/甥姪）× 必要書類セットの導出テスト**（行内訳・概算通数）
- 順位繰上りケースでマトリクス導出が停止し個別確定警報が出ること
- 除票の最優先起票（受任確定フックで M1 下書きが作られる）・14日遅延警報
- 連鎖ループ: 従前戸籍検出→承認→次請求起票／出生到達で停止／検出不能→要確認
- 収集見込み日数×提出目標日の突合警報（境界: ちょうど提出目標日）
