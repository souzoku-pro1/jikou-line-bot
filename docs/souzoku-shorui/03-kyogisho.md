# 03. 遺産分割協議書

財産（App 36）× 相続人（App 37）× 割付（App 38）から「8割初稿」を差込生成する。
条項ライブラリはマスタ駆動（App 32 同封物ブロックマスタと同じ思想）。

## 1. 設計原則: 「8割初稿」

- **システムが書くのは定型部分だけ**: 前文（被相続人・相続人の表示）・財産の特定と
  取得条項（割付データから機械的に導出できるもの）・定型の一般条項・署名押印欄
- **特殊条項は AI 生成しない**。条項マスタの雛形差込か、`【弁護士記入】` プレースホルダを
  残して人が書く。生成文書はあくまで初稿であり、**最終文言の確定は全文弁護士**
- 生成トリガーは弁護士の明示操作（案件アプリのアクション等）。自動起票はしない
  （割付の合意形成は人間のプロセスであり、機械が先回りする場面がない）

## 2. ★App 39 条項マスタ（マスタ駆動・App 32 と同思想）

1レコード = 1条項雛形。事務員・弁護士がノーコードで文言をメンテする。

| フィールドコード | 型 | 用途 |
|---|---|---|
| `条項キー` | SINGLE_LINE_TEXT | 一意識別（例 `代償金_一括`）。重複禁止 |
| `カテゴリ` | DROP_DOWN | 取得条項 / 代償金 / 換価分割 / 債務負担 / 祭祀承継 / 生命保険 / 後日判明財産 / 一般条項 / その他特約 |
| `雛形本文` | MULTI_LINE_TEXT | プレースホルダ入り条文（例: `{{取得者}}は、第{{条番号}}条の財産を取得する代償として、{{相手方}}に対し、金{{代償金額}}円を{{支払期限}}までに支払う。`） |
| `自動採用条件` | DROP_DOWN | 手動のみ / 割付から自動（取得区分との対応・§3） |
| `表示順` | NUMBER | 条文の並び順 |
| `対象ユニット` | CHECK_BOX | 相続一般（将来拡張用） |
| `有効` | RADIO_BUTTON | |

- 初期データ（条項キーの初期セット）: 単独取得 / 共有取得 / 換価分割_売却・分配 /
  代償金_一括 / 代償金_分割 / 債務負担 / 葬儀費用負担 / 祭祀承継 / 生命保険の確認 /
  後日判明財産（再協議 or 特定相続人取得の2種）/ 清算条項 — **雛形文面は弁護士が作成**
- 整合性検査: 雛形本文のプレースホルダが規定セット外の名前を含む場合は
  日次死活監視で警報（App 32 の同期検査と同じ仕組みに登録）

## 3. 生成ロジック（割付 → 条項の自動組み立て）

```
1. 前文: 被相続人の表示（案件アプリ+App 36 由来）＋相続人全員の表示（App 37。
   住所・続柄・氏名。未成年/後見は特別代理人等の表示枠を【弁護士記入】で挿入）
2. 財産の特定: App 36 の有効行を種別順に条・別紙目録として採番
   （目録部の可変行は 02 §2 の fill_table_rows を共用）
3. 取得条項: App 38 の割付行を取得区分→条項マスタの `自動採用条件` で対応付けて生成
   （単独取得→単独取得条項、代償取得→代償金条項…）。対応する雛形が無効・不存在なら
   生成を止めて警報（暗黙のフォールバック文言は作らない）
4. 一般条項: カテゴリ=一般条項 の有効行を表示順に挿入（清算条項・後日判明財産）
5. 特殊事情の受け皿: 案件アプリ側の「特約メモ」があれば
   `第○条【弁護士記入: 特約メモ参照】` の空条を挿入（AI で文章化しない）
6. 署名押印欄・添付目録（§4）
```

- 生成前の整合性検証は 01 §3（全財産割付済み・共有持分合計=1・代償金対応）＋
  §5 の前提条件ゲート。違反は生成せず警報

## 4. 形式要件（テンプレートとチェックリストで担保）

| 要件 | 実装 |
|---|---|
| 署名押印欄 | 相続人ごとに「住所（自書）・氏名（自書）・実印」欄を App 37 から人数分生成（fill_table_rows）。代理人・特別代理人の欄種別に対応 |
| 印鑑証明書の添付 | 添付書類目録（印鑑証明書 各1通・発行3ヶ月以内等の注記）を自動生成し、App 37 の `印鑑証明` 未受領者がいれば**承認通知に警告を付記**（生成は止めない — 署名手配と並行するのが実務のため） |
| 契印・割印・製本 | docx 末尾に「製本・契印要領」を事務員向け注記として同梱（複数通作成: 相続人の人数分＋手続用の通数を案件から計算） |
| ページ番号・条番号 | テンプレート書式＋生成時採番。別紙目録との条・番号の対応はテストで検証 |
| 不動産の表示 | 登記事項証明書の表示に一致させる（App 36 特定情報は登記事項証明 OCR 由来を優先。手入力行は承認時に登記との突合を弁護士へ促す注記） |

## 5. 人間に残す分担（明記）

| 作業 | システム | 人間（弁護士） |
|---|---|---|
| 相続人の確定 | App 37 の一覧表示 | **戸籍による確定**（全員の `戸籍確認済=yes` が生成の前提条件） |
| 割付の内容 | 入力 UI（App 38）と整合検証 | **分割案そのもの**（合意形成・遺留分・特別受益・寄与分の考慮） |
| 条項文言 | マスタ雛形の差込 | **雛形の作成・特殊条項の起草・最終文言の全文確認** |
| 生成の前提条件ゲート | ①全相続人 戸籍確認済 ②全財産 評価確定（02 §6 と同一ガード関数を共有） ③割付整合 ④未成年/後見の状態なら特別代理人設定の警告 | ゲートを通す各確定行為 |
| 承認・発送 | App 30 の承認待ち起票→M4 送付案内で相続人へ郵送（**既存設計のまま使う**） | 承認（対外発信の承認必須原則） |

## 6. テスト観点（S 系列の完了条件用）

- 割付→条項の対応全パターン（6取得区分）と、雛形不存在時の生成停止
- 整合検証: 未割付財産・持分合計≠1・代償金の片側欠落 → 生成拒否
- 前提条件ゲート: 戸籍未確認・評価未確定・未成年警告の各分岐
- 署名欄・添付目録の人数分生成（1人〜多人数・受遺者混在）
- ゴールデンファイル比較（標準ケース: 不動産+預貯金+代償金+清算条項）
