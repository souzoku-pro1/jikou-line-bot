# 01. データスキーマ（kintone）

書類3種（財産目録・遺産分割協議書・遺言書）が共通に使う正規化データ層。
新設3アプリ＋条項マスタ（03 で定義）で構成し、**既存アプリは壊さない**。

> アプリ番号は仮番号（実IDは env 注入・既存規約どおり）。
> 既存採番: 21 案件(時効) / 25 不動産 / 26 相談カード / 27 戸籍 / 28-29 / 30-32 ハブ / 33-35 相続放棄

## 1. ★App 36 財産（案件横断の財産台帳）

1レコード = 1財産（または1債務）。財産目録の行・協議書の割付対象・遺言の目録別紙の
**単一の真実**。OCR 抽出の着地点でもある。

### 1.1 フィールド定義

| フィールドコード | 型 | 選択肢 / 用途 |
|---|---|---|
| `案件アプリID` / `案件レコードID` / `ユニット種別` / `被相続人名表示用` | SINGLE_LINE_TEXT ×3 + DROP_DOWN | ハブ共通の案件参照方式（相続一般=App 26 / 相続放棄=App 33 の両方から使える） |
| `財産種別` | DROP_DOWN | 不動産_土地 / 不動産_建物 / 不動産_区分建物 / 預貯金 / 有価証券 / 生命保険 / 出資金 / 自動車 / 動産 / 債権 / **債務** / 葬儀費用 / その他 |
| `特定情報` | MULTI_LINE_TEXT | 書類に印字する特定表示（不動産: 所在・地番・地目・地積等／預貯金: 金融機関・支店・種別・口座番号／保険: 会社・証券番号 等）。**目録・協議書はこの欄をそのまま差し込む**（種別ごとの推奨書式は 02 §2.3） |
| `名義` | SINGLE_LINE_TEXT | 被相続人名義か否かの確認用（名義預金等の検討材料） |
| `評価額` | NUMBER | 円 |
| `評価方法` | DROP_DOWN | 固定資産税評価額 / 相続税評価額 / 残高証明 / 解約返戻金相当額 / 時価査定 / 額面 / その他 |
| `評価基準日` | DATE | 残高証明の基準日・課税明細の年度など |
| `評価確定` | RADIO_BUTTON(no/yes) | **弁護士（または依頼税理士）のみ yes にする**。書類生成の前提条件（02 §6） |
| `備考` | MULTI_LINE_TEXT | |
| `データ源` | DROP_DOWN | OCR_課税明細 / OCR_残高証明 / OCR_登記事項証明 / 手入力 / ヒアリング |
| `確信度` | NUMBER | OCR 経路のみ（0〜1）。閾値未満は登録されず要確認キューへ |
| `元アプリID` / `元レコードID` | SINGLE_LINE_TEXT | 既存詳細台帳への参照（不動産→App 25 のレコード等・§3） |
| `原本` | FILE | 根拠書類の PDF（課税明細・残高証明・登記事項証明）。**必ず添付**（穴の解消） |
| `冪等キー` | SINGLE_LINE_TEXT | Drive_fileId または PDF の SHA-256＋ページ番号（重複投入防止） |
| `有効` | RADIO_BUTTON(yes/no) | 誤登録の論理削除（物理削除しない・監査痕跡） |

### 1.2 設計判断

- **債務・葬儀費用も財産種別として同一アプリで扱う**（協議書の債務負担条項・
  目録の消極財産の部で必要。マイナスの財産を別アプリにすると割付が二重管理になる）
- 種別ごとの詳細構造（不動産の床面積等）は持たない。詳細は元台帳（App 25）に残し、
  書類に必要な表示だけを `特定情報` に正規化する（書類生成に必要十分・過剰正規化しない）

## 2. ★App 37 相続人

1レコード = 1案件の1相続人（受遺者を含む）。

| フィールドコード | 型 | 用途 |
|---|---|---|
| 案件参照4点 | （App 36 と同じ） | |
| `氏名` / `フリガナ` | SINGLE_LINE_TEXT | |
| `続柄` | DROP_DOWN | 配偶者 / 子 / 直系尊属 / 兄弟姉妹 / 甥姪（代襲） / 受遺者（相続人外） / その他 |
| `法定相続分` | SINGLE_LINE_TEXT | 分数表記（例 `1/2`）。**Railway が続柄構成から自動計算して書き込み、弁護士が確認**（代襲・放棄で変わるため確定は人・§2.1） |
| `住所` / `生年月日` / `本籍` | SINGLE_LINE_TEXT ×2 + SINGLE_LINE_TEXT | 協議書の当事者表示・署名欄に差込 |
| `連絡先` | SINGLE_LINE_TEXT | |
| `状態` | DROP_DOWN | 通常 / 放棄済み / 代襲 / 相続分譲渡 / 未成年（特別代理人要） / 成年被後見人 |
| `戸籍確認済` | RADIO_BUTTON(no/yes) | **弁護士のみ**。協議書生成の前提条件（相続人の確定は戸籍による・03 §5） |
| `印鑑証明` | DROP_DOWN | 未 / 依頼中 / 受領 | 協議書の添付書類管理 |
| `データ源` | DROP_DOWN | ヒアリング / 戸籍読解 / 手入力 |

### 2.1 戸籍読解との将来接続（設計のみ・実装は後続）

- 相続放棄ユニットの連続戸籍ループ（souzoku-houki/10 §4）が M5 で戸籍を読解した際、
  判明した相続人候補を App 37 に `データ源=戸籍読解`・`戸籍確認済=no` で自動起票する
  拡張ポイントを確保（**本設計ではフィールドを用意するだけ**。自動起票は H 系列側の将来タスク）
- 法定相続分の自動計算は「配偶者+子/尊属/兄弟姉妹」の基本構成のみ対応し、
  代襲・二重身分・相続分譲渡は計算せず空欄+警報（弁護士が記入）

## 3. ★App 38 割付（誰がどの財産を取得するか）

1レコード = 1財産 × 1取得者。協議書「8割初稿」と財産目録の取得者列の駆動データ。

| フィールドコード | 型 | 用途 |
|---|---|---|
| 案件参照4点 | | |
| `財産レコードID` | SINGLE_LINE_TEXT | App 36 参照 |
| `相続人レコードID` | SINGLE_LINE_TEXT | App 37 参照 |
| `取得区分` | DROP_DOWN | 単独取得 / 共有取得 / 換価分割 / 代償取得 / 債務引受 / 保険金受取（みなし） |
| `持分` | SINGLE_LINE_TEXT | 分数（共有取得時） |
| `代償金額` | NUMBER | 代償取得時（支払側・受領側は条項で表現） |
| `条件メモ` | MULTI_LINE_TEXT | 弁護士向け（例: 引渡し時期） |
| `有効` | RADIO_BUTTON(yes/no) | |

- 整合性検証（Railway・生成時）: ①全有効財産が1件以上の割付を持つ（換価分割は例外規定）
  ②共有持分の合計=1 ③代償金の支払・受領の対応。違反は生成せず警報
- 別アプリ（SUBTABLE でなく）にした理由: 相続人単位の取得集計・
  協議書の条項順生成・将来の遺留分チェックが行指向で扱えるため

## 4. 既存の相続系4アプリとの関係（統合か参照か）

**方針: 統合しない。参照する。**（既存アプリのフィールドは一切変更しない）

| 既存アプリ | 関係 | 理由 |
|---|---|---|
| 相談カード（26） | **案件アプリとして参照**（App 36-38 の案件参照先） | 相続一般ユニットの事実上の案件台帳。UNIT_CONFIG 登録のみで昇格 |
| 不動産（25） | **詳細台帳として参照**（財産行の `元アプリID/元レコードID`） | 登記詳細・持分・担保は 25 に残し、App 36 には書類表示用の正規化行だけ持つ。/ocr/fixed-asset の既存上書き先も 25 のまま |
| 戸籍（27） | 参照（将来: 相続人テーブルの自動起票ソース・§2.1） | 財産ではない |
| 通帳（env 未設定・休眠） | **新規書き込み停止**（再開時から財産テーブル直行） | 残高証明ベースの預貯金行と二重管理になるため。既存レコードは読み取り専用で温存 |

### 4.1 既存アプリを壊さない移行手順

```
Step 1  App 36/37/38 を新設（既存アプリ・既存コードに変更なし。この時点で共存）
Step 2  EXPECTED_KINTONE_SCHEMA に3アプリを登録（作成直後から死活監視・既存規約）
Step 3  /ocr/fixed-asset を「追記型」で拡張（02 §3）:
        既存動作（不動産25の上書き）は完全に維持し、成功時に App 36 の財産行を
        upsert する処理を追加。ロールバックは追加処理の無効化のみ（env フラグ）
Step 4  新書類種別（残高証明・登記事項証明）は最初から App 36 直行（02 §4）
Step 5  通帳経路の再開判断時: DOC_TYPE_CONFIG の登録先を App 36 に設定して再開
        （既存通帳アプリは変更せず放置。レコードは残る）
Step 6  安定稼働後、不動産25→App 36 の既存データ一括転記スクリプト（dry-run 付き・
        S1 完了条件）で過去分を財産テーブルに取り込む（元レコードID で二重取込防止）
```

## 5. UNIT_CONFIG への追加

```python
UNIT_CONFIG["相続一般"] = {
    "case_app_env": ("SOUZOKU_KINTONE_APP_ID", "SOUZOKU_KINTONE_API_TOKEN"),  # 既存 App 26
    "customer_name_field": "氏名",
    "customer_addr_field": "住所",
    "channels": ["送付案内", "スキャン受領"],       # 発送はM4・受領はM5（既存設計のまま）
    "template_dir": "souzoku",                      # docx_templates/souzoku/
}
```
