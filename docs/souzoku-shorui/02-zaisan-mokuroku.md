# 02. 財産目録

App 36（財産）から docx 帳票を生成し、入力側は既存 OCR 2系統を拡張して自動化する。
遺言書の「財産目録別紙」（04 §2）と同じ生成部品を共用する。

## 1. 出力: docx 帳票（hub/docx_builder に乗せる）

- テンプレート: `docx_templates/souzoku/財産目録.docx`（規約配置・resolve_template）
- 構成: 表紙情報（被相続人・作成日・作成者表示）＋種別ごとのセクション表
  （Ⅰ 不動産／Ⅱ 預貯金／Ⅲ 有価証券・保険等／Ⅳ 動産その他／Ⅴ 債務・葬儀費用）＋合計欄
- 差込: 固定部は既存 `fill_template`（**既存のまま使う**）。
  **可変行（財産の行）は §2 の行複製拡張**で差し込む

## 2. hub/docx_builder の拡張: 表の行複製（新エンジン禁止の範囲内）

既存 `fill_template` は文字列置換のみで**表の行数を増やせない**。
本書類群（目録・協議書の目録部・遺言の別紙）はいずれも可変行の表を持つため、
hub/docx_builder に**1関数だけ追加**する（T0-3 成果物への追加・S2）:

```python
def fill_table_rows(doc, row_marker: str, rows: list[dict]) -> None:
    """row_marker（例 "{{行:財産}}"）を含むテンプレート行を rows の件数分
    複製し、各行の {{行:列名}} プレースホルダを置換する。
    - python-docx の tr 要素コピーで実装（書式・罫線はテンプレート行を継承）
    - rows が空のときはテンプレート行ごと削除（空セクションは「該当なし」行に）
    """
```

- 既存 `fill_template` の実装・挙動は不変（回帰テストで担保）。
  **別テンプレートエンジン（Jinja2 等）は導入しない**
- 数値の書式（3桁カンマ・円）・分数表記は呼び出し側（units 層）で文字列化してから渡す

### 2.3 `特定情報` の推奨書式（種別別・入力時ガイド）

| 種別 | 目録・協議書に印字される書式例 |
|---|---|
| 不動産_土地 | `所在 川口市○○一丁目 / 地番 12番3 / 地目 宅地 / 地積 120.45㎡` |
| 預貯金 | `○○銀行 △△支店 普通預金 口座番号1234567` |
| 生命保険 | `○○生命 終身保険 証券番号12-345678` |
| 債務 | `○○銀行 住宅ローン（残債）` |

（OCR 転記時は Railway が抽出項目からこの書式に組み立てる。手入力時の見本として
App 36 のフィールド説明にも同文を記載する）

## 3. 入力自動化①: 課税明細 —「/ocr/fixed-asset を流用・拡張」

**既存のまま使う部分**: 事務所 PC の `ocr_watcher.py`（OCR_inbox 監視→POST）、
Vision OCR、Claude 抽出（評価額・年度・所在地・地番）、不動産25の検索・上書き。

**拡張する部分**（追記型・既存動作は不変。01 §4.1 Step 3）:

```
既存処理成功後に追加:
 1. 案件紐付け: リクエストに case_hint（案件レコードID）が無い場合、
    不動産25のヒットレコード → 過去の財産行（元レコードID）→ 案件を逆引き。
    どれtoo不能なら App 36 に登録せず要確認キューへ（§5）
 2. App 36 に財産行を upsert:
    財産種別=不動産_*（種別は25の種別から）/ 特定情報（§2.3 書式に組み立て）/
    評価額 / 評価方法=固定資産税評価額 / 評価基準日=年度 / データ源=OCR_課税明細 /
    元アプリID=25・元レコードID / 原本=受信PDF / 冪等キー=PDF SHA-256
    ※ upsert キーは (案件, 元レコードID, 評価基準日)。同一年度の再送は上書き
 3. 冪等: SHA-256 一致の既処理 PDF は skip 応答（ocr_watcher 側は送信済み扱い）
```

- ロールバック手段: 追加処理を env フラグ `ZAISAN_SYNC_DISABLED=1` で無効化できる
  （既存の上書き動作だけが残る＝現状と同一）

## 4. 入力自動化②: 残高証明・登記事項証明 — M5（/scan/v2）のエントリ追加

architecture/08 の DOC_TYPE_CONFIG（分類→抽出スキーマ→登録先）に**2種別を追加するだけ**
（M5 本体のコード変更なし＝ハブ拡張ポイントの検証を兼ねる）:

| doc_type | 抽出項目 | 登録先 |
|---|---|---|
| 残高証明書 | 金融機関名・支店・預金種別・口座番号・残高・基準日・（複数口座は口座ごとに行分割） | App 36（1口座=1財産行・種別=預貯金・評価方法=残高証明） |
| 登記事項証明書 | 所在・地番/家屋番号・地目/種類・地積/床面積・名義人・（乙区の担保有無） | App 36（種別=不動産_*）＋**不動産25にも詳細行を作成**し相互参照。抽出スキーマは `ocr_to_claude.py`・`registry_to_kintone.py` の項目対応表を下敷きにする（**registry の既知不整合〔担保内容フィールド不存在・種別選択肢〕は流用時に修正**） |

- **T4 系（/scan/v2）完成前の暫定運用**: 系統A（GAS）は現状エラー処理が無く
  poison-pill リスクがあるため、新種別の投入は**系統B のローカル送信（手動）または
  /scan/v2 完成後**とする。S 系列は T4-1 完了を前提依存に置く（05）
- 原本 PDF 添付・Drive_fileId 冪等・案件紐付けは M5 設計（architecture/08 §1・§3）を
  そのまま使う（本設計で新規に作らない）

## 5. 確信度低・紐付け不能 → 要確認キュー（既存設計のまま使う）

- M5 の要確認キュー（App 30・発送ステータス=要確認・architecture/08 §4）に乗せる。
  課税明細（系統B）も同じキューに登録する（系統B専用の別キューは作らない）
- 人の操作: 要確認レコードに案件参照・種別を補記→下書きに変更→再処理（既存の一巡）

## 6. 評価額の妥当性チェック — 人間に残す分担（明記）

| 作業 | システム（自動） | 人間（弁護士・依頼税理士） |
|---|---|---|
| 抽出値の機械検証 | 数値形式・桁（評価額が0や10^12超で警報）・基準日の妥当性（年度が古い→警報）・同一財産の重複検知 | — |
| 評価方法の選択 | OCR 由来の初期値を設定するだけ | **評価方法の妥当性判断**（固定資産税評価額か時価か等・遺産分割の性質による） |
| 評価額の確定 | — | **`評価確定=yes` にする行為そのもの**（弁護士のみ。全行 yes が目録生成の前提条件） |
| 合計・整合 | 目録の合計計算・積極/消極の区分集計 | 名義預金・使途不明金など評価以前の帰属判断 |

- 目録 docx には `評価確定=no` の行が1件でもあれば生成しない（前提条件ガード・
  協議書 03 §5 と同一のガード関数を共有）

## 7. テスト観点（S 系列の完了条件用）

- fill_table_rows: 行複製・書式継承・空リスト時の「該当なし」・既存 fill_template の回帰
- 課税明細拡張: 既存動作の完全回帰（不動産25上書きが不変）・upsert キー・SHA-256 冪等・
  ZAISAN_SYNC_DISABLED フラグ・紐付け不能→要確認
- 残高証明: 複数口座の行分割・基準日抽出
- 前提条件ガード: 評価確定=no 混在で生成拒否
- 目録 docx: 種別セクション振り分け・合計・債務の部（ゴールデンファイル比較）
