- 最終更新: 2026-07-03（P0＝共通基盤の本番反映まで）
- この説明書は「いま実際に動いているもの」だけを §1〜3 に、「設計済み・未着工のもの」を §4 に分けています

## 1. 全体地図：うちのシステムには誰がいるのか

事務所に例えると、このシステムは「24時間働く事務員チーム」です。
それぞれの係は次のとおりです。

| 係 | 正体 | 何をしてくれるか（たとえ話） |
|---|---|---|
| **受付窓口** | LINE 公式アカウント（時効援用専門窓口） | 依頼者と話す窓口。相談者はここに話しかけてきます |
| **24時間働く事務員** | Railway（レイルウェイ）上のプログラム | クラウド（インターネット上の借りサーバー）に住んでいる事務員。LINE の応対文を考え、キャビネットに記録し、警報を鳴らします。**頭脳として Claude（AI）を使っています** |
| **キャビネット** | kintone（キントーン）※クラウド型のデータベースサービス | 事務所の書類棚。中に7つの引き出し（アプリ）があります（下表） |
| **郵便受けの監視係** | GAS（ガス）※Google のスプレッドシート等に付けられる自動処理 | Google Drive（グーグルのオンライン保管庫）の3つのフォルダを見張り、書類のPDFが入ると事務員に渡します。**確認済みは1本**（「相続書類自動化」）。ほかに「案件管理」「droa」という名前の GAS が存在する模様ですが、中身は未確認です（確認待ち） |
| **事務所PCのスキャン係** | ocr_watcher（オーシーアール・ウォッチャー）※事務所のパソコンに常駐する小さなプログラム | デスクトップの「OCR_inbox」フォルダに固定資産税のPDFを入れると、自動で読み取って不動産の引き出しに評価額を書き込みます |
| **電子ハンコ屋** | CloudSign（クラウドサイン） | 委任契約書のオンライン締結。署名が終わると事務員に「締結完了」の電話（後述の Webhook）をかけてきます |
| **レジ係** | Stripe（ストライプ） | クレジットカード決済。入金があると事務員に知らせます |
| **文字読み取りの外注先** | Google Vision（ビジョン）※画像から文字を読むAIサービス | PDFの文字起こし職人。読んだ文字は Claude が意味を解釈します |

**kintone の7つの引き出し（アプリ）:**

| 引き出し | 番号 | 中身 |
|---|---|---|
| 案件（時効援用） | App 21 | 依頼者ごとの1件1枚のカルテ。進行状態（status）もここ |
| チャットログ | App 28 | LINE のやり取りの記録全部 |
| **承認キュー** | App 29 | **先生の承認待ちの返信下書き置き場。先生が一番よく使う引き出し** |
| 相談カード（相続） | App 26 | スキャンした相続相談カードの内容 |
| 戸籍謄本 | App 27 | スキャンした戸籍の読み取り結果（簡易版） |
| 不動産 | App 25 | 物件情報と固定資産税評価額 |
| 通帳 | （休眠中） | **接続設定が未完了のため使っていません。⚠ Drive の「通帳」フォルダにPDFを入れないでください**（入れると監視係が転んで、他のフォルダの処理まで止まります） |

**見えない仕組みを2つだけ**：
- **Webhook（ウェブフック）＝内線電話**。「締結が終わりました」「承認済になりました」と、外部サービスがうちの事務員に自動でかけてくる電話です。合言葉付きなので部外者はかけられません。
- **毎朝7時の見回り（日次死活監視）**。事務員が毎朝、AIの頭脳・7つの引き出しの棚割り・書類のひな型を点検します。**異常があるときだけ**先生の LINE に報告が来ます。何も来ない朝＝正常です。

## 2. 業務の流れ：時効援用の実際の1件が流れる順番

依頼者が LINE で相談してから入金までを、部品の動きで追います。

### ① 相談開始（全自動）
依頼者が LINE 友だち追加 → 受付窓口が挨拶し、5項目（債権者名・借入時期・最終返済日・裁判所書類の有無・信用情報）を聞き取ります。この応対文は Claude が作りますが、**定型ヒアリングなので先生の承認は不要**です。

### ② カルテ作成（全自動）
5項目が揃うと、事務員が App 21 に新しいカルテを作ります（status＝問い合わせ）。時効の可能性がありそうなら、続けて氏名・住所・生年月日・電話・メールを聞き、カルテに追記します。

### ③ 以後の会話は「トリアージ」（自動と承認の振り分け）
ヒアリング完了後の依頼者メッセージは、Claude が内容を分類（トリアージ）します。
- **自動返信してよい6分類**（挨拶／手続きの一般的な流れ／必要書類の案内／費用の定型案内／進捗の事実回答／営業案内・アクセス）→ そのまま返信されます
- **それ以外**（法的判断・費用交渉・クレーム・裁判所書類などの緊急・第三者・迷ったもの全部）→ **返信されず、下書きが App 29（承認キュー）に入り、先生に【承認依頼】LINE が届きます**。依頼者には「確認してご連絡します」の定型文だけが返ります

### ④ 契約（ここは一部、人の作業）
受任が決まったら、**CloudSign での契約書の作成・送信は現状手動**です（先生または事務員が CloudSign の画面から送ります。このとき書類番号〔documentID〕を App 21 に控えておくのも手動です）。
依頼者が署名すると、CloudSign が内線電話（Webhook）をかけてきて、**事務員が App 21 の status を自動で「受任」に変え、先生に【締結完了】LINE を送ります**。

### ⑤ 入金（一部、人の作業）
**Stripe の決済リンクを依頼者に送るのは現状手動**です。依頼者がカード決済すると、Stripe の内線電話で事務員が入金を記録します。
⚠ 既知の弱点：この記録は今、**新しいカルテとして追加される**作りです（既存カルテへの追記になっていない）。週次点検（§3）で二重カルテがないか見てください。改修予定は §4 のとおりです。

### ⑥ 受任後の日常対応（③と同じ）
受任後も依頼者との会話は③のトリアージで回り続けます。並行して、相続系の紙書類は Drive のフォルダ（相談カード／戸籍謄本）に入れれば監視係→事務員→引き出しへ自動転記、固定資産税の課税明細は事務所PCの OCR_inbox に入れれば自動で不動産の引き出しに反映されます。

**まとめ：人がやるのは「承認」「CloudSign 送信」「決済リンク送付」「紙のスキャン投入」の4つ。それ以外は自動です。**

## 3. オーナーの操作手順

### 3.1 毎日やること（平常時：合計5分以内）

1. **LINE を見る**。来ていなければ、やることはありません（平常時人間ゼロが設計方針です）
2. **【承認依頼】が来ていたら承認する**（下の3.3）
3. 毎朝7時の見回り報告は「異常時のみ」届きます。**何も来ない＝健康**です

### 3.2 週次でやること（10分）

1. **Stripe の入金と App 21 の突合**：決済があった週は、App 21 に二重カルテができていないか確認（§2⑤の既知の弱点対策）。二重があれば古い方に統合メモを残してください
2. **Google Drive の整理（任意）**：処理済みファイルには先頭に「[済]」が付きます。溜まってきたら別フォルダに移動して構いません。**「[済]が付かないまま残っているPDF」があれば処理に失敗しています** → 開発担当（Claude Code）に伝えてください
3. **OCR_inbox の「エラー」フォルダ確認**：中にPDFがあれば読み取り失敗です → 同上

### 3.3 承認のやり方（画面操作）

1. LINE に「【承認依頼】顧客: ○○ / カテゴリ: ○○ / 承認キューレコードNo: ○○」が届く
2. kintone を開き、**App 29（承認キュー）** の該当レコードを開く
3. **「AI下書き」欄を読む**。直したければこの欄を直接編集する（編集した文がそのまま送られます）
4. **「ステータス2」を「承認済」に変えて保存**
5. これだけで依頼者の LINE に送信され、「送信済み」が自動で yes になります（二重送信はされません）

### 3.4 警報 LINE が来たときの対応表

| 届いた LINE | 意味 | 先生のやること |
|---|---|---|
| 【承認依頼】 | 返信下書きが承認待ち | 3.3 の手順。**当日中推奨** |
| 【締結完了】 | 契約書が署名された | 対応不要（App 21 が「受任」になったか見るのは任意） |
| ✅固定資産税評価額の更新が完了しました | スキャンが引き出しに反映された | 対応不要 |
| 【Claudeフォールバック発動】 | AIの頭脳を予備に切り替えて**稼働継続中** | 急ぎ対応不要。落ち着いたら開発担当に「モデル更新して」と依頼 |
| 【Claude応答不能・要対応】 | AIが完全停止。依頼者には「確認中」と自動返信済み。App 29 に**要対応**レコードあり | App 29 を開き、**AI下書き欄に先生が返信文を書いて**「承認済」にする（＝手動返信）。続くようなら開発担当へ |
| 【日次死活監視: 異常検知】モデルが存在しません | AIモデルの提供終了 | 開発担当に「モデル更新して」と依頼 |
| 【日次死活監視: 異常検知】フィールド「○○」が存在しません／選択肢がありません | **誰かが kintone の棚割り（フィールド名や選択肢）を変えた** | 心当たりを確認し、元に戻す。意図的な変更なら開発担当に連絡（プログラム側も直す必要あり） |
| 【日次死活監視: 異常検知】テンプレート○○にプレースホルダがありません | 書類ひな型の**差込枠 `{{…}}` が編集で消された** | ひな型（Word ファイル）の `{{日付}}` のような二重カッコを復元する |

### 3.5 やってはいけないこと・注意

- ⚠ **Drive の「通帳」フォルダに PDF を入れない**（§1 の表のとおり。全フォルダの処理が止まります）
- ⚠ **kintone のフィールド名・選択肢を変えない**（変えると翌朝警報＋機能停止。変えたい時は開発担当とセットで）
- ⚠ **書類ひな型（Word）を編集するときは `{{…}}` を消さない**
- 依頼者の status を変えた直後に LINE の応対がおかしい場合、事務員の「記憶のリセット」（再起動）で直ります → 開発担当に「redeploy して」と依頼（30〜60秒 LINE 応答が遅れるため、深夜早朝が安全です）

## 4. 建設中のもの（設計図は完成・工事はこれから）

設計図はすべて docs/ フォルダに保存済みで、AI（Sonnet）に1工程ずつ発注できる状態です。
**土台（P0：共通部品3点）は完成し、本番で稼働中**です（見た目の変化はありませんが、この上に以下が載ります）。

| 建設予定 | 完成すると何ができるか（3行） |
|---|---|
| **発送/受領ハブ**（設計: docs/architecture/） | 職務上請求・内容証明・FAX・送付案内という「事務所から外に出るもの」を1つの台帳で管理。全件、先生の承認を通ってからしか外に出ない仕組み。返送書類はスキャンだけで自動消込 |
| **相続放棄ユニット**（docs/souzoku-houki/） | 相続放棄専用の LINE 窓口と Bot ヒアリング。命綱の「3ヶ月の熟慮期間」を安全側で自動計算し、30/14/7日前に警報。申述書と家裁提出セットを自動で組み立て（提出前は必ず先生の承認） |
| **相続書類生成ライン**（docs/souzoku-shorui/） | 財産目録・遺産分割協議書・遺言書の「8割初稿」を自動生成。課税明細・残高証明・登記事項証明のスキャンから財産台帳へ自動転記。評価額の確定と特殊条項は先生の仕事のまま |
| **補助金ユニット**（docs/hojokin/) | 補助金申請支援の第3の商売。新しい公募が出ても**プログラム改修なしで**マスタ登録だけで受付開始できる構造。適格性診断 Bot・締切警報・着手金＋成功報酬の請求まで |
| **戸籍読解・関係図**（docs/koseki-ocr/） | 戸籍の束をスキャン→AIが読み→**画面で原本と見比べて直す**半自動方式。相続人関係図と法定相続情報一覧図を自動作図。通帳の取引明細も表計算に自動整理 |

## 5. 用語集（五十音・ABC順）

| 用語 | 意味 |
|---|---|
| **API（エーピーアイ）** | プログラム同士の注文窓口。「kintone の API を呼ぶ」＝プログラムが kintone に読み書きの注文を出すこと |
| **App（アプリ）** | kintone の引き出し1つのこと。App 21 なら21番の引き出し |
| **CloudSign** | 電子契約サービス。紙とハンコの代わりにオンラインで契約書を締結する |
| **GAS（ガス）** | Google Apps Script。Google のサービスに付けられる自動処理。うちでは Drive のフォルダ監視係 |
| **kintone（キントーン）** | サイボウズ社のクラウド型データベース。うちの全記録の保管庫 |
| **OCR（オーシーアール）** | 画像やPDFから文字を読み取る技術。スキャンした紙をデータにする係 |
| **Railway（レイルウェイ）** | プログラムを24時間動かしてくれる借りサーバー。うちの事務員の住まい |
| **Stripe（ストライプ）** | クレジットカード決済サービス。うちのレジ係 |
| **Webhook（ウェブフック）** | 出来事が起きた瞬間に外部サービスからうちの事務員へかかってくる自動の内線電話 |
| **警報／死活監視** | システムが自分の健康を毎朝点検し、異常時だけ LINE で知らせる仕組み |
| **デプロイ** | 改修したプログラムを本番の Railway に配置し直すこと。引っ越し作業。30〜60秒 LINE 応答が遅れることがある |
| **トリアージ** | 依頼者メッセージの選別。自動返信してよいものと、先生の承認が要るものに分けること |
| **ブランチ** | プログラムの下書き用の分岐。本番（main）を汚さずに改修作業をする場所 |
| **プレースホルダ** | 書類ひな型の差込枠。`{{日付}}` のような二重カッコ。ここに実データが流し込まれる |
| **PR／マージ** | PR（プルリクエスト）＝下書きを本番に取り込む申請書。マージ＝その承認・合体。マージすると自動でデプロイされる |
| **モデル（Claude のモデル）** | AIの頭脳のバージョン。提供終了があるため予備を常備し、切替時は警報が来る |
| **リポジトリ** | プログラムと設計書一式の保管庫（GitHub 上）。全変更の履歴が残る |
| **レコード** | kintone の引き出しの中の1枚のカード。1案件・1メッセージなど |
