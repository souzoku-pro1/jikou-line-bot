## 1. 全体地図：うちのシステムには誰がいるのか

事務所に例えると、このシステムは「24時間働く事務員チーム」です。
それぞれの係は次のとおりです。

| 係 | 正体 | 何をしてくれるか（たとえ話） |
|---|---|---|
| **受付窓口** | LINE 公式アカウント（時効援用専門窓口） | 依頼者と話す窓口。相談者はここに話しかけてきます |
| **24時間働く事務員** | Railway（レイルウェイ）上のプログラム | クラウド（インターネット上の借りサーバー）に住んでいる事務員。LINE の応対文を考え、キャビネットに記録し、書類を作り、警報を鳴らします。**頭脳として Claude（AI）を使っています** |
| **キャビネット** | kintone（キントーン） | 事務所の書類棚。時効援用、相続系スキャン、発送管理などの引き出しがあります（下表） |
| **発送・受領ハブ** | App 30（発送管理）＋ hub/dispatch | 事務所から外へ出す書類と、返送待ちを1つの台帳で管理します。先生の承認なしに外へ出ることはありません |
| **市区町村住所録** | App 31（市区町村マスタ） | 職務上請求の宛先、担当部署、住所、手数料を持つ住所録です。未登録なら「登録してください」と警報します |
| **同封物マスタ** | App 32（同封物ブロックマスタ） | 送付案内に載せる同封物名、案内文、返送が必要かどうかを管理します |
| **郵便受けの監視係** | GAS（ガス）※Google Apps Script | Google Drive の「相談カード」「戸籍謄本」「通帳」フォルダを見張り、PDF が入ると Railway に渡します。2026-07-03 午前の調査で、確認済みの GAS は「相続書類自動化」1本です |
| **事務所PCのスキャン係** | ocr_watcher | デスクトップの「OCR_inbox」フォルダに固定資産税のPDFを入れると、自動で読み取って不動産の引き出しに評価額を書き込みます |
| **電子ハンコ屋** | CloudSign（クラウドサイン） | 委任契約書のオンライン締結。署名が終わると事務員に「締結完了」の電話（Webhook）をかけてきます |
| **レジ係** | Stripe（ストライプ） | クレジットカード決済。入金があると事務員に知らせます |
| **文字読み取りの外注先** | Google Vision | PDFの文字起こし職人。読んだ文字は Claude が意味を解釈します |

**主な kintone の引き出し（アプリ）:**

| 引き出し | 番号 | 中身 |
|---|---|---|
| 案件（時効援用） | App 21 | 依頼者ごとの1件1枚のカルテ。進行状態（status）もここ |
| チャットログ | App 28 | LINE のやり取りの記録全部 |
| **承認キュー** | App 29 | **先生の承認待ちの返信下書き置き場。先生が日常的に見る引き出し** |
| **発送管理** | App 30 | **職務上請求・送付案内など、外へ出す書類の台帳。成果物、承認、発送、返送期限を管理** |
| **市区町村マスタ** | App 31 | **職務上請求の宛先住所・担当部署・手数料のマスタ** |
| **同封物ブロックマスタ** | App 32 | **送付案内に載せる同封物と案内文のマスタ** |
| 相談カード（相続） | App 26 | スキャンした相続相談カードの内容 |
| 戸籍謄本 | App 27 | スキャンした戸籍の読み取り結果（簡易版） |
| 不動産 | App 25 | 物件情報と固定資産税評価額 |
| 通帳 | （相続系） | コード上は /scan の対象です。ただし現時点で Railway 側の通帳用環境変数が設定済みか断定できないため、**本番投入は要確認**です |

**見えない仕組みを3つだけ**：
- **Webhook（ウェブフック）＝内線電話**。「締結が終わりました」「承認済になりました」「発送管理レコードが保存されました」と、外部サービスや kintone がうちの事務員に自動でかけてくる電話です。合言葉付きなので部外者はかけられません。
- **毎朝7時の見回り（日次死活監視）**。AIの頭脳、kintone の棚割り、書類ひな型、App30/32 の同封物同期を点検します。**異常があるときだけ**先生の LINE に報告が来ます。何も来ない朝＝正常です。
- **毎朝8時の返送期限監視**。App 30 で「返送待ち」になっているものの返送期限を見ます。期限超過や期限未設定があれば LINE に警報します。正常時は何も来ません。

## 2. 業務の流れ：いま実際に動いているもの

### 2.1 時効援用の LINE 相談から入金まで

1. 依頼者が LINE 友だち追加 → 受付窓口が挨拶し、債権者名・借入時期・最終返済日・裁判所書類の有無・信用情報などを聞き取ります。定型ヒアリングなので先生の承認は不要です。
2. 必要項目が揃うと、App 21 にカルテが作られます（status＝問い合わせ）。
3. ヒアリング後の会話は Claude が分類します。挨拶、一般的な流れ、必要書類、費用の定型案内などは自動返信します。法的判断、費用交渉、クレーム、裁判所書類、第三者、迷ったものは App 29 に入り、先生へ【承認依頼】LINE が届きます。
4. CloudSign の契約書作成・送信は現状手動です。依頼者が署名すると、CloudSign の Webhook で App 21 の status が自動で「受任」になり、先生へ【締結完了】LINE が届きます。
5. Stripe の決済リンク送付は現状手動です。決済完了 Webhook は動いていますが、既存案件への追記ではなく新規レコード作成になる既知の弱点があります。週次で二重カルテを見てください。

### 2.2 発送・受領ハブ（App 30）

App 30 は、事務所から外へ出す書類を「下書き → 承認待ち → 承認済 → 発送処理中 → 発送済 → 返送待ち/完了」で管理する台帳です。

**実際に動いているチャネル:**
- **送付案内**：App 32 の同封物マスタを使って、送付案内 docx と宛名ラベル PDF を作ります。
- **職務上請求**：App 31 の市区町村マスタを使って、発送準備チェックリスト、職務上請求書の重ね打ち PDF、レターパック往復ラベルを作ります。

**大事な安全設計:**
- Railway が勝手に「承認済」にはできません。**承認待ち → 承認済は先生の kintone 操作だけ**です。
- 二重実行防止のため、「実行済み」フラグで同じ発送を二度走らせないようにしています。
- 物理郵送は自動投函ではありません。成果物を印刷・封入・投函するのは人の作業です。

### 2.3 送付案内

App 30 で「チャネル＝送付案内」のレコードを作ると、次のものが自動でできます。

- 送付案内.docx
- 宛名ラベル.pdf（宛先面と返信用の事務所宛面）
- 返送が必要な同封物があるかどうかの記録

同封物の文章は App 32 から読みます。App 32 の「ブロックキー」が App 30 の「同封物選択」に無い場合や、無効な同封物を選ぶと、エラーになって LINE 警報が出ます。

### 2.4 職務上請求

App 30 で「チャネル＝職務上請求」のレコードを作ると、次のものが自動でできます。

- 発送準備チェックリスト.pdf
- 職務上請求書の重ね打ち PDF（様式第1号・様式第2号）
- レターパック往復ラベル.pdf

App 31 に市区町村の住所や手数料が未登録の場合は、エラーにはせず、**下書きのまま止めて「App 31 に登録してください」と警報**します。登録後、同じ App 30 レコードを下書きのまま再保存すると再処理されます。

ただし、職務上請求書の重ね打ち座標はコード上の初期値です。**実用紙での試し刷り・キャリブレーションはまだ必要**です。つまり「生成する仕組み」は実装済み、「実際の紙にぴったり合わせる最終調整」は未完了です。

### 2.5 スキャン・OCR

**Google Drive（GAS）経由:**
- 「相談カード」「戸籍謄本」「通帳」の3フォルダがコード上の対象です。
- GAS はイベント駆動ではなく、一定間隔でフォルダを見回るポーリング型です。
- 処理済みファイルは別フォルダへ移動せず、同じフォルダ内でファイル名の先頭に「[済]」が付きます。
- 2026-07-03 午前の調査で、GAS 側に try/catch、リトライ、警報、エラーファイル隔離は無いことが確認されています。恒久エラーのPDFが1つあると、その回の処理全体がそこで止まる可能性があります。
- 通帳フォルダはコード上は対応していますが、Railway 側の通帳用環境変数が本番で設定済みか断定できません。**通帳PDFの投入は要確認**です。

**事務所PC（OCR_inbox）経由:**
- 固定資産税のPDFを OCR_inbox に入れると、Vision OCR → Claude 抽出 → 不動産アプリへの評価額更新まで動きます。
- 成功時は「送信済み」、失敗時は「エラー」フォルダへ移動します。

## 3. オーナーの操作手順

### 3.1 毎日やること（平常時：合計5分以内）

1. **LINE を見る**。来ていなければ、やることはありません。
2. **【承認依頼】が来ていたら承認する**（App 29 は 3.3、App 30 は 3.4）。
3. 毎朝7時の見回り報告、毎朝8時の返送期限監視は「異常時のみ」届きます。**何も来ない＝健康**です。

### 3.2 週次でやること（10分）

1. **Stripe の入金と App 21 の突合**：決済があった週は、App 21 に二重カルテができていないか確認してください。
2. **Google Drive の整理（任意）**：処理済みファイルには先頭に「[済]」が付きます。「[済]」が付かないまま残っているPDFがあれば処理に失敗しています。
3. **OCR_inbox の「エラー」フォルダ確認**：中にPDFがあれば読み取り失敗です。
4. **App 30 の返送待ち一覧確認（任意）**：毎朝8時の警報が来ていなければ急ぎではありませんが、返送待ちの件数を見ると状況把握に便利です。

### 3.3 App 29（LINE返信）の承認

1. LINE に「【承認依頼】顧客: ○○ / カテゴリ: ○○ / 承認キューレコードNo: ○○」が届く
2. kintone を開き、**App 29（承認キュー）** の該当レコードを開く
3. **「AI下書き」欄を読む**。直したければこの欄を直接編集する（編集した文がそのまま送られます）
4. **「ステータス2」を「承認済」に変えて保存**
5. これだけで依頼者の LINE に送信され、「送信済み」が自動で yes になります（二重送信はされません）

### 3.4 App 30（送付案内）の操作手順

1. kintone で **App 30（発送管理）** を開き、新しいレコードを作る
2. 主な項目を入れる  
   - ユニット種別：時効援用  
   - チャネル：送付案内  
   - 方向：発送  
   - 顧客名表示用、件名、宛先名、宛先郵便番号、宛先住所  
   - 同封物選択：送る書類にチェック  
   - 発送ステータス：下書き  
   - 実行済み：no
3. 保存する。自動で送付案内 docx と宛名ラベル PDF が作られ、発送ステータスが **承認待ち** になります。
4. LINE に承認依頼が届いたら、App 30 の成果物を確認する。
5. 問題なければ **発送ステータスを「承認済」に変えて保存**する。
6. 事務員から「印刷・投函をお願いします」という LINE が届きます。成果物を印刷し、封入・投函してください。
7. 投函後、必要に応じて追跡番号を入れ、**発送ステータスを「発送済」に変えて保存**する。
8. 返送が必要な同封物がある場合は、自動で **返送待ち** になり、返送期限が入ります。不要な場合は完了へ進みます。

**エラー時の戻し方:**
- App 30 が **エラー** になった場合は、原因を直したうえで **「承認待ち」へ戻して先生が再確認する**運用にしてください。
- **「エラー → 下書き」は禁止遷移です。** 下書きに戻すと成果物の再生成が走り、確認済みの書類・添付・状態が食い違うおそれがあります。

### 3.5 App 30（職務上請求）の操作上の注意

- 市区町村の住所・担当部署・手数料は App 31 から引きます。未登録なら下書きのまま止まり、LINE で登録依頼が来ます。
- 登録後は、同じ App 30 レコードを下書きのまま再保存すると再処理されます。
- 職務上請求書の重ね打ちは、**実用紙でのキャリブレーション前提**です。初回運用前に試し刷りで位置合わせをしてください。

### 3.6 LINE指示Botの使い方（2026-07-04 稼働開始）

顧客用とは**別の**LINE公式アカウント（「大野法律事務所 業務指示」）に話しかけると、
スマホから業務の起票ができます。現在できるのは**送付案内と職務上請求の起票**です
（職務上請求は第1.5弾として 2026-07-04 稼働。対応業務は順次追加）。

**話しかけ方の例**:
- 「鈴木さんに送付案内を作って」
- 「田中さんに委任契約書を送って」（同封する書類名まで言うと、次の質問が省略されます）
- 「佐藤さんの戸籍謄本を新宿区に職務上請求して」（種別・通数・自治体・対象者などが
  足りなければ、Bot が1項目ずつ聞き返します）

**やりとりの流れ**:
1. 同じ名字の依頼者が複数いると番号の一覧が出ます → 数字で返信（例:「2」）
2. 同封する書類を聞かれたら番号で返信（複数は「1,2」のようにカンマ区切り）
3. 最後に**復唱**が来ます:
   「鈴木一郎さん（No.45・受任）に送付案内（委任契約書）を起票します。OK / キャンセル（30分有効）」
   → **「OK」で起票**、「キャンセル」で取り消し（言い直せます）
4. 起票されると kintone のリンク付きで返信が来ます。あとは通常どおり
   自動で書類が作られ、**承認依頼のLINE**が（従来の通知チャネルに）届きます

**いちばん大事なこと**: 指示BotへのOKは「**起票の承認**」であって、
「**発送の承認**」ではありません。書類を実際に発送してよいかの承認は、
**従来どおり kintone の発送管理（App 30）で「承認待ち→承認済」に変える操作**で行います。
LINEでOKしただけでは、外に何かが送られることは絶対にありません。

**うまくいかないとき**:
- 起票はされたのに書類ができない・止まっている → App 30 の該当レコードを開いて
  **「エラー詳細」欄**を見る（例:「同封物が選択されていません」）。直せる内容なら
  直して**下書きのまま再保存**すると自動でやり直します
- 復唱に返事をしないまま**30分**たつと期限切れになります。「OK」と送っても
  「期限切れです」と言われたら、**最初から指示をし直して**ください（途中から再開はできません）
- 復唱を放置して別の指示を送ると、前の確認は自動で取り消されます（安全側の仕様です）

### 3.7 警報 LINE が来たときの対応表

| 届いた LINE | 意味 | 先生のやること |
|---|---|---|
| 【承認依頼】 | App 29 の返信下書き、または App 30 の発送成果物が承認待ち | 該当レコードを開き、内容を確認して承認 |
| 【締結完了】 | 契約書が署名された | 対応不要（App 21 が「受任」になったか見るのは任意） |
| ✅固定資産税評価額の更新が完了しました | スキャンが不動産アプリに反映された | 対応不要 |
| 【発送管理: 印刷・投函をお願いします】 | App 30 の成果物作成と承認が済み、物理郵送待ち | 成果物を印刷・封入・投函し、発送済に変更 |
| 【返送期限超過】 | App 30 の返送待ちが期限を過ぎた、または期限未設定 | 追跡番号で配達状況を確認。書類が届いていれば受領処理を進める |
| 【発送管理: 対応依頼（エラーではありません）】 | App 31 の市区町村住所・手数料など、マスタ登録待ち | 指示されたマスタを登録し、App 30 を下書きのまま再保存 |
| 【発送管理: エラー】 | 起票内容やテンプレート等に問題があり処理失敗 | 原因を直し、エラーから承認待ちへ戻して再確認。エラー→下書きは禁止 |
| 【Claudeフォールバック発動】 | AIの頭脳を予備に切り替えて稼働継続中 | 急ぎ対応不要。落ち着いたら開発担当に「モデル更新して」と依頼 |
| 【Claude応答不能・要対応】 | AIが完全停止。依頼者には「確認中」と自動返信済み。App 29 に要対応レコードあり | App 29 を開き、AI下書き欄に先生が返信文を書いて「承認済」にする |
| 【日次死活監視: 異常検知】 | モデル、kintone の棚割り、ひな型、App30/32同期などの異常 | 内容に応じて元に戻す。意図的な変更なら開発担当に連絡 |

### 3.8 やってはいけないこと・注意

- ⚠ **Drive の「通帳」フォルダに PDF を入れる前に要確認**。コード上は対象ですが、現本番の安全性を断定できません。
- ⚠ **kintone のフィールド名・選択肢を変えない**。変えると翌朝警報＋機能停止の原因になります。
- ⚠ **App 32 のブロックキーを変えたら、App 30 の同封物選択も合わせる**。ずれると送付案内が作れません。
- ⚠ **書類ひな型（Word）を編集するときは `{{…}}` を消さない**。
- ⚠ **App 30 の「承認待ち → 承認済」は先生の操作だけ**です。自動で承認される仕組みは作っていません。
- ⚠ **App 30 の「エラー → 下書き」は禁止**です。復帰は「エラー → 承認待ち」として、成果物を再確認してください。

## 5. 用語集（五十音・ABC順）

| 用語 | 意味 |
|---|---|
| **API（エーピーアイ）** | プログラム同士の注文窓口。「kintone の API を呼ぶ」＝プログラムが kintone に読み書きの注文を出すこと |
| **App（アプリ）** | kintone の引き出し1つのこと。App 30 なら30番の引き出し |
| **CloudSign** | 電子契約サービス。紙とハンコの代わりにオンラインで契約書を締結する |
| **GAS（ガス）** | Google Apps Script。Google のサービスに付けられる自動処理。うちでは Drive のフォルダ監視係 |
| **kintone（キントーン）** | サイボウズ社のクラウド型データベース。うちの全記録の保管庫 |
| **OCR（オーシーアール）** | 画像やPDFから文字を読み取る技術。スキャンした紙をデータにする係 |
| **Railway（レイルウェイ）** | プログラムを24時間動かしてくれる借りサーバー。うちの事務員の住まい |
| **Stripe（ストライプ）** | クレジットカード決済サービス。うちのレジ係 |
| **Webhook（ウェブフック）** | 出来事が起きた瞬間に外部サービスからうちの事務員へかかってくる自動の内線電話 |
| **宛名ラベル** | レターパックやラベルシートに貼る宛先 PDF。App 30 の送付案内・職務上請求で自動生成します |
| **警報／死活監視** | システムが自分の健康を毎朝点検し、異常時だけ LINE で知らせる仕組み |
| **承認待ち** | 先生の確認を待っている状態。外へ出す前の最後の確認場所です |
| **送付案内** | 依頼者などへ「この書類を送ります」と添えるカバーレター。App 30 と App 32 から自動生成します |
| **チャネル** | App 30 の発送種別。送付案内、職務上請求、FAX、e内容証明などの種類 |
| **デプロイ** | 改修したプログラムを本番の Railway に配置し直すこと。30〜60秒 LINE 応答が遅れることがある |
| **トリアージ** | 依頼者メッセージの選別。自動返信してよいものと、先生の承認が要るものに分けること |
| **発送ステータス** | App 30 の進行状態。下書き、承認待ち、承認済、発送処理中、発送済、返送待ち、完了、エラーなど |
| **プレースホルダ** | 書類ひな型の差込枠。`{{日付}}` のような二重カッコ。ここに実データが流し込まれる |
| **返送期限監視** | App 30 の返送待ちを毎朝8時に見て、期限超過があれば LINE で知らせる仕組み |
| **モデル（Claude のモデル）** | AIの頭脳のバージョン。提供終了があるため予備を常備し、切替時は警報が来る |
| **リポジトリ** | プログラムと設計書一式の保管庫（GitHub 上）。全変更の履歴が残る |
| **レコード** | kintone の引き出しの中の1枚のカード。1案件・1メッセージ・1発送など |
