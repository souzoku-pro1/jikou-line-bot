# 第1章 8月スプリントの目的と性格

## 1.1 7月との対比

7月スプリント(7/1〜7/7)は「**判断の機械化**」だった——仕分けの判定・戸籍の読解・名寄せの同一人判定・法定相続順位の導出という、設計の泥沼を伴う難所。成果は相続本線の背骨(入口→仕分け→分割→読解+セカンドオピニオン→人物化→名寄せ→確認語彙→順位エンジン→関係図。PR #69〜#96・テスト650→1063)。

8月スプリントは「**型に流し込む・振り分ける**」層——確立済みの部品(仕分けエンジン・関所型・Bot語彙・テンプレート思想・順位エンジン・従前戸籍チェーン)の応用が大半。判断部品は既にあるので、テンプレと画面を被せる作業が中心。進捗速度は7月を上回る見込み。

## 1.2 8月が終わると何ができるようになるか(到達イメージ)

- 順位エンジンの判定から**職務上請求書が自動生成**され、**相続放棄の申述書・代理人目録・必要戸籍の請求書**まで一気通貫で下書きされる(相続放棄バーティカルの中核=アメーバモデルの2本目の柱)
- App 34×App 35の台帳から**遺産分割協議書・用途別財産目録(協議書添付/家裁/税理士/顧客説明)・委任契約書・請求書領収書**が自動起案される(全て下書き止まり・人の決裁必須)
- **e内容証明・FAX・CloudSign**の対外送信が「文面自動生成→人の承認→送信」の半自動になる(e内容証明は時効援用本業にも直結——相続外への波及効果が最大)
- **Q系質問Bot**(読み取り専用・出典明示)に「熊澤案件の相続人は?」と聞けばレコード番号付きで答えが返る
- **PWA(自分専用の業務アプリ)**がiPhoneのホーム画面から開き、Q&A一覧・案件ダッシュボード・仕分けUIが使える。通知はLINE・作業はPWAの役割分担

## 1.3 全部Fableの裁定(確定・理由込み)

モデル使い分けによる節約案は棄却し、**司令塔的な開発作業は全部Fable**で確定。理由:

1. 経済面: 差額は最大でも月10〜20万円。判断力の劣るモデルで手戻り・監視・やり直しに大野自身の時間が食われる方が高くつく(監督者の時給が高いほど「安いモデル+人間の監督強化」は偽の節約)
2. 安全面(より本質的): 8月の作業対象は本番のkintone台帳・顧客Driveフォルダ・対外送信の関所であり、事故の被害が非対称に大きい。「pushは人間のみ」「問題検知は停止して報告」「外部効果は承認必須」を一度も踏み外さずに守り切る確度はモデルの格で変わる(7月のインシデント群の教訓)
3. 既存の分業(記事執筆のGemini研究・チャッピー校閲)はそのまま。削減はモデル格下げでなく運用側で取る(キャッシュ・max_tokens適正化・冒頭コンテキストを積まない)

- 何を作るか: テンプレ複数(戸籍謄本/除籍/改製原/住民票等)+請求先自治体・請求理由・対象の自動判別

- 既存資産との接続: M1職務上請求(7/4完成・App 31宛先引き当て・小為替計算・2様式重ね打ち)が既に稼働している。8月に作るのは「**何を請求すべきかの判定→起票の自動化**」であり、起票後の生成・発送は既存M1がそのまま担う
- 前提: P1(テンプレ実物)・P7(熊澤案件の従前戸籍請求=実機素材)

### 項目2: 相続放棄手続きの半自動化【確度高・見積6〜8h・アメーバモデル2本目の柱】

- 何を作るか: 申述書の自動作成・代理人目録の自動作成・**被相続人と申述人との関係から収集すべき戸籍を判別→職務上請求書を自動作成**
- なぜ簡単か: R4-3(順位エンジン)がそのまま心臓部。「第3順位の申述人なら父母の出生までの戸籍が要る」はF5判定そのもの。7月資産の最大の応用先
- 法務の正本: **H系列(docs/souzoku-houki/・監修5層)**。特に③続柄別戸籍マトリクス(最優先=被相続人の住民票除票または戸籍の附票)・①期日二本立て(法定満了日/社内締切日)・料金体系(標準型77,000円/超過型88,000円〜・7/4弁護士確定)を変更しないこと

## 第2群: 対外送信の半自動化(承認ゲート必須・関所型の横展開)

**共通原則(不可侵)**: 対外効果があるため人の承認なしに送信される経路を絶対に作らない。関所型(復唱→OK)+PWA承認フォームが承認の受け皿。LINEのOKは起票承認であって対外送信の承認ではない、の7/4確定判断は画面が変わっても維持。

### 項目7: CloudSign送信の半自動化【確度中(外部依存)・3〜5h】

- 委任契約書等→メールアドレス紐づけ+送信文面の自動生成+**人の承認で送信**
- 分岐: P5(契約プランのAPI利用可否)の結果次第。API可→承認後の送信まで自動/API不可→「文面生成→人がCloudSign画面で送信」に格下げ(それでも文面作成の手間は消えるので価値はゼロでない)

### 項目8: 電子内容証明(e内容証明)の半自動化【確度中・6〜8h・波及効果最大】

- Web APIがないため「文面自動生成→人が承認→**CU(Computer Use)がアップロード操作**」の型
- **時効援用業務(本業の柱)にも直結**——相続外への波及効果が最大の項目。時効援用通知の本文テンプレは大野の実務書面が正本(AI創作禁止・7/4の設計検収で確定済みの制約)

- 過去の設計資産: T5系(7/4ブリーフ)の「検証済みCSV+本文docx生成までが自動化境界・差込差出し最大100通/回」。【人・事前準備】日本郵便公式の差込差出し用雛形ZIPのダウンロード(未実施なら)

## 項目12(全面改訂): PWA業務アプリの開発【14〜24h・約2日】

**構想書の「モバイルアプリ化(設計調査から)」はこの内容に全面改訂された(7/8確定)。構想書の記載より本節が優先。**

### 12.1 裁定の経緯(なぜネイティブアプリではなくPWAか)

1. 大野の要件: 「公開するつもりはない。iPhoneの中にアプリのような形ですぐ開けるようにしたい」——この要件はPWA(manifest+Service Worker+Safariの「ホーム画面に追加」)で100%満たせる。アイコンタップ→全画面起動の体験はネイティブと見分けがつかない
2. ネイティブが持ち込む固定費: 配布(App Store審査またはTestFlight 90日更新、自己署名なら7日/Developer Program加入で1年ごとの再署名)・OSアップデート追従・通知基盤(APNs/FCM)の自前実装・認証の作り直し——**「LINEが無料提供しているインフラ一式の自前化」でありアメーバモデル(共有インフラの上に載せる)と逆行**
3. 大野が挙げた便益3つ(下記12.2)は全て「画面の問題」であり、ネイティブ固有機能(カメラ連携・バックグラウンド処理)を一つも要求していない→PWAで全部作れる
4. PWAは配布がないため**機能追加=Railwayへのデプロイだけ**。次にアイコンを開いたときには新機能が生えている
5. LINE資産は無駄にならない: LINE仕分けシステムの実体は「LINE部分1割・裏側9割」。仕分けエンジン・回送ロジック・冪等キー・関所語彙・kintone起票はPWAがそのまま呼ぶ共通API。**役割分担=通知が来る場所はLINE・作業する場所はPWA**(「仕分け3件溜まってます」の通知はLINEに飛び、タップするとPWAの仕分け画面が開く、が完成形)。外出先で1件だけ捌く最軽量経路としてもLINE語彙は残す

### 12.2 第1版の機能3つ(確定)

1. **Q&A一覧**【読み取り系・2〜4h】: Q系Botの回答を生成のたびレコード保存し、一覧→タップで回答+出典表示。チャットUIではなく「Q&A台帳のビュー」。LINEの流れる形式と共存(同じレコードを見るだけ)。Q系要件3(出典明示)・4(未確定注記)がそのまま画面仕様
2. **案件ダッシュボード**【読み取り系・2〜4h】: 顧客を選ぶ→相続人一覧(App 34)・財産目録(App 35)・進行状態・直近書類リンクが1画面に。「今この案件はどうなっているか」を10秒で見る画面。**データを複製せず既存台帳への読み取り専用ビュー**として作る(思想=「倉庫はkintone/Drive、アプリはその中から人が確認するために必要な情報を運ぶトラック」——大野の言葉)
3. **仕分けUI**【書き込み系・6〜10h・価値最大】: スキャンPDFのサムネイル+doc_type候補ボタン+顧客候補ボタンをタップで確定。名寄せ未確定の人間確認(機械は確定しない原則)も同じ画面型で捌く。LINEの文字応答による仕分けは長期的に持たない、という大野の見立てへの回答。実機のスキャン20件を大野が捌いて候補の並び順・タップ数の不満を潰す反復が品質を決める(見積りに実機日を含む)

### 12.3 承認フォーム(第2群の出口画面・独立項目ではない)

e内容証明・FAX・CloudSign・書類送付案内の「文面の個別部分だけ編集→承認ボタン」画面。**関所型のフォーム化**であり、項目7〜9の各実装日にそれぞれの出口として同時に作る(1つ目4〜6h・2つ目以降は型の使い回しで各1〜2h)。

### 12.4 アーキテクチャ(確定)

- 既存Railway FastAPIの上に載せる**画面1枚**。LINE Botとアプリは同じAPIを叩く2つの入口。新システムではない
- 骨格(機能数に関係なく1回だけ払う固定費・4〜6h): PWA化(manifest/Service Worker)・認証・ユーザー/ロール/操作ログのテーブル・前段の壁・画面枠

### 12.5 セキュリティ設計(確定・守秘義務対象データのため必須)

1. **認証=パスキー(WebAuthn)**: iPhoneのFace ID/Touch IDそのものでログイン。秘密鍵はSecure Enclaveから出ず「盗まれる文字列」が存在しない。パスワード方式より強い。FastAPI用WebAuthnライブラリで実装
2. **セッション**: トークンに有効期限(例12時間)。**書き込み系(仕分け確定・承認)は操作直前に再度Face IDを要求**する二段構え(承認ボタン=生体認証・関所型と相性が良い)
3. **ネットワーク層(実は最重要)**: 認証の手前に壁。(a)Cloudflare Access等を前段に置く または (b)URL推測不能化+レート制限。最低でもどちらかは入れる。全通信HTTPS
4. **データ層**: アプリにデータを持たせない(トラック思想がそのままセキュリティ)。kintoneのAPIキーはサーバー側のみ。iPhone紛失時はサーバー側でセッション失効1操作で締め出せる
5. 長時間放置で自動ログアウト

### 12.6 複数人利用前提の器(第1版から・確定)

大野はゆくゆく社員数名で使う意向。後付けは認証・ログ・画面の三層を掘り返すことになるため、以下3点を第1版の骨格に含める(実装コストは軽い):

1. ユーザーテーブル+**ロール列**(閲覧/仕分け/承認)——1行目は大野
2. **全確定操作にuser_idとタイムスタンプを記録**(操作ログテーブル。守秘義務・懲戒リスクへの防御記録。中身が当面「全部大野」でも器を先に作る)
3. 承認系エンドポイントにロール検査

権限の弁護士留保(法務判断・確定): **対外効果のある承認(e内容証明・FAX・CloudSign送信)は弁護士=大野に留保**。事務員は仕分けまで、という線引きを権限設計に刻む(非弁リスクと職責の観点)。名寄せ確定を誰まで降ろすかは運用開始後に裁定。案件単位のアクセス制御(利益相反の壁等)は第1版不要だが、データ設計に「案件×ユーザーの許可」を表現できる余地だけ残す。

社員追加の運用: パスキー登録+ロール付与のみ。ネットワーク層の壁はメールアドレス単位許可(Cloudflare Access等)を選んでおくと複数人管理が楽。

### 12.7 UXの規律(確定)

- 1人(少人数)利用の専用機の強み=その利用者に100%最適化できる。既定値・ボタン並び・確認の省略で徹底的にタップ数を削る。不満が出たらその日に直す
- ただし**使いやすさの9割は画面でなく裏の判定精度**(仕分け画面が快適なのはdoc_type候補が最初からほぼ正しいから)——7月の判断の機械化がここで換金される
- **速くするところと、わざと速くしないところを分ける**: 名寄せの人間確認・対外送信の承認には摩擦をあえて残す(例: 原本サムネイルを一度表示してからでないと確定ボタンが押せない)。関所型の思想を画面にも貫く。確認が流れ作業になる誘惑への構造的な対抗

### 12.8 機能追加の将来(参考)

完成形は存在しない——業務が増えるたびタイルが増える育つダッシュボード。9月以降の新バーティカル(補助金等)もAPIができれば1タイル追加。最初に決め切るべきは3つだけ: ユーザー/ロール/ログのテーブル設計・認証方式・URL構造(ここを固めれば機能は永遠に積み増せる)。
