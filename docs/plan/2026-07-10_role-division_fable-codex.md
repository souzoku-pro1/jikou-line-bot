# 1. 最終裁定

8月スプリントは並列実装しない。

- Fable司令塔が唯一の指揮系統となる
- PC-A／Claude Code Fableが全実装を単線で行う
- Codexは各日の確定commitを非同期に読み取りレビューする
- Codexはコードを編集、commit、push、mergeしない
- Codexの所見は指示ではなく、Fable司令塔への検討材料である
- push、本番変更、資格情報投入、実機送信、法務判断、最終承認は大野だけが行う

## 1.1 並列実装を採用しない理由

1. 7月は単線でPR #69〜#96の28PRを処理できており、PC-Aの実装速度は既に十分高い。
2. 実際の律速は、大野による実機確認、push、法務判断、P1〜P12の素材供給、外部サービスの準備である。
3. 2実装レーンにすると、指示票の二重発行、API契約凍結、BASE_SHA同期、取込、conflict裁定が必要になる。
4. 8月の対象は共有FastAPI、kintone、Drive、認証、承認、外部送信に集中しており、独立性より結合度が高い。
5. 1週間スプリント中に新しい複線運用を導入すること自体が、新たな検証対象と認知負荷を増やす。
6. Codexの価値は、第2実装者としてではなく、異なるモデルによる独立検査として使う方が大きい。

## 1.2 時間目標【第17章210時間版へ置換済み】

- 計画時間は長期設計正本の基準210時間、G0後190〜230時間とする。
- 70時間／96時間完遂をKPIにしない。
- 予定より早く終わった場合は上振れと扱い、検収時間を削らない。
- Codexレビューは原則としてPC-Aの実装終了後に非同期で行い、PC-Aの実装時間と重ねる。
- Codex指摘への修正時間は、不要な調整コストではなく、潜在不具合を本番前に除くための必要時間として扱う。

- Codexの「推奨」「次にすべきこと」は指示ではない。
- 大野の最新指示が現在タスクの追加か上書きかをFable司令塔が明示してから再開する。

# 3. 不可侵の運用規律

以下は速度のためにも省略しない。

1. git pushはFable司令塔、PC-A、Codex、CUのいずれも実行しない。pushは大野のみ。
2. mainへの直接作業、force push、履歴破壊、無断rebaseを禁止する。
3. 本番変更、env変更、kintone本番スキーマ変更、外部送信は大野の明示指示がある場合だけ行う。
4. 機械は「確認済み」「承認済み」「名寄せ確定」へ自動遷移させない。
5. 対外効果のある処理は、文面生成、承認、実行を別レイヤーに分離する。
6. 実機テスト中は新規実装を積まない。当該経路のログ確認・不具合修正だけを行う。
7. 問題を検知したら回避して進まず、問題・影響・安全な次手を報告する。
8. 弁護士確定事項、料金、FAQ、purpose文言、凍結ケース表をAIが創作・改変しない。
9. 資格情報、APIキー、token、顧客の機微情報をチャット、commit、通常ログ、例外ログへ出さない。
10. テストを通すために既存テストを削除、skip、期待値緩和してはならない。
11. 不足する実物テンプレートや外部仕様を推測して作らない。
12. 完了報告末尾の提案は次の指示ではない。
13. Codexレビューを理由にPC-Aの実装範囲を自動拡張しない。

# 5. 単線実装の基本サイクル

各日、次の順序を固定する。

1. Fable司令塔がその日のtask_idを一つ発行
2. PC-Aが正本・base SHA・既存テストを確認
3. PC-Aが実装し、local commit
4. PC-Aが必須テストを実行
5. Codexが確定commitを読取専用でレビュー
6. Fable司令塔がCodex所見を採用／棄却／保留に裁定
7. 高リスク所見はPC-Aが修正し、新SHAをCodexが再レビュー
8. 大野が必要なpush・実物・実機確認を行う
9. 実機中は新規実装を停止
10. 実機修正で新commitが生じた場合、その差分を再レビュー対象にする
11. 当日成果をCOMPLETE／PARTIAL／BLOCKEDで確定
12. 日次work-logを一つに統合

Codexレビューが終わる前に、同じ高リスク経路を本番反映しない。特に、PWA公開、実データの仕分け確定、外部テスト送信、Driveパイロットは、実装commit確定後・実機実行前にCodexの事前レビューを挟む。低リスクの独立タスクについては、Fable司令塔が影響範囲を確認したうえで翌日の調査まで進められるが、レビュー対象commitへ追加変更を重ねない。

# 7. Codex独立レビューの設計

## 7.1 Codexへ渡す入力

各レビューには、次だけを渡す。

- REVIEW_ID
- REVIEW_TARGET_SHA
- BASE_SHA
- 対象branch
- 当日のtask_id
- 関係する正本docs
- 変更ファイル一覧
- diff
- PC-Aのテストcommandと実出力
- 人の実機結果
- 本番・外部効果の有無
- 重点検査項目

顧客実データ、token、env実値、secretは渡さない。必要な再現は匿名fixtureまたはrecord IDのない構造例で行う。

## 7.2 Codexの権限

Codexは次を行える。

- repo、指定commit、diff、docsの読取り
- 既存テストの実行
- test collection、失敗、skipの確認
- 静的なsource search
- 権限境界、禁止経路、idempotency、情報漏えいの分析
- 欠けているtest caseの提案
- 再現手順の提案

既存テストを実行できるのは、次を全て満たす場合だけとする。

- 本番資格情報を読み込まない
- kintone、Drive、LINE、CloudSign、InterFAX、日本郵便等へ通信しない
- mock、fixture、使い捨てtest DBだけを使う
- source管理対象を書き換えない
- 実行前後でgit statusに差分が生じない

保証できないテストは実行せず、実行候補と確認目的だけをFable司令塔へ返す。

Codexは次を行わない。

- source、test、docs、設定ファイルの編集
- snapshot更新、golden file更新
- commit、branch作成、push、merge、rebase
- package追加
- DB・kintone・Driveへの書込み
- 外部APIの送信系endpoint実行
- 本番資格情報の要求・読取り
- PC-AやCUへの直接指示

テスト実行がcache等を生成する場合は、source管理対象を変更しないことを確認する。test更新flagを使用しない。

## 7.3 レビュー重大度

| 重大度 | 定義 | 扱い |
|---|---|---|
| BLOCKER | 誤送信、情報漏えい、承認省略、法務正本違反、データ破壊、本番事故の現実的経路 | 当該経路を停止。Fableが修正taskを最優先起票 |
| HIGH | 既存回帰、権限不足、二重処理、誤判定、復旧不能につながる具体的欠陥 | 原則として次の関連実装前に修正 |
| MEDIUM | 例外処理・test不足・運用上の不整合 | 当日または8日目に回収 |
| LOW | 可読性、将来改善、軽微な保守性 | 8月スコープ外候補。自動起票しない |

「危ないかもしれない」だけではBLOCKERにしない。各指摘には、対象ファイル・関数・条件・想定結果・実際の結果・影響を付ける。

## 7.5 Fable司令塔による裁定

Fable司令塔はCodex所見を次のどれかに分類する。

- ACCEPT: PC-Aへ新task_idで修正指示
- REJECT: 根拠をwork-logへ記録
- DEFER: 9月候補または8日目候補
- NEEDS_HUMAN: 法務・実物・本番判断を大野へ返す

Codex所見をそのままPC-Aへ転送して「全部直して」と指示してはならない。現在の正本、スコープ、外部影響と突合する。

# 8. 日別レビュー観点

## 8.1 1日目: PWA骨格・Q系

- Railway直URLから前段認証を迂回できないか
- WebAuthnのchallenge、userVerification、期限、replay防止
- session失効、長時間放置logout
- role検査が画面だけでなくserver側にあるか
- Service Workerが顧客dataやAPI応答をcacheしていないか
- Q系がread-only credentialだけを使うか
- 案件横断取得やOCR prompt injectionの経路
- LINEへ機微な全文を残していないか

## 8.2 2日目: 仕分けUI

- 原本表示前に確定できないか
- 名寄せ、確認済みへ自動遷移しないか
- user_id、時刻、case_id、対象版が記録されるか
- 二重tap・reload・timeoutで二重起票しないか
- 候補0件、複数、低確信度の停止経路
- 別案件のPDFや候補が混ざらないか

## 8.3 3日目: 職務上請求・相続放棄

- koseki_chain・順位engineを再実装して不一致を作っていないか
- 続柄別必要戸籍がH系列と一致するか
- 住民票除票／戸籍附票の優先
- 期日・料金・purpose正本文言の改変
- 再実行による二重起票
- 全成果物が下書き止まりか

## 8.4 4・5日目: 帳票・受任

# 9. 対外送信の共通安全設計

CloudSign、FAX、e内容証明は、サービスごとに独自の承認を作らず、共通状態機械を通す。

## 9.1 状態

1. DRAFT
2. PENDING_APPROVAL
3. APPROVED
4. SENDING
5. SENT
6. FAILED
7. UNKNOWN_REQUIRES_HUMAN
8. CANCELLED

UNKNOWN_REQUIRES_HUMANから自動再送してはならない。

## 9.2 承認対象

承認は、次の固定スナップショットへ結び付ける。

- 案件ID
- 宛先
- 本文
- 添付ファイル
- 送信手段
- 版番号
- 作成時刻
- 上記全体のhash

承認後に内容が変わった場合、APPROVEDを失効させ、再承認を要求する。

## 9.3 WebAuthnと監査

- userVerification必須
- 書込み・承認直前の新しいassertion
- challengeは短時間・一回限り
- challengeを対象hashへ結び付ける
- session一括失効手段
- 操作ログにuser_id、case_id、role、対象版、hash、宛先、外部受付番号、結果、相関ID
- 本文全文、token、戸籍情報を通常ログへ残さない

## 9.4 資格情報

- Q系読取、仕分け書込、承認、送信実行、サービス別、開発・本番別に分離
- ブラウザへ送信資格情報を返さない
- Codexへ本番資格情報を与えない
- Webhookの署名、時刻、replay検証
- test環境の許可宛先listと上限

## 9.5 e内容証明

CUはアップロードと最終確認画面の表示までとする。宛先、本文、料金を大野が確認し、最後の送信操作は人が行う。画面差異、session切れ、表示不一致があれば停止し、自己判断で再試行しない。

# 10. Git・commit・push

## 10.1 PC-A

- 既存運用どおりfeature branchで作業する。
- 開始時にBASE_SHA、branch、git statusを記録する。
- dirty worktreeがあれば既存変更の所有者が判明するまで停止する。
- 1 task_idごとに意味のあるlocal commitを作る。
- test結果と変更ファイルを完了報告へ記載する。
- pushは行わず、大野へ返す。
- mainが進んでも勝手にrebase、amend、base変更しない。

- source管理対象を変更しない。
- review用branch、commit、PRを作らない。
- separate PCから読むためfeature branchのpushが必要な場合、そのpushは大野が行う。

# 17. 結論

8月スプリントで増やすべきものは実装レーンではなく、独立検査である。

- 実装はPC-A一本
- 指揮はFable一人
- 本番権限は大野一人
- Codexは読取専用レビュー

これにより、7月に実証された単線の速度と安全な運用語彙を維持しながら、Fableと同じ盲点を持たない異モデルの検査を追加できる。工程は210時間版へ一本化し、本書からは役割分担、review独立性、禁止経路検査、回帰、security、停止条件だけを使用する。
