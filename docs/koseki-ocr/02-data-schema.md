# 02. 構造化スキーマと kintone 設計

「人物」「身分事項」「戸籍間の連続性」を分離して持つ。
AI 出力（未確認）と確定データ（人の確認済み）を**別の場所**に置くのが要諦
（未確認データが下流に流れない構造・README 共通原則1）。

## 1. ★App 44 戸籍（1レコード = 1戸籍。スキャン受領の着地点）

| フィールドコード | 型 | 用途 |
|---|---|---|
| 案件参照4点（ユニット種別/案件アプリID/案件レコードID/被相続人名表示用） | | ハブ共通方式 |
| `本籍` / `筆頭者`（戸主） | SINGLE_LINE_TEXT | 戸籍の識別子（原文表記） |
| `戸籍種別` | DROP_DOWN | 現行 / 改製原（平成） / 改製原（昭和） / 除籍 / 不明 |
| `編製日` / `消除日` | SINGLE_LINE_TEXT | 連続性の判定材料（この戸籍がカバーする期間）。**和暦原文のまま保持**（例: 昭和32年4月1日。DATE型だと原文が失われるため文字列。構造化された日付は 読解JSON 側に持ち、機械比較が必要な処理は読解JSON由来の値で行う。2026-07-05 検収裁定・実機 App 33 と一致） |
| `編製事由` | SINGLE_LINE_TEXT | 転籍・改製・婚姻等（原文） |
| `従前戸籍_本籍` / `従前戸籍_筆頭者` | SINGLE_LINE_TEXT | **連鎖請求の入力**（01 §4） |
| `新戸籍_本籍` | SINGLE_LINE_TEXT | 前方向の連続性（検算用） |
| `原本PDF` / `ページ画像` | FILE | 確認 UI の並置表示用 |
| `Drive_fileId` | SINGLE_LINE_TEXT | 冪等（M5 既存設計） |
| `読解JSON` | MULTI_LINE_TEXT | AI 出力の生データ（フィールド別 confidence 込み・§3 スキーマ） |
| `読解状態` | DROP_DOWN | 未読解 / AI読解済 / **確認済** / 要再読解 |
| `確認者` / `確認日時` | SINGLE_LINE_TEXT / DATETIME | 監査痕跡 |
| `様式確信度` / `全体確信度` | NUMBER | 品質管理（01 §5） |

## 2. ★App 43 人物（1レコード = 1案件の1人物。**確認済データのみ**）

| フィールドコード | 型 | 用途 |
|---|---|---|
| 案件参照4点 | | |

| `生年月日` / `死亡日` | DATE | 和暦原文は身分事項側に保持 |
| `性別` | DROP_DOWN | 男 / 女 / 不明（旧戸籍の続柄解釈に使用） |
| `父人物ID` / `母人物ID` | SINGLE_LINE_TEXT | **親子エッジ**（関係図・相続人導出の骨格） |

## 3. 読解 JSON スキーマ（App 44 `読解JSON`・AI 出力の形式）

```json
{
  "様式": "改製原（昭和）", "様式confidence": 0.9,
  "戸籍": {"本籍": "...", "筆頭者": "...", "編製日": "...", "編製事由": "...",
           "従前戸籍": {"本籍": "...", "筆頭者": "..."}, "confidence": {...}},
  "人物": [
    {"氏名": "山田太郎", "続柄": "長男", "生年月日": "昭和10年3月15日",
     "除籍済み": true, "除籍事由": "婚姻",
     "身分事項": [
       {"種別": "出生", "日付": "昭和10年3月15日", "confidence": 0.95},
       {"種別": "婚姻", "日付": "...", "相手方": "佐藤花子", "confidence": 0.7},
       {"種別": "死亡", "日付": "...", "confidence": 0.9}
     ],
     "confidence": {"氏名": 0.6, "生年月日": 0.9}}
  ]
}
```

- 身分事項の `種別` 許容値: 出生 / 婚姻 / 離婚 / 養子縁組 / 離縁 / 認知 / 死亡 / 転籍 /
  入籍 / 除籍 / 改製 / その他（その他は原文を備考に保持）
- 日付は**和暦原文のまま**保持し、西暦変換（DATE 型への転記）は確認 UI での確定時に実施
  （変換誤りも人の確認対象に含める）

## 4. 名寄せ（戸籍間の同一人物統合）

```
確認済の戸籍が増えるたびに:
 1. 機械が候補提示: 氏名_正字＋生年月日の一致（±続柄の整合）で既存人物との統合候補を提示
 2. 人が確定: 確認 UI 上で「同一人物として統合 / 別人として新規」を選択 → 名寄せ確定=yes
 3. 統合時: 登場戸籍 SUBTABLE に行追加・身分事項をマージ（重複行は記載元戸籍IDで区別）
```

- 名寄せを機械確定しない理由: 同姓同名・改名・旧字体化けによる誤統合は相続人確定を
  直接誤らせる（安全側 = 人の1クリックを挟む）

## 5. UNIT_CONFIG・環境変数

- App 43/44 はユニット非依存（相続放棄・相続一般の両方から案件参照4点で使う）
- 環境変数: `APP_KOSEKI_PERSON` / `TOKEN_KOSEKI_PERSON`（App 43）、
  `APP_KOSEKI_BOOK` / `TOKEN_KOSEKI_BOOK`（App 44）。作成直後に EXPECTED_KINTONE_SCHEMA 登録（既存規約）
