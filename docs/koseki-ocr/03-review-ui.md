# 03. 確認 UI（AI 読解結果の人手確認・修正）

半自動設計の中核。「PDF 画像と抽出結果を並べて確認・修正」する作業効率が
本ライン全体のスループットを決める。

## 1. 方式比較

| 観点 | (a) kintone 標準画面 | (b) 簡易 Web ビューア（Railway 上・推奨） | (c) その他（kintone カスタマイズ JS / スプレッドシート） |
|---|---|---|---|
| 並置表示（画像↔入力欄） | ✗ 添付 PDF は別タブ表示。SUBTABLE 編集と画像を同時に見られない。**校正作業に致命的** | ○ 左: ページ画像（拡大・回転）／右: 抽出フィールド（confidence 低は赤強調） | JS カスタマイズなら△可能だが kintone 画面 API の制約と保守負荷 |
| 修正操作 | △ JSON 手編集 or SUBTABLE 行編集（和暦・続柄の選択肢補助なし） | ○ フィールド型に応じた入力補助（和暦→西暦の自動変換プレビュー・続柄セレクト・除籍トグル） | △ |
| 開発コスト | ◎ ゼロ | △ 中（1画面・1エンドポイント＋静的 HTML/JS。§2 で最小化） | ✗ kintone JS は別スキル・デプロイ経路が増える |
| 認証・個人情報 | ◎ kintone のアクセス制御そのまま | △ 追加の認証設計が必要（§3） | kintone 内なら◎ |
| 死活監視・障害点 | ◎ 増えない | △ Railway 内なので既存監視の枠内（新規サービスは増やさない） | — |
| 名寄せ操作（02 §4） | ✗ 手作業でレコード間コピー | ○ 統合候補の並置比較＋1クリック統合 | △ |

**推奨: (b) 簡易 Web ビューア。**
戸籍読解は「画像と突き合わせて直す」作業が本質で、(a) では確認1通あたりの時間が
数倍かかり半自動設計が破綻する。開発コストは §2 の割り切りで1タスク規模に抑える。
**ただし v0 運用は (a) で開始できる**（App 44 に JSON・画像が揃っているため、
ビューア完成前でも読解 v2 の価値検証は可能 — R 系列の順序に反映・07）。

## 2. ビューアの最小設計（作り込まない割り切り）

```
GET  /review?token=<合言葉>&record=<App44レコードID>   … 確認画面（1 URL・1画面）
POST /review/save?token=...                            … 修正結果の保存
```

- **SPA フレームワークは使わない**。素の HTML + 最小限の JS（fetch のみ）を
  FastAPI の Jinja2 なし・文字列テンプレートで返す（既存リポジトリに前端ビルドを持ち込まない）
- 画像は App 44 添付のページ画像を kintone API 経由で中継表示（hub/kintone.download_file）
- 保存時の動作: 読解JSON を修正版で上書き＋読解状態=確認済＋確認者/日時 →
  BackgroundTasks で人物への反映（02 §4 名寄せ候補提示）
- 確認待ちの入口: 弁護士/事務員への LINE 通知にビューア URL を添付
  （「戸籍3通の確認待ちがあります」日次まとめ）
- 名寄せ画面: 同一画面内の第2タブ（統合候補の2人物を並置・「統合/別人」ボタンのみ）

## 3. 認証（合言葉 URL 方式の強化）

- 既存 Webhook の合言葉方式を人間用に強化: `REVIEW_UI_TOKEN`（長いランダム値）＋
  **有効期限付きの署名 URL**（レコードID+期限を HMAC 署名。LINE 通知に添付する URL は
  7日で失効）。恒久 URL を LINE に残さない
- Railway の同一サービス内（新規公開面は /review の2ルートのみ）。
  失敗時 404（存在しないフリ・既存流儀）。アクセスログを記録
- 将来 kintone の OAuth 連携等が必要になれば差し替え（認証層は関数1つに分離しておく）

## 4. 確認作業の設計（人の動線）

1. LINE 通知 → URL タップ → 画像と抽出結果の並置画面
2. confidence 低（赤）フィールドから順に確認・修正（和暦→西暦変換のプレビュー付き）
3. 戸籍分割（1PDF 複数戸籍）の妥当性確認（分割位置の修正 UI は v1 では作らず、
   誤分割は「要再読解」に落として人が kintone でページ範囲を指定 → 再読解）
4. 保存 → 次の確認待ちレコードへ自動遷移（連続処理）

- 目標: 現行戸籍1通 2分以内・手書き除籍1通 10分以内（受け入れ検査 R10 の測定項目）

## 5. テスト観点

- 署名 URL: 期限切れ・改竄・レコード不存在で 404
- 保存: 読解状態遷移・確認者記録・BackgroundTasks 起動・kintone 書き込み内容
- 画像中継: 添付なし・大容量のハンドリング
- （UI の見た目は人の受け入れ確認・自動テスト対象外と明記）
