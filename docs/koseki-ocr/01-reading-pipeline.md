# 01. 戸籍読解パイプライン

現行方式（Vision OCR テキスト → Claude 構造化）を土台に、戸籍特有の課題に対処する
2段階読解＋確信度付き出力へ拡張する。

## 1. パイプライン全体

```
[受領] M5 受信箱（/scan/v2・T4 系）で doc_type=戸籍謄本系 に分類
   ├─ 冪等: Drive_fileId（既存設計）
   └─ 原本 PDF は App 44（戸籍）に必ず添付
[読解 v2]（本設計の中核）
 1. ページ画像化: PDF をページ単位で扱う（Vision files:annotate はページ別テキストを
    返す＝既存実装のまま。加えてページを PNG 化して保存 — 確認 UI の並置表示用）
 2. 様式判定（Claude・1回目）: 現行戸籍（横書き・コンピュータ化後）/ 改製原戸籍（縦書き・
    平成改製前）/ 除籍 / 手書き（昭和改製前）を判定し、確信度を付す
 3. 構造化抽出（Claude・2回目）: 様式別プロンプトで 02 のスキーマ（JSON）に抽出。
    **フィールドごとに confidence を出させる**（tool use スキーマで強制）
 4. 旧字体・異体字の正規化: 正規化テーブル（辻/邊/髙/𠮷 等）で検索用の正字を併記。
    **表示用は原文どおり保持**（一覧図・関係図は戸籍の記載に忠実であるべきため、
    正規化は名寄せ・検索にだけ使う）
 5. App 44 に保存: 読解JSON（未確認）・様式・全体確信度・ページ画像 → 読解状態=AI読解済
[確認]（人・03 の UI）: PDF/画像と抽出結果を並置して修正 → 読解状態=確認済
[反映] 確認済データから人物・身分事項（App 43）へ名寄せ・登録（02 §4）
[連鎖] 従前戸籍が検出されていれば次請求の提案（§4）
```

## 2. 戸籍特有の課題への対処方針

| 課題 | 対処 |
|---|---|
| **旧字体・異体字** | 正規化テーブル（データとして保持・追記可能）＋「原文保持・正字併記」の2欄方式（§1-4）。OCR が正字に化けた場合に備え、確認 UI で氏名欄を最優先の確認対象に表示 |
| **手書き（昭和改製前・除籍）** | Vision の手書き認識精度に限界 → **OCR テキストに加えてページ画像を Claude に渡すマルチモーダル読解**を手書き様式のときだけ実施（トークンコスト増は様式判定で必要時に限定）。全体確信度が閾値未満なら抽出を粗くても出し、人の修正前提で確認 UI に回す（空で返すより修正が速い） |
| **改製による様式差** | 様式判定→様式別プロンプトの2段階（§1-2,3）。プロンプトは config のデータとして様式別に持つ（新様式・自治体差はプロンプト修正のみ） |
| **除籍の斜線・バツ印** | 「名欄に×や斜線がある者・『除籍』『死亡』等の記載がある者」を `除籍済み=true` として抽出させ、身分事項（死亡・婚姻による除籍・転籍）と突合。斜線は OCR テキストに現れないことが多いため、**マルチモーダル読解時は画像からの検出を明示指示**し、テキストのみの場合は身分事項からの推定であることを confidence に反映 |
| **縦書き・レイアウト崩れ** | files:annotate のテキスト順が崩れる場合がある → 構造化プロンプトに「記載順に依存せず、人物単位で再構成せよ」を固定。改善しない様式はマルチモーダルに切替 |
| **複数ページ・複数戸籍の合綴** | ページごとに本籍・筆頭者を抽出し、変わり目で戸籍単位に分割（1 PDF = 複数 App 44 レコードを許容）。分割の妥当性も確認 UI の確認対象 |

## 3. 既存 8項目抽出との関係（置き換え・段階移行）

| 段階 | 内容 |
|---|---|
| 併存期 | 読解 v2 は M5 受信箱経由で稼働。既存 `/scan`（戸籍フォルダ→App 27）はそのまま |
| 切替 | v2 の確認フロー運用が安定したら、GAS の監視対象から戸籍フォルダを外し受信箱へ一本化（GAS 側はフォルダ設定の変更のみ） |
| 温存 | App 27 は過去データの参照台帳として残す（新規書き込み停止・削除しない） |

- 現行 8項目の情報は v2 スキーマ（02）に包含される（8項目→人物1行＋身分事項に相当）。
  **現行の潜在バグ（養子縁組 DROP_DOWN への人名書き込み）は v2 では構造上発生しない**

## 4. 連続戸籍ループの「読解」部分（souzoku-houki 10 §4 / H10 との結線）

```
確認済の戸籍（App 44）に 従前戸籍（本籍・筆頭者）または 改製原・除籍への遡及情報がある
 → 案件の書類チェックリストに未取得の従前戸籍があるか照合
 → 未取得なら「次は○○市（本籍）の△△（筆頭者）の戸籍」を承認キューに提案
   （H10 の弁護士承認 → M1 職務上請求の自動起票へ。**本設計は「提案の生成」まで**。
    起票以降は H10 の実装をそのまま使う）
 → 出生まで到達（出生事項の記載を検出）→「連続完成の見込み」を表示。
   ただし `連続戸籍充足=yes` の宣言は弁護士のみ（既存原則・機械は参考表示まで）
```

## 5. 確信度と品質管理

- confidence はフィールド単位（0〜1・tool use で強制）。閾値（config・既定 0.8）未満の
  フィールドは確認 UI で赤色強調・必須確認
- 読解の回帰テスト: サンプル戸籍セット（現行・改製原・除籍・手書きの各様式）に対する
  抽出一致率テストを `test_triage_classification.py` と同型で作成（モデル更新時の
  劣化検知が README の運用手順に乗る）
- **個人情報の取り扱い**: ページ画像・読解 JSON は kintone（既存の管理境界内）にのみ保存。
  Claude API へは既存の他機能と同じ送信範囲（新たな外部保存先を作らない）
