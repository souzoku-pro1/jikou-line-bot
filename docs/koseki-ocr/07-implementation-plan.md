- 依存: R1, T4-1, T1-2 ／ 参照: 01
- 作業: doc_type=戸籍謄本系 の DOC_TYPE_CONFIG エントリ・様式判定→様式別プロンプト（config データ）・
  マルチモーダル切替（手書き/低確信時）・フィールド別 confidence・旧字体正規化テーブル・
  複数戸籍合綴の分割・ページ画像保存・要確認キュー接続
- 完了条件: [ ] サンプル戸籍セット（現行/改製原/除籍/手書き 各様式）の抽出一致率テスト作成・
  基準値合格 [ ] 分割・冪等・要確認行きのテスト PASS [ ] M5 本体変更がエントリ追加のみ
- **2026-07-05 裁定（受領口の暫定分離・スコープ再定義）**: T4-1（M5 /scan/v2・
  DOC_TYPE_CONFIG）が未実装のため、R2 の受領口は独立エンドポイント
  `POST /koseki/ingest`（koseki_ingest.py）で暫定実装した。既存 `/scan`
  （戸籍謄本フォルダ→App 27）は不変で併存（01 §3 の併存期のまま）。
  /scan との入口分離は事務所 PC watcher 側のサブフォルダ振り分けで行う
  （**→人作業リスト**）。R2 の実装範囲は「受領・原本PDF/ページ画像保存・
  Vision OCR 生テキストの保存（読解JSON に `{"ocr_text": ...}` で仮置き）・
  App 33 登録（読解状態=未読解）・Drive_fileId 冪等（省略時 sha256）」までとし、
  様式判定・様式別プロンプト・構造化・confidence・旧字体正規化・合綴分割・
  要確認接続の Claude 読解部分は R3 側で実施する。M5 完成後は本エンドポイントを
  DOC_TYPE_CONFIG エントリへ吸収可能とする（architecture/08 §5 の拡張ポイント）
- **2026-07-05 裁定（読解の起動方式・A+B ハイブリッド）**: R2 から切り出した
  Claude 構造化読解は `koseki_reader.py` に実装した。核は B案の形
  （`process_unread_records(limit)` / `process_record(record_id)`・対象は
  読解状態=未読解 のみ）とし、入口は A案（`/koseki/ingest` の登録成功後に
  `process_record` を同期呼び出し。読解の失敗・Claude 全断・例外は ingest の
  成功応答を壊さず、レコードは 未読解 のまま核関数で後日回収できる）。
  定期実行・再読解の結線は核関数の再利用で行う（今回スコープ外）。
  **C案（kintone Webhook 起動）は不採用**: 更新イベント起点の再読解が、人の
  確認・修正（編製日等の手修正・読解JSON の校正）を AI 出力で上書きする
  競合リスクがあるため。核関数が 読解状態=未読解 のみを対象とすることで
  同リスクを構造的に回避する。無効化スイッチは env `KOSEKI_READER_DISABLED=1`・
  低確信度の閾値は `KOSEKI_REREAD_THRESHOLD`（既定 0.5・下回ると 要再読解）。
  v1 の範囲は様式判定込みの単段読解（プロンプトは config.KOSEKI_READER_PROMPTS
  のデータ・様式別最適化はキー追加で拡張）。マルチモーダル切替・合綴分割・
  旧字体正規化テーブルは核関数の拡張として後続タスクで実施する
