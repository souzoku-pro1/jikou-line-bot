# 06. パート2: 預貯金取引明細の整理

通帳コピー・取引明細 PDF を OCR → 時系列データ化し、機械検算と半自動分類を経て
xlsx として整理する。**用途は遺産整理の財産調査に限定**
（使い込み調査は商品廃止済みのため明確にスコープ外。調査対象期間の網羅性・
時効・立証水準といった争訟向けの要件は本設計に含まない）。

## 1. パイプライン

```
[受領] M5 受信箱で doc_type=通帳 / 取引明細 に分類（DOC_TYPE_CONFIG エントリ追加。
       既存の通帳4項目抽出は休眠中のため、本設計が実質の初回実装 — 現行実装との競合なし）
[OCR] Vision（既存）。通帳見開きは表構造が崩れやすい → ページ画像併用（01 §2 と同じ
      マルチモーダル切替）
[構造化] Claude で行単位に抽出:
  {口座: {金融機関, 支店, 種別, 口座番号, 名義}, 
   明細: [{日付, 摘要_原文, 出金, 入金, 残高, confidence}], ページ範囲}
[機械検算] 残高連続性チェック（§2）→ 不整合行に検算フラグ
[分類] 摘要の自動分類（§3）
[出力] xlsx 生成（§4）→ App 36 財産行に添付・最終残高を評価額候補に（§5）
[確認] 人（03 の確認 UI は使わず **xlsx 上で確認・修正**。表データの校正は Excel が
       最速のため。修正後の xlsx を kintone に再添付して確定）
```

## 2. 残高連続性チェック（OCR 誤読の機械検出）

```
各行について: 前行残高 − 出金 + 入金 == 当行残高 を検算
 ├─ 一致 → OK
 ├─ 不一致 → 検算フラグ（xlsx で行を赤色表示・「要確認」列に理由を記載）
 │   典型原因: 数字の OCR 誤読（1↔7・0↔8）/ 行の取りこぼし / ページ順の乱れ
 └─ 連続不一致が閾値（既定10%）超 → ページ順・見開き分割の問題と推定し
     読解単位を見直して再実行（それでも超えるなら要確認キューへ・LINE 警報）
```

- 通帳の繰越ページ・合算記帳（「○行分省略」等）は「連続性の断点」として明示行を挿入
  （検算をリセット。断点だらけの明細は財産調査上の注意として xlsx 先頭に注記）
- この検算があるため、**明細の数値は1行ずつ人が照合しなくてよい**（不一致行だけ見る）
  — 半自動設計の効率の要

## 3. 摘要の自動分類（Claude 判定・確信度低は未分類）

- 分類: 振込入金 / 振込出金 / 引落（公共料金・カード・保険料） / ATM入出金 / 年金 /
  給与 / 利息 / 税金 / 医療費 / その他 / **未分類**
- Claude tool use（claude_gateway 経由・バッチで1口座分を1回で判定）。
  confidence < 閾値（既定 0.8）は**未分類のまま人に回す**（誤分類より未分類が安全）
- 分類は集計シート（§4）の科目別小計に使うだけで、法的判断・使途の評価はしない
  （スコープ限定と整合）

## 4. 出力先の比較と推奨

| 観点 | kintone SUBTABLE | **xlsx 生成（推奨）** |
|---|---|---|
| 行数 | 数百〜数千行で編集・表示が重い（SUBTABLE の実用限界） | 数千行でも軽快 |
| 人の確認・修正 | 行単位の修正が苦痛 | Excel の編集・フィルタ・色分けが最速 |
| 提出・共有 | 都度エクスポート | 家裁・税理士・依頼者への提出物としてそのまま使える |
| 集計 | kintone 集計は貧弱 | 科目別小計・月次推移シートを同梱生成 |
| データの真実性 | kintone が正 | **確定版 xlsx を App 36 添付＝正**とする運用規約（明細を kintone に二重保持しない） |
| 新規依存 | なし | openpyxl を requirements に追加（軽量・純Python） |

**推奨: xlsx 生成。** シート構成: ①明細（検算フラグ・分類列・confidence 列付き）
②科目別集計 ③月次推移 ④注記（断点・要確認一覧・生成メタ情報）。

## 5. App 36（財産）への接続

- 1口座 = App 36 の財産行1件（種別=預貯金・特定情報=金融機関/支店/種別/口座番号）
- `原本` に通帳/明細 PDF・確定版 xlsx を添付。`評価額` 候補に**基準日時点の残高**
  （相続開始日残高が明細範囲内にあればその値・なければ最終残高＋注記）を設定
  — **`評価確定=yes` は従来どおり人**（souzoku-shorui 02 §6 の分担を変えない）
- 残高証明書（souzoku-shorui 02 §4）が別途ある場合はそちらが評価の正。
  明細整理はあくまで財産の把握・裏付け（両者の突合差異があれば注記）

## 6. テスト観点

- 検算: 一致/不一致/断点/閾値超過の各分岐（数値誤読の合成データ）
- 分類: バッチ判定・未分類への安全側倒し（モック）
- xlsx: 4シート構成・色分け・数千行のスモーク（生成時間）
- App 36 接続: 財産行 upsert・基準日残高の選択ロジック・評価確定が人に残ること
