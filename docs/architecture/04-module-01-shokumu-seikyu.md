# 04. モジュール1: 職務上請求

市区町村への戸籍・住民票等の職務上請求を、起票→成果物生成→承認→発送→返送消込まで
発送管理（App 30）のトランザクションとして扱う。

## 0. 業務前提

- 弁護士が職務上請求書（日弁連統一用紙・**複写式**）で市区町村に郵送請求する
- 送付物: ①職務上請求書 ②定額小為替（交付手数料分） ③返信用（レターパック等）
- 市区町村から戸籍等が**返送**される → M5（スキャン受領）が消込む
- 物理制約により完全無人化できない作業は次の3点に**限定**する:
  弁護士の「承認」／事務員の「印刷・小為替同封・投函・追跡番号入力」／警報後の対応

## 1. フロー（App 30 状態機械へのマッピング）

```
[起票] 案件アプリのアプリアクション（GUI設定）で App 30 に下書きレコード作成
   ├─ 自動引き継ぎ: ユニット種別 / 案件アプリID / 案件レコードID / 顧客名表示用
   └─ 人が入力: 宛先市区町村（App 31 ルックアップ→宛先名・郵便番号・住所に反映）
               請求内訳（チャネル固有データ§2）/ 対象者情報 / 利用目的
      保存 → Webhook → /hub/dispatch
[prepare]（Railway 自動）
   1. App 31 から手数料を取得し 小為替合計額 を計算
   2. 成果物3点を生成して添付:
      a. 職務上請求書 重ね打ちPDF（§3）
      b. レターパック宛名ラベルPDF（往路: 市区町村宛 / 復路: 事務所宛の2面）
      c. 発送準備チェックリストPDF（請求内訳・小為替合計・同封物一覧）
   3. 発送ステータス → 承認待ち + 弁護士へ LINE 承認依頼
[承認] 弁護士が kintone で成果物を確認 → 承認済（または却下）
[dispatch]（Railway 自動・冪等ガード通過後）
   外部APIなし。発送ステータス → 発送処理中 とし、事務員へ印刷指示通知
   （manual_mailing チャネル。printing は人）
[投函] 事務員が印刷・小為替同封・投函し、追跡番号 を入力して 発送済 に手動変更
   → Webhook → Railway が 返送期限 = 今日 + UNIT_CONFIG.return_deadline_days を設定し
     発送ステータス → 返送待ち
[返送] M5 が返送スキャンを消込 → 送達結果=返送受領・完了（08 §3）
[監視] 日次ジョブ return_deadline_check: 返送期限 超過 → LINE 警報（レコードは返送待ちのまま）
```

## 2. チャネル固有データ（JSON スキーマ）

```json
{
  "request_items": [
    {"type": "戸籍謄本", "count": 1},
    {"type": "除籍謄本", "count": 2}
  ],
  "target": {
    "本籍": "埼玉県戸田市...",
    "筆頭者": "山田太郎",
    "対象者": "山田花子",
    "生年月日": "1950-03-15"
  },
  "purpose": "消滅時効援用通知書の送付先調査のため",
  "kogawase_total": 1950
}
```

- `type` の許容値: 戸籍謄本 / 除籍謄本 / 改製原戸籍 / 戸籍の附票 / 住民票 / 住民票の除票
- `kogawase_total` は prepare が App 31 の手数料 × count で計算して書き込む
  （手数料フィールドが空の市区町村 → **エラー遷移せず**「App 31 の手数料を登録してください」の
  登録依頼警報。§5 の PrepareDeferred 参照。2026-07-03 T3-1 指示で「エラー遷移」から変更）

## 3. 複写式用紙への重ね打ち印刷

### 3.1 方式

> **実装済み（2026-07-03 T3-2・同日の追加要件で2様式対応に改訂）**: 職務上請求書は2様式あり、
> 様式別の座標表を実装。請求書類種別から自動判定し、両様式が必要な請求は複数枚生成する。
> - **様式第1号**（戸籍謄本等・戸籍法10条の2第3項〜第5項）: 戸籍・除籍・原戸籍。
>   `FORM1_COORDS`（35項目）。「いずれかに○」のため**1枚につき1種別**（種別ごとに1枚）。
>   **請求に係る者の生年月日は必須**（欠損→エラー遷移＋「生年月日が必要です」警報）
> - **様式第2号**（住民票の写し等・住基法12条の3第2項等）: 住民票・除票・戸籍の附票。
>   `FORM2_COORDS`（38項目）。該当種別すべてに○（1枚に集約）。生年月日は任意（空欄は非印字）
>
> 共通仕様: チェック印「レ」・選択丸「○」（U+2713 "✓" は同梱フォント外のため）。
> 生年月日は「昭和25年3月15日」「1950-03-15」両形式対応（元号 M/T/S/H/R に○＋年月日）。
> 請求者欄の印字は様式1=既定OFF（印字済み在庫）・様式2=既定ON（`print_requester` で上書き可）。
> **座標は初期値であり実用紙の実測が未実施** —
> 手順は [04a-shokumu-seikyu-calibration.md](04a-shokumu-seikyu-calibration.md)。
> 校正用PDF（様式別方眼2枚＋サンプル2枚＋レターパック方眼）は
> `python -m channels.shokumu_seikyu <出力フォルダ>` で生成。

- 統一用紙（A4・複写式）に、**記入欄の文字だけ**を印字した PDF を重ね打ちする
- `hub/address_label.render_overlay()`（03 §7）を使用。座標表はこのチャネルが持つ:

```python
# channels/shokumu_seikyu.py
FORM_COORDS = {
    "請求者資格":   (x_mm, y_mm),
    "事務所名":     (x_mm, y_mm),
    "対象者本籍":   (x_mm, y_mm),
    "対象者筆頭者": (x_mm, y_mm),
    "請求種別チェック_戸籍謄本": (x_mm, y_mm),   # "✓" を印字
    "通数_戸籍謄本": (x_mm, y_mm),
    "利用目的":     (x_mm, y_mm),
    # ... 実用紙の実測で確定（T3-2 の作業内容）
}
```

- 事務所固定情報（事務所名・弁護士名・登録番号・所在地）は config の定数で持つ

### 3.2 制約と運用

- 複写式のためプリンタは**手差し1枚給紙**で運用（用紙セット方向を README 化）
- 統一用紙の版が変わったら座標がずれる → 版番号を config に持ち、
  試し刷り確認をリリース手順に含める

### 3.3 キャリブレーション手順（運用ドキュメント化する内容）

1. `render_overlay(grid=True)` の方眼PDFを白紙に印刷
2. 統一用紙に透かして各欄の座標を読み取り `FORM_COORDS` を更新
3. プリンタ個体差は `PRINT_OFFSET_X_MM` / `PRINT_OFFSET_Y_MM`（環境変数）で微調整
4. 本番用紙1枚で試し刷りして確定

## 4. 発送・返送追跡

- `追跡番号`: レターパックの追跡番号を投函時に人が入力（バーコード読み取り運用可）
- 日本郵便は個人向け追跡の公式 API を一般提供していないため、**v1 ではスクレイピングしない**
  （壊れやすく「平常時人間ゼロ」に反する）。追跡は次の2段で代替する:
  1. M5 の返送消込（正常系: 人手ゼロで完了に到達）
  2. `返送期限` 超過の日次警報（異常系のみ人が追跡番号で日本郵便サイトを確認）
- 将来拡張ポイント: 日本郵便 API（法人契約）が使えるようになれば
  `scheduler.register_interval` にポーリングジョブを1本足すだけ（設計変更なし）

## 5. 異常系一覧

| 事象 | 検知 | 自動対応 | 警報 |
|---|---|---|---|
| 宛先市区町村の未登録・住所未登録 | prepare | **PrepareDeferred（下書き維持・遷移なし）** | ○（登録依頼文言。「エラーではありません」明記） |
| 手数料未登録 | prepare | **PrepareDeferred（下書き維持・遷移なし）** | ○（登録依頼文言） |
| 請求種別不正・チャネル固有データ不備 | prepare | エラー遷移 | ○ |
| テンプレート/フォント欠損 | prepare / 日次検査 | エラー遷移 | ○ |
| 返送期限超過 | 日次ジョブ | なし（返送待ち維持） | ○（追跡番号を添えて通知） |
| 不正な状態遷移（手動操作ミス） | dispatch | 処理せず skip | ○ |

> **PrepareDeferred（2026-07-03 T3-1 で導入）**: マスタ登録待ち等の「エラーではない中断」。
> ディスパッチャは状態を変更せず（下書きのまま）登録依頼の LINE 警報のみ送る。
> 人が App 31 に登録後、レコードを下書きのまま再保存すれば Webhook 再発火で自動再処理される。
> 実装: `channels/base.PrepareDeferred` ＋ `hub/dispatch._handle_prepare` の専用ハンドリング。

## 6. テスト観点（実装タスクの完了条件に含める）

- 小為替計算: 請求内訳 × App 31 手数料の組み合わせ（手数料欠損・0通・複数種別）
- 重ね打ちPDF: 座標表の全キーが印字されること・長文の縮小・grid モードのスモークテスト
- 状態遷移: 起票→prepare→承認待ち、承認済→発送処理中（冪等: 二重 Webhook で1回のみ）
- 返送期限: 発送済→返送待ち時の期限設定、超過検知ジョブ（日付固定モック）
