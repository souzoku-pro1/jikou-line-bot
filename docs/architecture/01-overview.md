## 3. 責務分担

| レイヤ | 責務 | 持たないもの |
|---|---|---|
| **案件アプリ（App 21 等）** | 案件・顧客のマスタ情報、案件ステータス | 発送・受領の履歴（発送管理への関連レコード表示のみ） |
| **発送管理（App 30）** | 全チャネルのトランザクション台帳、承認 UI、状態機械、添付成果物（docx/PDF/CSV）の保管 | 文面テンプレート（リポジトリ側）、チャネル固有ロジック |
| **マスタアプリ（App 31/32）** | 事務員がメンテする参照データ（宛先・文章ブロック） | 業務ロジック |
| **hub/ 共通ライブラリ** | kintone I/O・文書生成・承認連携・警報・スケジューラの共通実装 | チャネル固有の知識 |
| **チャネルアダプタ** | チャネル固有の成果物生成と外部 API 呼び出し、結果の書き戻し | 承認判断（必ず hub/approval 経由）、直接の LINE 送信 |
| **kintone Webhook** | 状態遷移の通知（トリガー） | ロジック（Railway 側で最新レコードを取り直して判定＝App 29 と同じ二重チェック方式） |

## 4. 発送管理の状態機械（全チャネル共通）

```
 下書き ──(必須項目充足・成果物添付)──▶ 承認待ち ──弁護士承認──▶ 承認済
                                        │却下                    │Webhook
                                        ▼                        ▼
                                       却下                  発送処理中
                                                                 │成功         │失敗(リトライ超過)
                                                                 ▼             ▼
                                              発送済 ──(返送想定あり)──▶ 返送待ち   エラー ──▶ LINE警報
                                                 │(返送想定なし)           │M5が返送消込
                                                 ▼                       ▼
                                                完了 ◀────────────────── 完了
                                                             （期限超過 ─▶ LINE警報・返送待ちのまま）
```

- **承認済 → 発送処理中** の遷移だけが Railway への Webhook を発火する
  （App 29 の「承認済 + 送信済み=no」パターンの一般化）
- 冪等ガード: `実行済み` フィールド（yes/no）。Webhook 二重配信・再送でも1回しか実行しない
- チャネルごとの「発送処理」の中身はディスパッチャがチャネル値で振り分ける

## 5. 制約の適用方法

### 5.1 平常時は人間の作業ゼロ・異常時のみ LINE 警報

| 場面 | 平常時 | 異常時（LINE警報） |
|---|---|---|
| 成果物生成（docx/PDF/CSV） | Webhook 起点で自動生成・添付 | テンプレート差込失敗・マスタ不整合 |
| 発送実行（FAX/CSV 等） | 承認済 Webhook で自動実行 | 外部 API エラーのリトライ超過 |
| 送達・返送追跡 | 日次ジョブが自動消込 | 期限超過・送達失敗 |
| マスタ整合性 | 日次死活監視がスキーマ検証 | フィールド/選択肢の破壊的変更 |

- 人間（弁護士）が登場するのは「**承認**」と「**警報を受けた後の対応**」のみ
- 警報は既存 `notify_admin_line`（スロットル付き）を `hub/notify.py` に移設して共用
- 日次ジョブは `daily_healthcheck.py` のスケジューラを job registry 化して相乗り
  （返送期限チェック・FAX結果確認・マスタ検証を同じ仕組みに登録）

### 5.2 弁護士名義の対外発信は必ず承認ステップを挟む

- 対外発信（M1 職務上請求 / M2 内容証明 / M3 FAX / M4 郵送）は**全件**
  発送管理レコードの `承認待ち → 承認済` を経由する。承認スキップ設定は設けない
- 承認 UI は kintone（発送管理レコードを開き、添付の成果物を確認して状態を変更）
- 承認依頼は既存の「【承認依頼】」LINE Push と同型の通知を弁護士に送る
- App 29（LINE 返信承認）は現行のまま**変更しない**。発信物の承認は発送管理側で行い、
  仕組み（状態+冪等フラグ+Webhook）だけを共通化する

### 5.3 拡張ポイント（相続放棄・相続一般・補助金ユニット）

| 拡張ポイント | 仕組み |
|---|---|
| ユニット識別 | 発送管理・マスタ全アプリに `ユニット種別` DROP_DOWN（時効援用/相続放棄/相続一般/補助金）。選択肢追加のみで新ユニット対応 |
| 案件参照 | `(ユニット種別, 案件アプリID, 案件レコードID, 顧客名表示用)` の4フィールド組。案件アプリの構造には依存しない |
| ユニット別設定 | `config.py` に `UNIT_CONFIG` dict（案件アプリID env 名・氏名フィールドコード・利用可能チャネル・テンプレートdir）。新ユニット＝エントリ追加 |
| テンプレート | `docx_templates/<ユニット>/<種別>.docx` の規約ベース配置 |
| 文章ブロック | 同封物マスタ（App 32）の `対象ユニット` 列でフィルタ |
| Claude プロンプト | 特記事項生成・書類分類のプロンプトはユニット別に config で差し替え可能にする |
| チャネルアダプタ | ユニット非依存に書く（入力は発送管理レコードのみ）。新ユニットでコード変更ゼロ |

## 6. 技術方針（既存踏襲）

- 言語/FW: Python / FastAPI / Railway 単一サービス（現行のまま。分割はしない）
- kintone 連携: REST API + Webhook（合言葉クエリ + 最新レコード再取得 + 冪等フラグ）
- 文書生成: docx = python-docx（`document_webhook.fill_template` を共通化）、
  ラベル/重ね打ち = **PDF（reportlab を新規採用**・座標指定印字が必須のため）
- AI: 既存 `claude_gateway.create_message_with_fallback` を全モジュールで使用
  （モデル名は config.py 一元管理・フォールバック/警報込み）
- テスト: unittest 流儀（httpx/requests をモック）。外部 API 実呼び出しテストは
  `railway run` 前提で skipUnless ガード
- 秘密情報: Railway 環境変数。Webhook は合言葉 URL 方式（既存踏襲）
