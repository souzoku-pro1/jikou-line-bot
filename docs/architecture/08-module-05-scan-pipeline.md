# 08. モジュール5: スキャン→OCR→kintone 受領パイプライン

既存の Google Drive（GAS）+ Vision API + Claude 抽出構成を拡張し、
**書類種別の自動分類**と**案件・発送レコードへの自動紐付け（返送消込）**を追加する。
ハブに「入る」側の唯一のアダプタ。

## 0. 現状（実装済み・`POST /scan`）

```
GAS（フォルダ監視: 相談カード / 戸籍謄本 / 通帳）
 → POST /scan {pdf_base64, folder_name, file_name}
 → Vision OCR → フォルダ別プロンプトで Claude 抽出 → フォルダ別アプリに登録
```

課題: ①人がフォルダに仕分ける必要がある ②案件への紐付けがない ③原本 PDF が kintone に残らない
④重複投入の防止がない。

## 1. 拡張後のパイプライン（`POST /scan/v2`・既存 `/scan` は互換維持）

```
GAS（監視: 「受信箱」1フォルダのみ。仕分け不要）
 → POST /scan/v2 {pdf_base64, drive_file_id, file_name}
 → ① 冪等チェック: Drive_fileId で App 30 を検索。既処理なら skip を返す
 → ② Vision OCR（既存 _ocr_pdf_bytes を流用）
 → ③ Claude 分類 + 抽出（tool use classify_document・§2）
 → ④ 紐付け解決（§3）
 → ⑤ 書き戻し:
      (a) 返送消込 …… App 30 の 返送待ち レコードを 完了 に（受領ファイル添付）
      (b) 種別別アプリ登録 …… 既存 _SCAN_FOLDER_CONFIG を一般化した
          DOC_TYPE_CONFIG（分類→登録先アプリ+抽出スキーマ）で登録・原本 PDF 添付
      (c) 未確定 …… App 30 に 方向=受領・発送ステータス=要確認 レコードを作成 + LINE 警報
 → ⑥ GAS へ処理結果を返す → GAS がファイルを 処理済み / 要確認 フォルダへ移動
```

- 平常時（分類・紐付け成功）は人手ゼロ。人が呼ばれるのは (c) の警報時のみ

## 2. 分類器（`channels/scan_intake.py`）

`claude_gateway.create_message_with_fallback` + tool use 強制（chat_responder と同型）:

```python
CLASSIFY_TOOL = {
  "name": "classify_document",
  "input_schema": {
    "doc_type": {"enum": [
        "戸籍謄本", "除籍謄本", "改製原戸籍", "戸籍の附票", "住民票",
        "相談カード", "通帳", "固定資産税課税明細", "名寄帳",
        "裁判所書類", "信用情報開示結果", "業者からの通知", "その他"]},
    "confidence": {"type": "number"},          # 0.0〜1.0
    "extracted": {"type": "object"},           # doc_type 別スキーマ（既存プロンプトを移植）
    "case_hints": {                            # 紐付け手がかり
        "氏名": ..., "生年月日": ..., "本籍": ..., "発行市区町村": ..., "事件番号": ...}
  }
}
```

- 既存 `_SCAN_FOLDER_CONFIG` の3プロンプト（相談カード・戸籍謄本・通帳）は
  `DOC_TYPE_CONFIG` の抽出スキーマとして移植（プロンプト文言は変えず一致率を保つ）
- `confidence < 0.8`（config 定数）→ 要確認行き
- **回帰テスト**: `test_triage_classification.py` と同型の分類一致率テストを作る
  （実 OCR テキストのサンプルセットに対し一致率 95% 以上で合格。
  モデル更新時の回帰確認が README 運用手順にそのまま乗る）

## 3. 紐付け解決（優先順に3段階）

| 優先 | 対象 | 照合キー | 成立時の動作 |
|---|---|---|---|
| 1 | App 30 `返送待ち`（チャネル=職務上請求） | 発行市区町村=宛先名 かつ 対象者氏名一致（case_hints） | **返送消込**: 送達結果=返送受領・完了・受領ファイル添付・案件へは App 30 経由で辿れる |
| 2 | 案件アプリ（UNIT_CONFIG を全ユニット横断） | 氏名+生年月日（または本籍） | 種別別アプリへ登録し、`案件アプリID`/`案件レコードID` を付記した受領記録を App 30 に作成（方向=受領・完了） |
| 3 | 不成立 | — | 要確認レコード + LINE 警報 |

- 照合は完全一致を基本とし、氏名は空白・旧字体正規化（`_normalize_shozaichi` と同様の
  正規化ヘルパを scan_intake 内に持つ）。**曖昧一致で誤紐付けするくらいなら要確認に落とす**
  （誤消込は「発送物が届いていないのに完了」となり実害が大きい）

## 4. 要確認キューと再処理

- 要確認レコード（App 30）: OCR 全文の先頭 500 字を `エラー詳細` に、分類結果と手がかりを
  `チャネル固有データ` に保存。受領ファイル（PDF）添付
- 人の操作: レコードを開き、正しい `チャネル固有データ.doc_type` や案件参照を補記して
  発送ステータスを `下書き` に変更 → Webhook → `adapter.reprocess()` が⑤を再実行
- LINE 警報は都度送信（受信箱の流量は少ない想定。多くなればスロットル/日次まとめに変更可能）

## 5. 既存資産の扱い

| 資産 | 扱い |
|---|---|
| `POST /scan`（フォルダ指定） | **互換維持**。GAS 移行完了後に非推奨化（削除はしない） |
| `POST /ocr/fixed-asset` | 現状維持。将来 doc_type=固定資産税課税明細 の DOC_TYPE_CONFIG に吸収可能（拡張ポイント） |
| `_ocr_pdf_bytes` | `channels/scan_intake.py` へ移設し main.py から re-export |
| 受領先アプリ（相談カード等） | `原本PDF`（FILE）と `Drive_fileId` フィールドを追加（02 §5） |

## 6. GAS 側の変更仕様（リポジトリ外・docs として管理）

1. 監視対象を「受信箱」1フォルダに変更（従来の3フォルダ監視は移行期間中並存）
2. 送信ペイロードに `drive_file_id` を追加
3. レスポンスの `result`（ok / skip / needs_review / error）に応じて
   処理済み / 要確認 フォルダへ移動。error は移動せず次回リトライ（最大3回→要確認へ）
4. GAS コード本文は `docs/gas/scan_inbox.gs.md` に写しを保存する（現状 GAS はリポジトリ外で
   バージョン管理されていないため、仕様と写しを docs で管理する）

## 7. 異常系一覧

| 事象 | 検知 | 自動対応 | 警報 |
|---|---|---|---|
| 同一ファイル二重投入 | Drive_fileId 検索 | skip 応答 | × |
| OCR 空結果・Vision エラー | ② | GAS リトライ（→3回で要確認） | 3回目 ○ |
| 分類確信度不足 | ③ | 要確認レコード | ○ |
| 紐付け不成立 | ④ | 要確認レコード | ○ |
| 返送待ち候補が複数一致 | ④ | 要確認レコード（誤消込防止） | ○ |
| kintone 登録失敗 | ⑤ | エラー応答（GAS リトライ） | 連続時 ○ |

## 8. テスト観点

- 冪等: 同一 drive_file_id の二重 POST で登録が1件
- 分類一致率回帰テスト（§2・95% 基準・`railway run` ガード）
- 紐付け: 3段階の優先順・複数一致→要確認・氏名正規化
- 消込: 返送待ち→完了・受領ファイル添付・`実行済み` に影響しないこと
- 再処理: 要確認→下書き変更→reprocess の一巡
- `/scan` 互換: 既存3フォルダのリクエストが従前どおり動く（既存挙動の回帰テスト）
