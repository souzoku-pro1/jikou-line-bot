# 05. 締切管理（相続放棄 03 の期日設計を流用）

相続放棄の「社内締切・提出目標日・通知済み閾値・毎日通知」の体系をそのまま流用する。
相違点は**起算の向き**だけ（熟慮期間=起算日から前向きに計算／補助金=公募締切から逆算）。

## 1. 期日の定義（申請フェーズ）

| 期日 | 計算 | 用途 |
|---|---|---|
| 公募締切 | App 40 `締切日時`（外部確定値・時刻まで） | 対外の絶対期限。電子申請はサーバ混雑・不備差戻しがあるため直前提出を避ける |
| **社内締切日** | 公募締切 − 5日（config・公募マスタで上書き可） | **警報・進行管理の基準**（相続放棄と同じ役割） |
| 提出目標日 | 社内締切日 − 2日 | 承認→転記→提出の作業バッファ |
| 収集期限 | 提出目標日 − 計画書作成リードタイム（既定14日） | 書類チェックリストの督促基準 |

- 受任判断時の逆算ゲート: `今日 + GBizID取得リードタイム（未取得なら既定14日）+
  収集見込み + 計画書作成リードタイム > 提出目標日` → **「間に合わないリスク」を
  受任前に警報**（相続放棄 10 §5 の受任時突合と同型）。受任するかは弁護士判断

## 2. 警報体系（日次ジョブ `hojokin_deadline_check`・hub/scheduler 登録）

対象: status が {完了, 不採択, 不受任, 辞任} 以外の全案件。
残日数 = 社内締切日 − 今日。`通知済み閾値` CHECK_BOX で冪等（相続放棄 03 §4 と同一機構）。

| 条件 | 警報 | 併せて行う自動処理 |
|---|---|---|
| 残日数 ≤ 14 かつ未通知 | 【社内締切14日前】＋書類チェック残・計画書確定状態 | — |
| 残日数 ≤ 7 かつ未通知 | 【社内締切7日前】 | 顧客にも進捗依頼の定型送信（不足書類一覧） |
| **提出目標日到達** | 【提出目標日・要対応】以後毎日 | — |
| 社内締切超過・未提出 | 【社内締切超過】公募締切までの実残時間を併記 | — |
| 公募締切超過・未提出 | 【申請不能】 | status を弁護士判断待ちに（次回公募への振替提案を添付） |
| 公募マスタ側: 状態=公募中 かつ 締切超過 | 【マスタ更新漏れ】 | 状態を 締切済 に自動更新 |

- 診断段階（受任前）の案件にも「対象公募の締切が近い」リマインドを1回送る
  （検討中の離脱防止・マーケティング上も有効）

## 3. 採択後の期日（実績報告ほか）

- `採択結果=採択` の記録（人・1フィールド）をトリガーに、公募マスタの
  `実績報告ルール`（交付決定からN日 / 事業終了からN日 / 固定日）から
  `実績報告期限` を自動設定 → §2 と同じ警報体系を適用（閾値 30/14/7・通知済み閾値を流用）
- 交付決定日・事業終了日は人が記録（jGrants に API がないため）。
  未記録のまま採択後30日 → 「交付決定日を記録してください」警報（データ欠損の検知）
- 賃上げ報告等の付帯報告義務がある公募は `実績報告ルール` に行を追加するだけ
  （期限種別の追加もマスタ表現の範囲）

## 4. 相続放棄 03 との対応表（流用の明示）

| 相続放棄 03 | 本ユニット | 差分 |
|---|---|---|
| 法定満了日（前向き計算・142条繰越） | 公募締切（外部確定値をそのまま使用） | **計算不要**（マスタの値が正）。二本立ての「正確値」側が入力値になるだけで警報機構は同一 |
| 社内締切日（安全側） | 公募締切 − バッファ | 同じ役割・同じフィールド名 |
| 提出目標日（郵送バッファ） | 転記・提出の作業バッファ | 同上 |
| 通知済み閾値 CHECK_BOX・毎日通知切替 | そのまま流用 | なし |
| 期間伸長申立の検知 | 「間に合わない→次回公募への振替提案」 | 伸長という救済がない分、受任前ゲート（§1）を厳しめに |

## 5. テスト観点

- 逆算ゲートの境界（ちょうど提出目標日）・GBizID 未取得時のリードタイム加算
- 閾値警報の冪等・毎日通知切替・公募締切超過の status 変更
- 実績報告ルール3種の期限計算・交付決定日未記録の検知
- マスタ更新漏れ（公募中×締切超過）の自動更新
