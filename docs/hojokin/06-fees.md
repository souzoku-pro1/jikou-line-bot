# 06. 報酬設計の構造（着手金＋成功報酬型・Stripe 実装方式）

業界標準（着手金＋成功報酬）を前提に、**構造だけを設計**する。
金額・率は公募マスタの `報酬設定` SUBTABLE に**人が登録**する（コードに持たない）。

## 1. 報酬の構成要素（公募マスタで公募ごとに設定）

| 要素 | 請求タイミング | Stripe 実装 |
|---|---|---|
| 着手金 | 契約時（CloudSign 締結とセット） | 既存フロー流用（H8 の型: Payment Link 送付 → Webhook で入金記録 → 締結+決済=受任確定） |
| 成功報酬 | 採択結果の記録後（§2 で選択） | Payment Link を**承認後に**自動送付（§3） |
| 実費（GBizID 代行等はしない・実費は原則顧客直接負担） | — | 原則発生させない構造（立替を作らない） |

## 2. 成功報酬の請求タイミング（選択肢の提示・公募ごとにマスタで選択）

| 選択肢 | 長所 | 短所 | 向く場面 |
|---|---|---|---|
| (a) 採択発表時 | 回収が早い・実務で最多 | 交付決定前の取消リスク（僅少だが存在）・顧客の資金は未着 | 既定値として推奨 |
| (b) 交付決定時 | 補助対象の確定後で紛争リスク最小 | 採択→交付決定の期間分回収が遅い | 再構築系など交付決定までの審査が重い公募 |
| (c) 補助金入金時 | 顧客の資金繰りに最も優しい（訴求点になる） | 回収が最も遅い・実績報告の完了に依存 | 実績報告まで受任する高関与プラン |

- **推奨: 既定 (a)・公募マスタで (b)(c) を選択可能**。どれを選んでも実装は同一
  （トリガーとなる status/フィールドが違うだけ）。委任契約書の条項テンプレート
  （CloudSign 側の書類雛形）もタイミング別に3種用意する【人の作業】

## 3. 実装フロー（採択→請求→消込）

```
👤 採択結果=採択 を記録（1フィールド・01 [6]）
 🤖 成功報酬額を計算: 報酬設定（率 or 固定額）× 採択額（採択額フィールドは人が記録。
    率計算の基礎を「申請額」でなく「採択額（交付決定額）」にするかもマスタの設定値）
 🤖 請求ドラフトを App 30 に起票（チャネル=なし・承認待ち。金額・計算根拠を表示）
 ✅ 弁護士承認（金額の最終確認。**請求も対外発信として承認必須の原則に乗せる**）
 🤖 Stripe Payment Link を生成し LINE で送付（metadata に ユニット・案件ID — H8/G3 の方式）
 🤖 Webhook で入金 → 成功報酬請求状態=入金済 → 完了報告へ
 ⚠ 請求後14日未入金 → リマインド自動送信 → 30日で弁護士警報
```

- Stripe の実装は **Payment Link（都度生成）を推奨**。Invoice（Stripe 請求書）は
  請求書 PDF・自動リマインダーが付く利点があるが、既存実装（checkout.session.completed）
  との統一性と BtoC 顧客の支払い体験を優先。**BtoB 比率が上がり請求書払いの要望が
  増えた段階で Invoice 併用に拡張**（拡張ポイントとして明記・実装は差し替え不要の追加）
- 不採択時: 成功報酬なし（着手金のみ）。`成功報酬請求状態=対象外` にして完了フローへ

## 4. kintone フィールド（App 41・03 §2 に含む）

`採択結果` / `採択額` / `成功報酬請求状態`（対象外/未請求/請求済/入金済）/
`Stripe決済ID`（着手金と成功報酬で2枠 or サブテーブル化は実装時判断）

## 5. テスト観点

- 報酬計算（率・固定・基礎額の設定分岐）・タイミング3種のトリガー
- 承認前に Payment Link が送られないこと（承認ガード）
- 入金 Webhook の案件紐付け（metadata 方式・H8 のテストを拡張）
- 未入金リマインド・警報の冪等
