## 中核課題への答え：「新しい公募が出たらマスタに登録するだけ」の構造

公募ごとの差分（要件・様式・締切・加点）を**3つのマスタデータ**に押し込み、
コードは「マスタを解釈する汎用エンジン」だけを持つ:

```
★App 40 公募マスタ   1公募回 = 1レコード（締切・補助率・様式・必要書類・加点・適格性ルール）
★App 42 診断変数マスタ 公募横断の質問バンク（変数名・質問文・型。例: 従業員数・業種・資本金）
docx_templates/hojokin/ 事業計画書の構成テンプレート（公募類型別・規約配置）
```

- 適格性ルールは**宣言的ルール（JSON）＋ Claude 補助のハイブリッド**（02 §3 で比較・推奨）
- **新公募の追加手順（コード変更ゼロの証明・受け入れ検査を 08 K11 に含める）**:
  1. jGrants 公募情報 API の週次取込（K3）が公募マスタの**下書きを自動作成**（締切・上限額等）
  2. 人（事務員+弁護士）が公募要領を読み、適格性ルール行・必要書類行・加点行を登録
  3. 診断変数が既存バンクにあればそのまま。新変数が必要な場合のみ App 42 に1行追加
     （質問文・型・選択肢もデータ。**ここまで全て kintone 登録のみ**）
  4. 登録完了→`状態=公募中` に変更した瞬間から Bot が診断・受付を開始する

## 3原則の継承と補助金固有の追加原則

1. 平常時人間ゼロ・異常時 LINE 警報（締切警報は相続放棄の体系を流用・05）
2. **対外提出（jGrants 提出・事務局への書類送付）は弁護士承認必須**
3. チャネルはアダプタ・案件はユニット（M4/M5・CloudSign/Stripe は既存のまま流用）
4. **適格性判定は安全側**: 判定不能・境界は「要確認（弁護士）」に倒す。不適格の断定も
   弁護士確認を経る（機会損失の防止と誤案内の防止の両面）
5. **AI の役割は「構成と初稿」に限定**（04）: 採択可能性に関わる品質（事業の実態把握・
   数値計画・加点戦略）は人が担う
