# 02. 適格性診断 Bot

公募マスタ駆動で「質問の生成」と「適格性の判定」を行う。
時効援用/相続放棄のトリアージ（tool use・二重チェック・承認キュー）の型を流用する。

## 1. 質問の動的生成（診断変数マスタ駆動）

```
1. 状態=公募中 の公募マスタ全行から、適格性ルール（§2）が参照する変数名を集合として抽出
2. 診断変数マスタ（App 42）から該当変数の質問文・型・選択肢を取得
3. 依存順（前提変数→詳細変数）に LINE で質問（選択肢はクイックリプライ）
   例: 事業形態（法人/個人）→ 業種 → 従業員数 → 資本金 → 所在地 → 直近売上 →
       投資予定の内容 → 創業年
4. 回答は案件（App 41）の `診断回答`（JSON）に upsert（相続放棄 H3 と同じ逐次保存・
   途中離脱しても再開できる）
```

- 質問数の上限（既定12問）を超える場合は、絞り込み効果の大きい変数
  （多くの公募のルールに登場する変数）から優先。**優先度もマスタの数値**（コード変更なし）
- 1回の診断で**全公募中案件を横断判定**する（「持続化は不適格だがIT導入は適格」を1回で出す）

## 2. 適格性ルールの表現形式（公募マスタに持たせるデータ）

公募マスタの `適格性ルール` SUBTABLE。1行 = 1条件:

| 列 | 例 |
|---|---|
| `変数名` | `従業員数`（App 42 の変数名と一致） |
| `演算子` | `<=` `>=` `==` `in` `not_in` `between` の6種のみ（拡張しない） |
| `値` | `20`／`製造業,建設業`（in はカンマ区切り） |
| `条件区分` | 必須要件 / 除外要件 / **要確認要件**（§3 ハイブリッドの Claude 側に回す） |
| `根拠メモ` | 公募要領の該当箇所（人間の登録時メモ・判定結果の説明に使用） |

判定: `必須要件を全て満たす AND 除外要件に1つも該当しない → 適格候補`。
要確認要件が1つでもあれば最終判定は「要確認」（§3）。

## 3. 判定方式の比較と推奨（ハイブリッド）

| 方式 | 長所 | 短所 |
|---|---|---|
| (a) 宣言的ルールのみ | 決定的・テスト可能・高速・説明可能 | 定性要件（「革新的な取組」「販路開拓に資する」等）を表現できない。無理に表現すると誤判定 |
| (b) Claude 判定のみ（公募要領全文＋回答→判定） | 定性要件も扱える・マスタ登録が楽 | 非決定的・誤判定（特に「適格」の誤断定）が事業リスクに直結・回帰テスト困難 |
| **(c) ハイブリッド（推奨）** | 定量は (a) で決定的に足切り・定性は Claude が「要確認+根拠」を出すだけで**判定の主体にならない** | マスタ設計がやや複雑（条件区分の使い分け） |

**推奨 (c) の動作**:

```
定量要件（必須/除外）→ 宣言的ルールで機械判定（不適格はここで確定・根拠メモ付きで案内）
定性要件（条件区分=要確認）→ Claude（tool use・claude_gateway 経由）が
  「回答内容が要件に沿う見込みか」を confidence 付きで下書き → 出力は必ず「要確認」であり、
  適格/不適格を Claude が確定することはない → 承認キュー（App 29）で弁護士が確定
境界・回答不能・変数欠損 → 要確認（安全側）
```

- **「適格」の顧客への断定は常に留保付き文言**（「要件を満たす可能性が高いです。
  正式な判定は公募要領に基づき弁護士が確認します」）。トリアージの禁則にも入れる（§5）
- 判定ログ: 案件に `診断結果`（公募ごとの三値＋根拠 JSON）を保存（弁護士の確認材料・
  誤判定時の遡及調査用）

## 4. 回帰テスト（公募マスタの品質保証）

- 公募マスタに `判定テストケース` SUBTABLE（回答セット JSON → 期待判定）を持たせ、
  **マスタ登録者がテストケースも登録する**運用。日次死活監視がテストケースを
  ルールエンジンに流して期待判定と照合（マスタの登録ミス・改変事故を翌朝検知）
- ルールエンジン自体の単体テストは 6演算子×境界値で網羅（K4 完了条件）

## 5. トリアージ（補助金版カテゴリ・G1 一般化の前提）

### 自動送信 OK

| カテゴリ | 例 |
|---|---|
| 挨拶・雑談 / 営業案内・アクセス / 費用の定型案内 / 進捗の事実回答 | 他ユニットと同じ |
| 制度の一般説明 | 「持続化補助金って何が対象？」（公募マスタの登録内容の範囲で回答） |
| 必要書類の案内 | チェックリストの事実 |
| 締切の事実回答 | **公募マスタの締切・社内締切の事実のみ**（「間に合うか」は承認必須） |
| 診断の再実行・回答修正 | 機械的操作 |

### 承認必須

| カテゴリ | 理由 |
|---|---|
| 適格性の個別判断 | §3 のとおり確定は弁護士 |
| **間に合うか・採択可能性の見込み** | 期待値管理と法的責任。断定禁止 |
| **経費の対象可否**（「この機械は対象？」） | 交付規程の解釈。誤答は不正受給リスク |
| 事業計画の内容相談 / 他社事例 | 品質の中核・守秘 |
| 費用交渉 / クレーム / 解約辞任 / 第三者 / その他判断系 | 他ユニットと同じ |

プロンプト禁則（追加分）: 採択可能性・採択率の言及禁止／経費対象の断定禁止／
「確実に通る」等の保証表現禁止／診断結果は常に留保付き文言。

## 6. 異常系

| 事象 | 対応 |
|---|---|
| 公募中の公募が0件 | 診断は受け付けて「現在募集中の公募がない」定型＋次回公募の通知登録（公募マスタに `通知希望` 案件を紐付け、公募中になったら自動案内） |
| ルールが参照する変数が App 42 に無い | マスタ整合性エラー→日次検査で警報（App 32 同期検査と同型・登録ミス検知） |
| Claude 全断 | 既存 handle_claude_outage の型（定型文＋承認キュー） |
| 判定テストケース不一致 | 日次警報「公募○○のルールがテストケースと不一致」 |
