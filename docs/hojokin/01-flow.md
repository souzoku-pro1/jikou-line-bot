# 01. 全体フロー

記号: 🤖=完全自動 / ✅=弁護士承認 / 👤=人の実作業 / ⚠=異常時のみ LINE 警報

## 0. jGrants 等の電子申請システム接続調査（2026-07-03・自動化境界の根拠）

| 接続点 | 調査結果 | 自動化境界 |
|---|---|---|
| 公募情報の取得 | **公開 API あり**（デジタル庁資料で「補助金検索用の公開 API」を確認。近年のアップデートで事業名等がレスポンスに追加されている。認証不要の検索系 REST） | 🤖 週次ジョブで新規公募を取込み、公募マスタの下書きを自動生成（K3。エンドポイント仕様の確定は K3 スパイクで実施） |
| 申請の提出 | **申請者向けの提出 API は確認できない**。提出は GビズID プライム（またはメンバー）でログインする Web UI のみ。マイページの事前登録情報による入力補助・事業単位の委任機能はあるが、いずれも UI 機能 | 👤 提出操作は人。システムは「**申請パッケージ**」（添付書類一式＋jGrants 入力項目の転記シート・04 §4）を承認済みで用意するところまで（e内容証明・申述パッケージと同じ境界） |
| 採択結果・事務局連絡 | jGrants マイページ・メール通知（API なし） | 👤 人が結果を kintone に記録（1フィールド）→ 以降の処理（成功報酬請求・実績報告期限設定）は 🤖 |
| GビズID | 事業者本人のアカウントが必要（プライム）。事務所への委任は jGrants の委任機能で可能 | 顧客に GBizID プライム取得を案内する定型フロー（未取得だと申請できないため、**診断直後に取得案内**を自動送信・発行リードタイムを締切逆算に織り込む） |
| 独自ポータル系（持続化の商工会議所経由等）・郵送 | 公募による | 公募マスタの `申請方式` で分岐（jGrants / 独自ポータル / 郵送=M4） |

> ブラウザ自動操作（RPA）による jGrants 自動提出は**採用しない**。UI 変更で壊れる・
> GBizID 認証の代行リスク・誤提出の影響が大きい。「平常時人間ゼロ」の例外として
> 提出クリックは人に残す（承認と一体の操作のため実務負荷は小さい）。

## 1. フロー全体

```
[0] 集客: SEO 記事 / LP（07 の訴求骨子）→ 補助金専用 LINE 公式アカウント友だち追加
 🤖 挨拶＋適格性診断の開始（H2 のマルチチャネル基盤に /webhook/hojokin を追加）
      │
[1] 適格性診断（02）
 🤖 公募マスタ（状態=公募中）×診断変数マスタから質問を動的生成 → 回答を案件（App 41）に upsert
 🤖 ハイブリッド判定 → 公募ごとに 適格 / 不適格 / 要確認 の三値＋根拠
 ⚠ 要確認 → 弁護士 LINE（承認キューに判定理由つきで登録）
 🤖 適格公募が1つ以上 → 診断結果の提示（補助上限・締切・報酬目安）→ [2] へ
 🤖 GビズID プライム未取得なら取得案内を即時送信（発行リードタイムを締切逆算に反映）
      │
[2] 見積・契約・決済
 🤖 見積提示: 公募マスタの報酬設定（着手金・成功報酬率。06）から自動生成
 ✅ 受任判断: 締切まで日数が不足する案件（05 の逆算で間に合わない）・要確認案件は弁護士判断
 🤖 CloudSign 委任契約 → Stripe 着手金 → **締結＋決済完了=受任確定**（H8 の型そのまま）
      │
[3] 資料収集（締切タイマー稼働・05 の監視対象）
 🤖 公募マスタの必要書類リストから案件の書類チェックリストを自動生成（H9 の型）
 🤖 依頼者へ提出依頼を定型送信（決算書・確定申告書・登記事項証明・見積書等）
 🤖 受領は M5（スキャン受領・DOC_TYPE_CONFIG に 決算書/確定申告書/見積書 を追加）
    または LINE ファイル送信（PDF を受信箱へ中継）→ チェックリスト消込
 ⚠ 社内締切から逆算した収集期限の超過 → 警報
      │
[4] 事業計画書・申請書類の作成（04）
 🤖 ヒアリング（Bot の追加質問: 事業内容・課題・投資内容・効果）→ 構造化して案件に保存
 🤖 AI 下書き: 公募類型別テンプレートの**構成に沿った初稿**を生成（04 の縛り）
 👤 弁護士（＋顧客）が仕上げ: 数値計画・実現可能性・加点戦略は人
 🤖 加点項目チェックリスト（公募マスタの加点行から生成）で取りこぼしを機械検知
 ✅ 完成した計画書・申請書類一式を弁護士が最終確認
      │
[5] 申請（対外提出・承認必須）
 🤖 申請パッケージ生成: 添付一式＋ jGrants 転記シート（04 §4）→ App 30 起票（承認待ち）
 ✅ 弁護士承認 → 👤 事務員が jGrants に転記・アップロード・提出（顧客委任のもと）
    ／郵送公募は M4 の承認発送
 🤖 提出記録（提出日時・受付番号）を案件に記録 → status=申請済み
      │
[6] 採択発表
 👤 結果を kintone に記録（採択/不採択の1フィールド。jGrants に API なし）
 🤖 採択 → 顧客へ祝い連絡＋成功報酬の請求（✅ 承認後に Stripe リンク送付・06）
        → 交付申請・実績報告期限を公募マスタのルールから自動設定（05）
 🤖 不採択 → 顧客へ定型連絡＋次回公募・別公募の再診断提案（[1] へ戻るループ）
      │
[7] 採択後（交付決定〜実績報告〜入金）
 🤖 実績報告期限の警報体系（05。証憑収集は [3] と同じ M5 チェックリスト方式）
 🤖 実績報告書類の下書き（経費明細は受領証憑から機械集計・様式転記シート）
 ✅→👤 提出は [5] と同じ承認→人の提出
 🤖 補助金入金の確認（顧客申告 or 通帳スキャン）→ 案件クローズ・完了報告
```

## 2. 人間が登場する場面（それ以外は全自動）

| 場面 | 誰 | 備考 |
|---|---|---|
| 要確認案件の適格性判断・受任判断 | 弁護士 | 安全側に倒した分だけここに集まる |
| 事業計画書の仕上げ | 弁護士（顧客と協働） | 採択品質の中核。AI は初稿まで（04） |
| 申請パッケージの承認・jGrants 提出操作 | 弁護士承認＋事務員提出 | 提出 API がないため（§0） |
| 採択結果の記録 | 事務員 | 1フィールド入力のみ |
| 公募マスタの要件登録 | 事務員＋弁護士 | 新公募ごと。README の手順1〜4 |
| 警報対応 | 弁護士 | 締切・収集遅延・判定不能 |
