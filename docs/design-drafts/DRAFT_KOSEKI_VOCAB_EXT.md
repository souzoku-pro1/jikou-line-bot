## 3. 判別方法の実地検討（住民票（現在）vs 除票 vs 附票）

読解（OCR テキスト）での判別材料:

| 書類 | 判別材料（記載実態） | 誤読リスク |
|---|---|---|
| 住民票の除票 | 表題「住民票**の除票**」または「除票」表記／**消除事由・消除日**（転出・死亡等）の記載／「除票につき〜」注記 | 表題が「住民票」のまま除票欄だけで示す自治体書式がある（表題のみ判定は不可） |
| 戸籍の附票 | 表題「**戸籍の附票**」（本籍・筆頭者＋住所履歴の構成） | 「附票の写し（除附票）」の亜種あり |
| 住民票（現在） | 表題「住民票」＋消除記載なし | 消除記載の見落とし＝除票を現在住民票と誤読 |

- 設計方針: 判定は**表題＋消除系記載の二材料の合致**で行い、tool スキーマに
  `resident_doc_kind`（enum: 住民票 / 住民票の除票 / 戸籍の附票 / 不明）＋
  フィールド別 confidence を持たせる（R3/S6 と同一規約）。
- **判別不能（不明・低確信度）は充足に数えない**（R5）。除票と現在住民票の
  誤読は「除票取得済みと誤認→請求候補から外す＝過少提案（危険側）」に直結する
  ため、**「住民票の除票」判定は消除系記載の実在を必須条件**とする（表題のみでは
  除票と判定しない・安全側）。

## 4. 回送ゲート変更の影響範囲（実査）

- 変更点は `_FORWARD_LINES` への 1 entry 追加のみだが、下流は koseki lane
  （`ingest_koseki_pdf` → App33 起票 → koseki_reader）を**戸籍以外の書類が
  初めて流れる**ことになる:
  - koseki_reader のプロンプト（正本 02 §3・config KOSEKI_READER_PROMPTS）は
    戸籍前提＝**除票/附票用のプロンプト分岐 or 統合プロンプトの改定**が必要
    （02 §3 の改定範囲: 戸籍種別 enum・読解 JSON スキーマへの resident 系
    キー追加・確信度規約は既存踏襲）。
  - 人物化（koseki_person_sync）・連続性判定（koseki_chain）は**戸籍のみを
    対象とする現行維持**（除票/附票の読解行は対象外にする除外条件を追加＝
    誤って人物レコードを生成しない）。
  - 既存 pin（test_sortation_ingest.py:444「住民票・戸籍附票は回送しない」）は
    **意図的拡張として更新**（挙動変更を票で明示・回帰は新 pin で固定）。
- ゲート条件（auto 確定・confidence 閾値・SORTATION_FORWARD_ENABLED）は不変。
