### 1.2 応答方針（プロンプト構造・_SYSTEM_PROMPT_BASE :272-）

「会話スタイル（最重要）」節に**既に人間っぽさの指示が存在する**（逐語）:

> - 自然な会話を最優先。テンプレートの棒読み感を出さない
> - 同じことを二度言わない。…既に確認済みの質問・確認事項は絶対に繰り返さない
> - 1メッセージは短く。…詳細は聞かれたら答える
> - 顧客への質問は一度に1つ、答えやすい形で聞く
> - 敬体（です・ます調）、1メッセージ400字以内を目安とする

＝改善の出発点は「指示の追加」ではなく「**指示が実際の応答でどの程度守られているかの
実測**」。守られていない失敗パターンの特定が先（§4）。

### 1.3 品質に影響する構造上の特徴（観察）

- 定型文面が多層にある: 即時定型（PENDING_REPLY・CRISIS_SUPPORT_REPLY 等 :66-106）・
  FAQ定型・必須文言（FEE_REQUIRED_PHRASES・留保文言 B型 :192-）。**定型と生成文の
  接続部が「棒読み感」の主要リスク**（必須文言の挿入が文脈から浮く構造）。
- サーバーガードは**降格のみ**（品質を上げる方向の介入はない）。降格時の顧客体験は
  PENDING_REPLY（確認中）固定＝**待たされ感**の発生点。
- 履歴は直近10往復固定。長い相談での「前に言ったことを忘れる」体験の構造的上限。
- カテゴリ reason は弁護士向けであり顧客文面の品質評価には使われていない。

## 2. 匿名化ログ抽出の設計（[人]が実行する前提の手順案）

### 2.1 規律との整合（RV-10）

- App28 チャットログ・承認キューの実体は**顧客 PII そのもの**。PC-A は読まない。
  抽出・匿名化の実行者は**[人]（弁護士）**とし、PC-A が受け取るのは匿名化後
  コーパスのみ（DRAFT_RV10_REDACTION_AND_NOTIFY の「既定=完全抑止・emit 契約」と
  同じ向き: 生データが PC-A/レビュー系に渡る経路を作らない）。
- **抽出の実施は別票で[人]ゲート**。本書は手順案の設計のみ。

### 2.2 手順案（別票の実施内容・すべて[人]操作）

1. 抽出単位: 「会話スレッド」（user_id 単位・時系列往復）。件数目安は初回 30-50 スレッド
   （自動送信/承認送信/降格の 3 群から層化抽出。件数は[人]の負担で調整）。
2. 匿名化変換（kintone CSV 出力に対しローカルで実施する想定・スクリプトは実装票で提供）:
   - user_id → 連番仮名（C001…）・氏名/電話/住所/口座 → カテゴリトークン
     （`<氏名>` 等）・業者名 → `<業者A>`（同一スレッド内の同一性のみ保持）
   - 金額・日付は**粒度を落として保持**（「40万円台」「2015年頃」— 応答品質評価には
     時期・金額の文脈が要るため全落としにしない。丸め粒度は[人]裁定）
   - 変換の完全性チェックリスト（残存 PII の目視確認欄）付き
3. 各スレッドにメタ付与（機械可能な範囲・PII 非含有）: カテゴリ・auto_send/降格・
   降格理由・応答文字数・往復数。
4. 成果物: 匿名化コーパス（repo 外・司令塔管理。**repo にはコミットしない**）。

## 3. 評価軸の設計 — 「人間っぽさ」の分解

### 3.1 評価軸（スレッド単位で 1-5 採点・定義固定）

| 軸 | 定義 | 測り方 |
|---|---|---|
| 共感の先出し | 不安・焦りの表明に対し、手続き説明の**前に**受け止めの一文があるか | 判定型（LLM judge＋人抜き取り） |
| 文長の適正 | 1 メッセージの長さが問いの重さに釣り合うか（400字上限内でも「長すぎ」はある） | 実測（文字数分布）＋判定型 |
| 質問数の規律 | 一度に 1 問が守られているか・答えやすい形か | 機械計数＋判定型 |
| 専門用語密度 | 法律用語が説明なしに出る頻度（「援用」「更新事由」等の裸出現） | 用語リスト機械計数 |
| 不安への応答速度 | 不安表明 → 承認制降格で PENDING_REPLY になった率（待たされ感の構造測定） | メタデータ機械計数（§2.2-3） |
| 反復回避 | 既確認事項の再質問・同一定型の再送があるか | 判定型＋_TEMPLATE_DEDUP_MARKERS 同型の機械検出 |
| 棒読み感 | 必須文言・定型の接続が文脈から浮いていないか | 判定型 |

### 3.2 チャッピー型第三者評価の適用案

- 型: v2 系で実績のある「**生成系とは別系統の LLM を審査員にする第三者評価**」を
  応答品質に転用。審査員には上表の軸ごとの定義と 1-5 の係留例（アンカー）を与え、
  スレッド全体を見せて軸別採点＋最も悪い一往復の指摘を返させる。
- 規律: (i) 審査入力は**匿名化コーパスのみ**（§2） (ii) 審査員プロンプトと係留例は
  repo 管理（再現性） (iii) 人（弁護士）が 10-20% を抜き取り採点し、LLM 採点との
  一致率を毎回併記（judge の信頼性を測ってから伸ばす） (iv) 審査員は生成系と
  別プロバイダ/別モデルを既定とし、選定は[人]確認（API 費用が発生するため）。

## 4. 改善ループの設計

### 4.1 ループ全体

```
[人] 匿名化ログ抽出（§2・別票）
  → 評価（§3: 機械計数＋LLM judge＋人抜き取り）
  → 失敗パターン分類（§4.2）
  → 応答方針改訂案の起票（プロンプト・定型文言の diff 案）
  → ★[人]関所: 文言変更は弁護士承認必須（§4.4）
  → トリアージ回帰（既存 120 ケース・TRIAGE_SCOPE=diff）＋品質再評価
  → デプロイ（マージ＝自動デプロイ・タイミングは[人]）
  → 次周期の抽出へ（頻度目安: 月1・[人]の負担で調整）
```

### 4.2 失敗パターン分類（初期分類枠・実測で改廃）

説明過多／共感欠落／定型接続の不自然（必須文言の浮き）／既出の再質問／
専門用語の裸出し／降格過剰による待たされ（ガード側の課題であって文言の課題ではない
ものを分離する — 改善先がプロンプトかガードかで票が変わる）。

### 4.3 A/B 検証の回し方（顧客影響を作らない範囲から）

- **段階1（オフライン・顧客影響ゼロ）**: 改訂前後のプロンプトで**過去の匿名化スレッド
  への応答を再生成**し、judge で盲検比較（どちらが改訂版か伏せる）。ここまでは
  顧客に一切触れない。**初版はこの段階のみを推奨**。
- **段階2（本番・要[人]裁定）**: 本番でのユーザー分割 A/B は「同じ質問に事務所が
  二通りの文体で答える」状態を作るため、法律事務所の応対として許容できるかの
  **[人]判断が先**。既定は「段階1で優位が確認できた改訂のみ全量切替（A/B なし）・
  切替前後の期間比較で代替」とする。
- 品質改善で auto_send 判定・カテゴリ判定を緩めない（安全側ガードは本トラックの
  変更対象外。触れる必要が出たら STOP して別票）。

### 4.4 顧客影響ゲート（関所設計）

- **顧客に届く文言の変更（プロンプト・定型文・必須文言）はすべて弁護士承認必須**。
  承認単位は「変更 diff＋変更理由＋想定影響カテゴリ」の3点セット（PR 上で提示）。
- 必須文言（費用・留保・禁止語）の**削除・緩和は本トラックでは提案しない**
  （接続の自然化=前後の文の書き方のみを扱う）。
- デプロイはマージ＝Railway 自動デプロイのため、タイミングは従来どおり[人]指示。
