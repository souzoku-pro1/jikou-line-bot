# DRAFT: 伝書鳩自動化（司令塔⇔PC-A⇔Codex の票/レビュー/報告 往復）

- 状態: **構想 DRAFT**（2.2 裁定の発動・PC-A 起草）。**実装しない**（構想レベル）。裁定は司令塔。
- 目的: 現在 [人]（大野）が手で貼り付け往復している「票発行→PC-A 実装→報告→Codex レビュー→
  所見→fix 票…」のメッセージ搬送（＝伝書鳩）を、**不変条件を壊さない範囲で**自動化する構想。

## 1. 現状（手動搬送の往復）

1. 司令塔が票（TASK_ID/scope/受入）を発行 → [人]が PC-A へ貼付。
2. PC-A が実装・commit・suite・報告（固定書式）→ [人]が司令塔/Codex へ貼付。
3. Codex がレビュー（対象 SHA 指定）→所見 → [人]が PC-A へ fix 票として貼付。
4. マージ・env・本番反映・**main・既存 ref の更新/上書き push（force-with-lease 等）**は
   [人] 専権（`!`）。

→ 往復の**搬送**を [人] が担っており、貼付の手数・取り違え（GAS アカウント誤投入・token 値の
取り違え等の遠因）・遅延が発生している。

## 2. 不変条件（自動化しても壊してはならない・FROZEN）

- **権限境界（`!`/案1 規律の一意化）**: local branch/commit まで PC-A 可。remote branch 複製・
  PR 作成は現行案1規律の範囲でのみ可（**main・既存 branch への ref 更新禁止**／**tree 一致機械確認の
  報告義務**）。**force-with-lease 等の ref 上書き push・merge・env・migration・本番デプロイは
  [人] 専権**。自動化は**搬送のみ**で、これらの実行主体を機械化しない（`!` 失敗時の代替実行禁止・
  大野の新 `!` 待ちも不変）。
- **宛先明記規律**: 各メッセージの宛先（[人]/[PC-A]/[司令塔]/Codex）と TASK_ID を明示。
- **redaction/secret 規律**: 搬送物に secret 値・PII を載せない（token 値・registry secret・
  顧客情報は搬送対象外・名前/参照のみ）。
- **tree 一致機械確認**: PC-A の remote 反映は git blob 経由＋tree 一致確認を維持。
- **モデル実測記録**: 各タスクのモデル実測（Fable 5）記録を維持。

## 3. 構想（段階・いずれも搬送の自動化に限定）

- **段A（最小・搬送ログ化）**: 票/報告/所見を構造化テキスト（TASK_ID・宛先・本文・対象 SHA）で
  やり取りし、貼付を1チャネル（例: 専用 issue/スレッド）へ集約。搬送は依然 [人] だが取り違え低減。
- **段B（半自動搬送）**: PC-A の報告（固定書式）を機械可読ヘッダ付きで出力し、[人]の貼付先を
  1 操作化（テンプレ化）。Codex 所見も同フォーマットで受領。
- **段C（自動搬送・要裁定）**: 司令塔票→PC-A→報告→Codex の**搬送のみ**を bot 化（例: GitHub の
  PR コメント/ラベルをトリガに次段へ受け渡す）。**実行（マージ/env/main・既存 ref の更新/上書き
  push（force-with-lease 等））は引き続き [人] の `!` ゲートを必ず経由**（bot は搬送と通知まで・
  実行はしない）。

## 4. リスクと未決（構想段階の論点）

- 自動搬送が `!` ゲートを迂回しないことの構造保証（bot に本番権限を持たせない）。
- secret/PII の混入防止（搬送前の redaction チェックの自動化・emit 契約の搬送層への適用）。
- Codex 連携の API/UI 経路（headless 可否・認証）。
- 障害時の手動フォールバック（bot 停止＝現行の手動搬送へ即戻せること）。

## 5. スコープ外（本 DRAFT では扱わない）

- 実装・スケジュール・費用。マージ/本番反映の自動化（不変条件で禁止）。
- 本 DRAFT は **Phase 2 以降の検討材料**であり、着手可否・優先度は司令塔裁定。
