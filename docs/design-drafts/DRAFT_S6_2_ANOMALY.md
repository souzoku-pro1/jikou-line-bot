## 2. 系統の位置づけ（要件）

- **プッシュ型**: 明細読解の完了時に**自動スクリーニング**が走り、検知があれば
  **業務 LINE 通知**する（人が照会しなくても異常が浮上する）。
- **Q系（プル型・指示 Bot 照会）とは系統分離**: プル型は「人が聞いたら答える」
  参照系。本票のプッシュ型は ingest 完了 hook のみに結線し、プル型の応答経路・
  語彙には手を入れない（結線点の分離＝相互に独立して点火/rollback 可能）。
- **「機械は確定しない」**: 検知は**通知まで**。単純承認事由該当性・使途の適否等の
  **判断は弁護士**（通知文言にも断定を書かない——「検知しました・確認してください」
  の道案内型。RV10 準拠で PII 最小・金額/日付/レコード ID の範囲は裁定④）。

## 3. 第2版: 明細の行データ化（設計）

- 読解拡張: bank_reader へ**通帳明細ページの行抽出**を追加——

  見開き複数ページ・繰越行・訂正印はスキップせず低 confidence で保持（安全側）。
- 保存の器（裁定①）: (A) App35 財産レコードのサブテーブル
  (B) 新 App（取引明細台帳・1 行=1 明細行） (C) DB（PostgreSQL・分析専用）。
  検知の再実行・期間 query の観点は (B)/(C) が有利・kintone 可視性は (A)(B)。
- ~~冪等: 口座×日付×摘要×金額×行位置 の複合キーで再送 upsert~~
  **【fix1・S6-2-03 で撤回・再設計】初版キーは「同一原本の再送」と「別原本
  （同内容の別ページ・再取得した通帳）」を区別できず、OCR 訂正で内容が変わると
  別行として二重計上される穴があった**。再設計:
  - ~~**原本 identity**: source doc ID（Drive file ID 等）＋ **source SHA-256**
    （PDF バイト列）——同一 SHA の再送は同一原本・別 SHA は別原本として扱う。~~
  - ~~**行 identity**: 原本 identity × account identity × page identity ×
    row locator~~
    **【fix3・S6-2-07 で撤回・一本化】fix1 の「原本 identity（doc ID＋SHA）を
    行 identity に含める」定義は、fix2 の 3 分離（content/provenance/状態）と
    不整合だった——doc ID（provenance）が identity に入ると、裁定⑩で (A) 収束を
    選んだ場合に同一内容の行が provenance ごとに別 identity になり二重計上する。
    行 identity を以下へ**一本化**する:
  - **行 identity（一本化定義）** = **content identity（source SHA-256）×
    account identity（金融機関/支店/口座番号の正規化組）× page identity
    （ページ番号/見開き位置）× row locator（ページ内行序数）**。
    **provenance（doc ID）は identity に含めない**——この構造は裁定⑩の
    (A) 収束・(B) 重複疑い の**どちらの帰結とも両立する**（provenance は
    行 identity と独立に複数保持/照合できる）。
  - **同一 doc ID＋別 SHA（原本差替え）の supersede 対応付け**は
    「**同一 provenance lineage（同一 doc ID の SHA 系列）内の row locator 対応**」
    で定義する（新旧 SHA 間で account/page/row locator が一致する行を対応付けて
    supersede・対応の取れない行は追加/消失として扱う）。
  - **検知永続キーの一意性（確認・明記）**: S6-2-04 の検知永続キー＝
    **規則 ID × 行 identity** は、新定義の下で「同一内容・同一口座・同一物理
    位置の行に対する同一規則の検知は 1 件」に一意化される（provenance 非依存＝
    別経路到着・収束の別にかかわらず同一検知に合流し、二重通知しない）。
  - **内容 hash**: 正規化した行内容（日付・摘要・金額・残高）の hash を別途保持し、
    **OCR 訂正・再読解で内容が変わった場合は同一 row locator の行を supersede**
    （追記型・旧行は無効化マークで残置＝二重計上せず履歴も失わない）。
  - ~~再送と別原本の区別: 同一 SHA 再送＝完全 skip（idempotent）・別 SHA で
    account/期間が重なる場合は「別原本の重複疑い」として検知系とは別の要確認へ~~
    **【fix2・S6-2-06 で精密化・初版の「同一 SHA＝完全 skip」を撤回（部分取込の
    再送を skip すると不足行が永久に欠落する穴）】3 概念を分離する**:
    - **content identity** = SHA-256（バイト列の同一性）
    - **provenance** = source doc ID（Drive file ID 等・「どこから来たか」）
    - **ingestion 状態** = 原本単位の取込状態 ~~`open（取込中/部分）→ complete →
      failed`~~（**fix4・S6-2-09: この矢印表記は撤回**——遷移の正は fix3 の
      遷移表〔S6-2-08〕のみ。閉集合 {open/complete/failed}・partial は open の
      説明語であり enum 値でない）
    - 組合せ規則:
      1. **同一 SHA の再送**: ingestion 状態が **complete のときのみ skip**。
         **open（部分取込を含む）/ failed は既存行 identity と照合して不足行のみ
         回収**（部分取込の再送が完了経路になる。~~open / partial / failed~~ の
         3 値列挙は fix4・S6-2-09 で訂正——partial は状態値でない）。
      2. **同一 doc ID＋別 SHA**: **原本差替え**（再スキャン・訂正版）として
         旧原本由来の行を supersede（追記型・§3 の内容 hash 規則と同じ型）。
      3. **別 doc ID＋同一 SHA**: 同一内容が別経路から到着（コピー・再アップ
         ロード）——収束（単一原本へ束ねる）か重複疑い（要確認）かは**裁定⑩**。
    - **部分失敗の回収点を揃える**: 原本保存（行データ化）と検知通知の両段は
      **同じ ingestion 状態機械上の回収点**を共有する（原本 complete 未満で
      検知だけ先行しない・検知の reconcile〔S6-2-04〕は ingestion complete を
      前提条件に照合する＝取込途中の部分データで誤検知しない）。
    - **【fix3・S6-2-08】ingestion 状態の遷移表（確定）**:

      | from | to | 条件 |
      |---|---|---|
      | （新規） | open | 原本受理・取込開始 |
      | open | complete | **期待行集合との照合完了後のみ**（読解が返した全行の保存を突合できた場合） |
      | open | failed | 取込失敗（読解全断・保存不能） |
      | failed | open | 再送・再取込の開始（→ complete で回収完了） |
      | complete | （なし） | **complete からの自動逆遷移は禁止**。後発の欠落発見は**要確認通知**または**明示的 reopen（[人] 操作のみ）** |

      - 状態は**閉集合 {open / complete / failed}**。「partial」は **open の
        説明語であり enum 値ではない**（部分取込＝open のまま）。
      - **S6-2-04 の検知 reconcile 前提条件（ingestion complete）は本遷移表上で
        一意に判定できる**——complete は「期待行集合との照合完了」を通過した
        行きの遷移でのみ到達し、自動逆遷移が存在しないため、reconcile 時点の
        complete 判定は単一の状態値読取で確定する（取込中/失敗と誤認する
        中間状態がない）。

## 4. 異常検知（スクリーニング規則）

| # | 規則 | 定義 | 入力 |
|---|---|---|---|
| A1 | **死後出金** | 明細行の日付（西暦確定分）が **被相続人の死亡日より後**の出金行 | App34 被相続人フラグ=yes 行の死亡日 × 明細行 |
| A2 | **生前大口出金** | 死亡日前の**期間窓 W 日以内**（既定案 90 日・env）かつ**閾値 T 円以上**（既定案 500,000 円・env）の出金行 | 同上＋閾値/窓 env |

- **【fix1・S6-2-01】口座×被相続人の相関**: 検知の前提として「この明細行の口座が
  被相続人の口座か」の相関付けが必要（相続人名義口座の死後出金は別の意味を持つ）。
  相関方式は**裁定⑥**（App35 財産行の案件紐付け経由 / 名義人×被相続人の突合 /
  人手の口座指定）。**相関不能（名義人不明・案件紐付けなし・複数解釈）の口座は
  A1/A2 を実行せず「相関不能の口座あり」の要確認通知**（沈黙しない・誤帰属で
  検知もしない）。
- **【fix1・S6-2-02】死亡日当日の 3 分類**: 明細行日付と死亡日の比較は
  **(i) 死亡日より前＝生前（A2 のみ対象）／(ii) 死亡日と同日＝時刻不明・要確認
  （A1 とも A2 とも断定せず専用分類で通知）／(iii) 死亡日より後＝死後（A1 対象）**
  の 3 分類とする（通帳明細・死亡日とも時刻を持たないため当日は判定不能が正）。
  **テスト期待値（本文固定）**: 死亡日 D に対し D-1 の出金＝A2 判定枠・D 当日の
  出金＝「当日・要確認」通知・D+1 の出金＝A1 検知。

- 検知の縮退（安全側）: 死亡日が未確定（空・和暦のみで西暦変換不能）は
  **A1/A2 とも実行せず「判定不能」を通知**（沈黙しない・判定もしない）。
  日付の西暦が null の明細行は「判定不能行あり」として件数を通知に併記
  （silent cap を作らない）。
- 通知: 業務 LINE（DISPATCHBOT）へ 1 案件 1 通に集約（行ごとに送らない・
  throttle_key=案件単位）。文言は件数＋レコード ID＋規則名のみを基本とし、
  金額・日付の掲載範囲は裁定④。
- **【fix1・S6-2-04】検知の永続化と通知状態機械**: 検知は揮発（通知して終わり）に
  しない——
  - **検知の永続キー**: 規則 ID × 行 identity（§3 の冪等キー）で検知行を一意化し
    永続化（器は裁定⑧）。同一検知の再スクリーニングは**新規通知しない**（冪等）。
  - **通知済み状態**: 検知行は `open（未通知）→ notified（通知済み）→ closed
    （人が確認済みとして閉じる・機械は閉じない）`の状態を持つ。
  - **ACK 不明の reconcile**: 通知送信の ACK 喪失（送信後クラッシュ）は
    「open のまま残置→次回 reconcile が再通知」で回収（二重通知の可能性は
    冪等キー併記で受容・沈黙より安全側）。
  - **並行実行**: 同一案件の同時スクリーニング（再送×定期の競合）は検知永続
    キーの UNIQUE で片方が勝つ（負け側は既存検知に合流・二重登録しない）。
- 業務上の含意（設計注記）: 死後出金は相続放棄の法定単純承認（民法921条）
  リスクの一次シグナルであり得るが、**該当性の判断は弁護士**（通知に法的断定を
  書かない＝§2 の原則）。
